# Retrieval — the embedding and vector pipeline

**Realizes:** FEAT-017, FEAT-004 (UC-014), FEAT-005 (UC-020); UC-078, UC-086; US-089, US-100

This document closes the bridge `backend/features.md` deliberately deferred. Feature 007 shipped the vector-rebuild **operation**, the full index **reset**, and an **empty `VECTOR_SOURCE_REGISTRY`**, explicitly deferring the embed-content bridge to "the first vector-backed domain model (the Stage-2 codex, behind the architect gate)". This is that gate.

Nothing here changes the standing rule: **SQLite is the source of truth; LanceDB is a derived sidecar index that is rebuilt from source rows on import and never exported.**

The entities indexed below are defined in the book-domain model: `CodexEntry` in `domain-codex.md`, `Chapter` in `domain-chapter.md`, note changesets in `domain-continuity.md`. Index: `domain-model.md`.

## What gets indexed, and when

| Corpus | Source | Registered at | Why then |
|---|---|---|---|
| **Codex entries** (`CodexEntry.body`, `+ name`) | `CodexEntry` | **Stage 2** | The codex is the first searchable content the system has, and it is what UC-078 needs to reach a chat |
| Chapter text (`Chapter.text`) | `Chapter` | later | UC-086's "the book's own material by meaning" |
| Chapter summaries (`Chapter.summary`) | `Chapter` | later (needs FEAT-012) | Compact continuity; nothing to index before summaries exist |
| State notes (`ChapterNoteChangeset`, `Book.active_notes`) | both | later (needs FEAT-012) | Same |

Users and LLM servers are **configuration, not searchable content** — they stay out, as feature 007 already recorded.

The index is built at **Stage 2** even though both consumers are **Stage 5**. That is deliberate: UC-078 (the codex reaches the chat) and UC-086 (meaning-search) are useless against an index that starts empty on the day they ship, and an index that has been maintained incrementally since the first codex entry was written has real content in it. Building the pipeline with its first corpus also exercises it long before the assistant depends on it.

## Dependency — the single designated embedding server

Embedding uses **the one row designated by FEAT-004 / UC-014** (`LlmServer.is_embedding` true, with `embedding_model` set). At most one row may hold that designation, enforced clear-all-then-set (`backend/features.md` → "Embedding designation").

`services/embedding.py` — the module feature 007 explicitly did **not** build — is the single point where text becomes vectors:

- it resolves the designated server through `db.llm_servers.get_embedding_server()`;
- it resolves the API key through the existing `services/secrets.py::resolve_env_ref` (`$ENV` indirection, resolved at use time only);
- it calls out through the `llm` client, never with a direct HTTP call (`backend.md` → "LLM client").

`services/db_admin.py::rebuild_vector_index()` **already validates this dependency** and raises `DbAdminError(no-embedding-provider)` → 400 when the designation is missing. That validation is now load-bearing rather than defensive.

## Sidecar shape — one table, discriminated by source kind

The sidecar holds **one row per chunk**, in a single table:

| Column | Purpose |
|---|---|
| `vector` | the embedding |
| `book_id` | **hard scope filter** — every query is book-scoped |
| `source_kind` | `codex_entry` \| `chapter` \| `chapter_summary` \| `chapter_notes` |
| `source_id` | the source entity's snowflake, as a string |
| `chunk_index` | position of this chunk within its source |
| `text` | the chunk's own text |

**One table rather than one per corpus.** Every consumer query is "within this book, across kinds, the most relevant *k*". With one table per corpus that becomes N queries plus a client-side merge over scores that are not comparable across independently-built indices. One table makes the merge the index's job, which is where it belongs.

**`book_id` is a hard filter, never a ranking preference.** Cross-book leakage would break the members-only codex rule (US-085) and the book-scoped authorization model outright — a hit from another book is not a worse result, it is a permission violation. The search API takes `book_id` as a required argument for exactly this reason.

**The chunk's text is stored in the index.** The alternative — store ids only and re-read from SQLite — cannot reconstruct *the chunk*, only the whole source row; reproducing chunk boundaries on read would mean running the chunker again and depending on it being byte-identical. The chunk is the retrieval unit, so the index owns it. It is derived data, replaced wholesale whenever its source is re-indexed, and regenerated by `rebuild_index()`.

**Archived codex entries are removed from the index, not flagged.** The index is derived and cheap to correct, and an "exclude archived" predicate is a rule every future consumer would have to remember and one of them would eventually forget. Detecting a *note that references an archived entry* (UC-080) is a name lookup against SQLite, not a vector query, so nothing needs archived entries to remain searchable.

## Chunking

The strategy differs by corpus because the corpora differ in shape:

- **Codex entries** — usually short. An entry under the chunk size is **one chunk**, with its `name` prepended to the chunk text so a name-only query ("Marek") matches the entry that is about Marek. Longer entries split on paragraph boundaries.
- **Chapter text** — **chunks are derived from the body, not from `ChapterChange` rows.** A chapter has one main body (`domain-chapter.md`), and a change is not a stable unit of text: `range`-placed changes overwrite parts of earlier ones, so a one-row-per-change index would accumulate text that is no longer in the chapter. The chunker splits the *current* body on paragraph boundaries into overlapping windows; overlap exists so a sentence spanning a boundary is still reachable from either side.
- **Summaries** — one chunk each; they are short by construction.
- **State notes** — chunked as a body, the same way chapter text is.

**Chunk size and overlap are tuning parameters, not architecture.** They are bounded by the embedding model's input window and belong with the chunker, set when it is built and adjustable without touching anything else. Pinning numbers here would freeze a value that depends on a model the operator chooses at runtime.

## Registry — widening the feature-007 seam

Feature 007's `VECTOR_SOURCE_REGISTRY` holds `(model_class, text_extractor)` tuples. That shape assumed one vector per row. It **widens** at Stage 2 to a typed entry carrying:

- the `source_kind` discriminator;
- the model class;
- a row selector that skips rows which must not be indexed (archived codex entries);
- a **chunker** — row → list of chunk texts — replacing the single `text_extractor`.

This is a deliberate change to a shipped seam, recorded rather than slipped in: the original tuple could not express "one row becomes many vectors", which is exactly what chapter text requires. The registry stays a module-level list that each vector-backed domain feature appends one entry to; `db/vector.py`'s iteration over it is unchanged in spirit.

## Two maintenance paths

### Full rebuild — the existing operation

`rebuild_index()` drops and recreates the sidecar table, then walks the registry re-embedding everything. It is reachable two ways, both already wired through one code path (`run_vector_rebuild()`): the admin trigger `POST /api/admin/db/vector/rebuild` (UC-020) and the automatic post-import refresh. Neither changes; they simply stop indexing zero rows.

### Incremental maintenance — new at Stage 2

A full rebuild of every book's content on every codex save would be absurd, so writes maintain the index in place:

| Event | Index action |
|---|---|
| Codex entry created / edited | delete this `source_id`'s chunks, re-chunk, re-embed, insert |
| Codex entry archived | delete this `source_id`'s chunks |
| Chapter change applied (later stage) | same delete-then-reinsert for that chapter |
| Book destroyed | delete by `book_id` |

Delete-then-reinsert rather than update, because the chunk *count* changes when the text does — an update-in-place would leave orphaned chunks from a longer previous version.

**Index maintenance never blocks the author's save.** The SQLite write commits first; the index update is attempted afterwards and a failure is logged, leaving the index stale until the next rebuild. Refusing an author's save because an embedding server is unreachable would make writing a book depend on an optional subsystem — and the index is derived, so the failure is recoverable by definition.

**No background job queue is introduced.** This is a single-instance app over local SQLite; a queue would add a moving part, a durability question and an operational surface to solve a problem that a synchronous best-effort call plus the existing admin rebuild already covers. If indexing latency ever becomes visible to authors, that is the point to revisit it.

## Vector dimension

The dimension is a property of the **model**, not of configuration, so it is discovered rather than declared:

- `rebuild_index()` embeds a short probe text **before** creating the table, and creates the table with the dimension the model actually returned.
- On an incremental write, the table already exists with a fixed dimension. If an embedding comes back with a different length, the designated embedding model has changed under a live index: the write is **refused with a typed error**, not coerced. A LanceDB table cannot hold mixed dimensions, and truncating or padding to fit would produce vectors whose distances mean nothing.

**Accepted limitation: a model swap at the same dimension is undetectable.** Two different models can both emit, say, 1024-dimension vectors while embedding into completely different spaces; the index would keep accepting writes and silently return nonsense neighbours. Changing the designated embedding server or model (UC-014) therefore **requires an admin rebuild** (UC-020), and the system does not perform one automatically — automatic re-embedding of an entire instance as a side effect of an admin toggling a dropdown is worse than an explicit action. This is an operational rule, and it is recorded as a limitation rather than solved.

## Query surface

One search entry point, book-scoped:

```
search(book_id, query_text, kinds, limit) -> list[Hit]
Hit: source_kind, source_id, chunk_index, text, score
```

`kinds` narrows the corpora (UC-078 asks the codex; UC-086 asks the book's material generally). A hit carries its `source_id` so a consumer can load the authoritative row from SQLite rather than trusting the indexed copy for anything beyond the snippet.

Placement follows the standing layers: the LanceDB session and table handles live in `db/vector.py`; `services/embedding.py` owns the model call; a service composes the two. No LanceDB handle leaves `db/`, for the same reason no `AsyncSession` does.

## Failure modes

| Failure | Behaviour |
|---|---|
| No embedding server designated | `DbAdminError(no-embedding-provider)` → **400** on rebuild (already shipped). Incremental writes log and skip |
| Embedding server unreachable / errors | Author's save **succeeds**; index left stale; logged |
| Dimension mismatch on incremental write | Write refused with a typed error; requires a full rebuild |
| Index empty or stale | Retrieval returns fewer or no hits. Consumers degrade — the assistant loses pulled context, it does not fail |
| Sidecar corrupted or missing | Rebuild from SQLite. The index holds nothing that SQLite does not |

The last row is the property the whole design rests on: **every failure above is recoverable by rebuilding**, because the index is derived.

## Out of scope

- **How retrieved material is ranked, merged, budgeted and placed into a prompt.** That is FEAT-013 assistant internals — context assembly, token budgets, tool protocol — and is undesigned until its own session before Stage 5 (`domain-chat.md` carries the full boundary). This document ends at "here are the relevant chunks".
- **UC-078's relevance criterion.** Product records it as an open `_TBD:` (challenge C27 — "what makes an entry *relevant* enough to reach the chat"). It is a product question with no measurable criterion offered, and choosing a threshold here would resolve it by design. Not done.
- **Web search (UC-087).** Not retrieval over the book's own material; part of the deferred assistant design.
- **Reranking, hybrid keyword+vector search, cross-encoder scoring.** None is required by any stated requirement. Nearest-neighbour over one book's chunks is what UC-078 and UC-086 ask for; anything more is added when a stated need appears.
