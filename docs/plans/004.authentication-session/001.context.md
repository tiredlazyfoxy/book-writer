# Step 001 — step-specific context

Feature-wide facts (token payloads, rotation rule, layering) live in `context.md`
→ "Token model", "Roles", "Layering discipline". Only the narrow facts for this
step are here.

## `require_role` is deferred to feature 005 (not built here)
The admin-role gate (`require_role`) is intentionally deferred to feature 005
(user-management), which has the real consumer and real acceptance criteria for
it. This step builds only `get_current_user` (the FEAT-002 guard) — no role
ladder, no `require_role`.

## Amends 003's `create_token` (cross-feature — not scope drift)

003 delivered a single `create_token(user)` in `services/auth.py` minting one
~30-day JWT (see `docs/plans/003.first-run-bootstrap/001.user-model-auth-primitives.md`).
This step **replaces** it with `create_access_token` + `create_refresh_token`.
Consequently the coder removes/repoints `create_token`, and **the test file
`tests/services/test_auth.py` (003's, DoD-2) still asserts `create_token`
decodes** — the 004 test-coder must update that assertion to the split (mint an
access token, decode it) in the same step so the whole `pytest` suite stays
green. That is why `tests/services/test_auth.py` is in this step's Test files.
`hash_password`, `verify_password`, `generate_signing_key` (also in
`services/auth.py`) are **unchanged** — leave them intact.

## `get_current_user` lives in the service layer

Per the briefing (decision, mirroring the reference
`LLMRPTextOnlyProject/backend/app/services/auth.py`), the FastAPI dependency
`get_current_user` lives in `services/auth.py`, imported by routes as
`from app.services import auth as auth_service`. Importing `fastapi` (`Depends`,
`HTTPBearer`, `HTTPException`) into the service is accepted here — the auth
dependency is a cross-cutting concern, not business/DB orchestration; it
introduces no `session`/`select()`.

## Two-stage decode (why `decode_token_unverified` exists)

The signing key is **per-user**, so verification needs the user's key, but the
key can't be looked up without first knowing which user the token claims to be.
Hence: (1) `decode_token_unverified` reads `user_id` with signature
verification disabled; (2) load the user; (3) `verify_token_signature` validates
sig + exp against that user's key. This mirrors the reference's `get_current_user`
in `LLMRPTextOnlyProject/backend/app/services/auth.py`. Adaptation vs the
reference: additionally enforce `type=="access"`.

## DB/token facts this step relies on
- `users.get_by_id(id)` (from 003) returns the `User` or `None`.
- `User.pwdhash is None` means **disabled** (003 decision 2) — the enabled check.
- `User.jwt_signing_key` / `User.last_key_update` (nullable, from 003) drive
  verification and the rotation window.
- JWT lib is PyJWT (`pyjwt[crypto]`, from `backend.md` deps); HS256. The
  expired-vs-invalid distinction comes from PyJWT's expiry-signature vs
  invalid-token error paths.

## Persistence is the caller's job
`maybe_rotate_signing_key` mutates the in-memory `User` and reports whether it
rotated; it does **not** persist. Step 002 adds `users.update` and calls it after
rotation. This step neither adds nor calls a db write.
