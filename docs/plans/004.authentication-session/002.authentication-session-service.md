# Step 002 — Authentication & session service (rate-limit, login, refresh)

## Goal
Add the in-memory rate-limit store, the `authenticate_user` login orchestration,
the `refresh_access_token` session-renewal orchestration, and the `users.update`
persistence the service needs — all business logic in the service layer per
decision 4.

## Source files
backend/app/services/rate_limit.py
backend/app/services/auth.py
backend/app/db/users.py

## Test files
backend/tests/services/test_login_auth.py

## Interface intent
Rate-limit policy (5 failures / 15-minute lockout, per username, in-memory) and
the generic-refusal rule are defined in `context.md` → "Rate-limiting".

- **`services/rate_limit.py`** (new) — a session-free, in-memory per-username
  failure store:
  - **is_locked(username)** — whether the username is currently locked out
    (≥ threshold failures inside the window).
  - **record_failure(username)** — records one failed attempt at "now",
    pruning attempts older than the window.
  - **clear(username)** — drops the username's failure record (called on a
    successful login).
  - **reset()** — clears the whole store; a test-isolation seam (the store is
    module-global / per-worker).
- **`authenticate_user(username, password)`** (in `services/auth.py`) — the full
  login orchestration, no logic left for the route:
  1. if `rate_limit.is_locked(username)` → raise `AuthError` (the same generic
     refusal — do not reveal the lockout).
  2. load the user via `users.get_by_username`; if `user is None` **or**
     `pwdhash is None` (disabled) → `record_failure` and raise `AuthError`.
  3. `verify_password`; on mismatch → `record_failure` and raise `AuthError`.
  4. on success → `rate_limit.clear`, `maybe_rotate_signing_key`, set
     `last_login`, persist via `users.update`, and return the `User`.
  Optional timing jitter to blunt enumeration may be applied; it is not a DoD.
- **`refresh_access_token(refresh_token)`** (in `services/auth.py`) — session
  renewal, no logic left for the route: reads `user_id`
  (`decode_token_unverified`), loads the user, verifies the token against that
  user's key (`verify_token_signature`) requiring `type=="refresh"`, rejects a
  disabled user (`pwdhash is None`), then `maybe_rotate_signing_key` +
  `users.update` **if** stale, and returns a **new access token**
  (`create_access_token`). Any failure (malformed, bad/rotated signature,
  expired, wrong `type`, unknown/disabled user) → raise `AuthError`.
- **`AuthError`** — a typed exception raised by both service functions for every
  refusal (bad creds, unknown user, disabled, rate-limited, invalid/expired
  refresh). The route (step 003) maps it to a single generic 401. Its home
  (`services/auth.py` or a shared `services` errors module) is the skeleton's
  call; keep it importable by the route without leaking layer boundaries.
- **`users.update(user)`** (in `db/users.py`, amend) — session-free persistence
  of an existing user's mutable fields (`jwt_signing_key`, `last_key_update`,
  `last_login`); opens/closes its own session; returns the updated `User`.
  Added here because 003 shipped no update and the service must not touch
  sessions.

## Definition of done
1. `[test]` `US-003.AC-1` — `authenticate_user` with a valid username/password
   returns the matching `User` and clears that username's failure counter.
2. `[test]` `US-003.AC-2` — `authenticate_user` with a wrong password raises
   `AuthError` and records a failure; an unknown username and a disabled user
   (`pwdhash is None`) raise the **same** `AuthError` (no enumeration, no
   session).
3. `[test]` `US-003.AC-3` — after 5 failed attempts within the window, the next
   `authenticate_user` call is refused with `AuthError` **even when the
   credentials are valid** (rate-limited regardless of validity); once cleared /
   after the window a valid login succeeds again and resets the counter.
4. `[test]` `US-003.AC-1` — a successful `authenticate_user` whose signing key is
   stale (older than the rotation window) rotates the key and persists the change
   (`users.update`), and sets `last_login`; a fresh-key user is not rotated.
   (UC-003 alt: rotation invalidates pre-rotation tokens.)
5. `[test]` `US-003.AC-1` — `refresh_access_token` with a valid refresh token
   returns a **new access token** that `get_current_user` accepts as the same
   user (session renewed).
6. `[test]` `US-004.AC-2` — `refresh_access_token` with an **expired** refresh
   token raises `AuthError` (an expired session cannot be renewed).
7. `[test]` `US-004.AC-1` — `refresh_access_token` for a **disabled** user
   (`pwdhash is None`) raises `AuthError` (access ends when the account is
   disabled).
