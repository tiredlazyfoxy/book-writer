# Step 004 — Frontend token storage + silent-refresh client + api/auth

## Goal
Move `auth.ts` to dual-token (access+refresh) storage with client-side identity
decode and a real `logout`, add `login`/`refresh` to `api/auth`, re-point
`setupCreate` to the token pair, and add the silent-refresh-on-401 interceptor to
`client.ts`.

## Interface intent
- **`src/types/auth.d.ts`** (amend) — replace the login-response `{token}` shape
  with **`TokenResponse`** (`access_token`, `refresh_token`) matching the step-003
  backend schema 1:1; add **`MeResponse`** (`id`, `username`, `role`) and
  **`RefreshRequest`** (`refresh_token`). Keep the existing status and create-DB
  request shapes. Pure wire shapes, no methods, no `any`, no zod.
- **`src/auth.ts`** (amend) — dual-token module state, still no import from
  `src/api/`:
  - store both tokens (e.g. `localStorage["access_token"]` /
    `localStorage["refresh_token"]`) via a setter that writes the pair, plus a
    setter that writes only the access token (used after a refresh);
  - **getToken** — returns the **access** token (what `client.ts` sends as
    Bearer);
  - **getRefreshToken** — returns the refresh token;
  - **getCurrentUser** — client-side JWT-decodes the access token to
    `{id/user_id, username, role}` for identity display (reference pattern,
    allowed by `frontend.md`; `/api/auth/me` is the *server-validated* probe);
  - **logout** — clears both tokens and redirects to `/login/` via
    `window.location.href` (replaces the 002 stub).
- **`src/api/auth.ts`** (amend) — the auth resource module (all HTTP via
  `client.request`):
  - **login** — POST `/api/auth/login` with `{username, password}`, returns
    `TokenResponse`;
  - **refresh** — POST `/api/auth/refresh` with `{refresh_token}`, returns
    `TokenResponse` (the public refresh fn; the interceptor uses its own path,
    see step context);
  - **setupCreate** (amend) — now returns `TokenResponse` (was `{token}`);
  - `getAuthStatus` / `setupImport` unchanged. Each fn keeps a trailing
    optional `AbortSignal`.
- **`src/api/client.ts`** (amend) — add the **silent-refresh-on-401**
  interceptor to `request<T>`: on a `401` for a request that carried a token,
  attempt **one** refresh using `getRefreshToken()`; on success store the new
  access token and **retry the original request once**; on refresh failure (or no
  refresh token) call `logout()` and surface the `ApiError`. Guard against loops:
  never refresh the refresh call itself, and retry at most once. To avoid the
  `client → api/auth → client` import cycle, the interceptor issues its refresh
  `fetch` **inside `client.ts`** (the sanctioned `fetch` location per
  `frontend.md`), not via `api/auth`.

## Definition of done
1. `[manual/live]` `US-003.AC-1` — after `login()` succeeds the app stores both
   tokens: `getToken()` returns the access token and `getRefreshToken()` returns
   the refresh token (confirmable in devtools/localStorage).
2. `[manual/live]` `US-004.AC-2` — an authorized call whose access token has
   expired triggers exactly one silent refresh via the interceptor and the
   original request then succeeds (session continues without a visible re-login).
3. `[manual/live]` `US-004.AC-1` — when the refresh also fails (expired/invalid
   refresh token, or none present), the interceptor calls `logout()`, which
   clears both tokens and redirects to `/login/`.
4. `[manual/live]` `US-003.AC-1` — `getCurrentUser()` decodes the access token to
   the caller's identity (`username`, `role`) for client-side display.
5. `[manual/live]` `cd frontend && npm run build` (tsc + vite) is clean; no
   `any`, no zod; the new DTOs (`TokenResponse`, `MeResponse`, `RefreshRequest`)
   live in `src/types/`; no `fetch` outside `client.ts`/`sse.ts`.
