# Step 002 — step-specific context

Feature-wide facts (rate-limit policy, generic-refusal rule, token model,
rotation rule, layering) live in `context.md`. Narrow facts only here.

## Refresh orchestration lives in the service (placement refinement)

The briefing sketched refresh logic under the *route* step. Per decision 4
(routes are thin; all auth business logic is service-layer), this plan places
`refresh_access_token` in `services/auth.py` **here**, so step 003's route just
calls it and maps errors. Login and refresh are grouped together because both are
session-issuance orchestration needing `maybe_rotate_signing_key` + `users.update`.

## `users.update` is a cross-feature amendment (not scope drift)

003 shipped `db/users.py` with `create` / `get_by_username` / `get_by_id` /
`admin_exists` and **no update**. The service cannot open a session (layer rule),
so persisting `last_login` and a rotated key requires a db write. This step adds
`users.update` to `db/users.py`. Match the module's existing style: session-free,
opens its own session via `get_standalone_session()`, returns model objects, no
ORM/session leak (see `docs/plans/003.first-run-bootstrap` context and
`backend.md` db-layer rules).

## Reference anchors (adapt, don't copy)
`LLMRPTextOnlyProject/backend/app/routes/auth.py` holds the reference login flow
(`_random_delay` jitter, DB-ready guard, rate-limit gate, `get_by_username`,
reject on `user is None or pwdhash is None`, `verify_password`, clear-attempts +
`maybe_rotate_signing_key` + `last_login` + `users.update`, then mint). **Move
all of it into `authenticate_user`** (decision 4). The reference rate-limit is a
`4/60s` module dict in the route — **replace** with the `5/15min` per-username
store in `services/rate_limit.py`. Reference `users.update` lives in
`LLMRPTextOnlyProject/backend/app/db/users.py` — mirror its session-free shape.

## Depends on step 001
Uses `verify_password` + `generate_signing_key` (from 003, in `services/auth.py`)
and `maybe_rotate_signing_key`, `decode_token_unverified`, `verify_token_signature`,
`create_access_token`, `get_current_user` (from step 001). No token-payload

## Test-isolation note
`services/rate_limit.py`'s store is module-global (per worker). Tests must isolate
between cases — call `reset()` (or `clear(username)`) so a lockout from one test
does not bleed into the next. The `5/15min` thresholds should be reachable by the
test without real waiting (e.g. drive 5 failures back-to-back for the lockout
case); do not assert wall-clock window expiry in an automated test — that is a
manual/inspection property.
