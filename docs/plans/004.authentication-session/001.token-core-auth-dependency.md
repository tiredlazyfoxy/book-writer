# Step 001 — Token core + auth dependency

## Goal
Split 003's single `create_token` into access + refresh minting, add token
verification, the FastAPI `get_current_user` auth dependency, and
`maybe_rotate_signing_key` — the session-integrity core the rest of the feature
builds on.

## Source files
backend/app/services/auth.py

## Test files
backend/tests/services/test_tokens.py
backend/tests/services/test_auth.py

## Interface intent
All in `services/auth.py` (no `session`/`select()` here — the dependency loads
users via the existing `db/users` layer). Token payloads and the rotation rule
are defined in `context.md` → "Token model".

- **create_access_token** — mints an HS256 access JWT for a given `User`, signed
  with that user's `jwt_signing_key`; payload carries `user_id`, `username`,
  `role`, `type:"access"`, and a ~30-minute `exp`. Returns the token string.
  (Replaces the access half of 003's `create_token`.)
- **create_refresh_token** — mints an HS256 refresh JWT for a given `User`,
  signed with the same per-user key; payload carries `user_id`, `type:"refresh"`,
  and a ~30-day `exp`. Returns the token string.
- **decode_token_unverified** — reads a token's `user_id` claim **without**
  verifying the signature (needed to know which user's key to verify against).
  Returns the `user_id` (or signals malformed).
- **verify_token_signature** — verifies a token's signature **and** expiry
  against a supplied per-user key; returns the decoded claims. Propagates the
  distinct expiry vs invalid-signature failures so callers can map them (a
  rotated key makes an old token's signature invalid).
- **get_current_user** — a FastAPI dependency (via `HTTPBearer`) that: reads
  `user_id` with `decode_token_unverified`, loads the `User` via
  `users.get_by_id`, verifies with `verify_token_signature` against that user's
  key, requires `type=="access"`, and rejects a user with `pwdhash is None`
  (disabled). Any failure — missing/malformed token, unknown user, bad/rotated
  signature, expired token, wrong `type`, or disabled user — results in **401**.
  On success returns the `User`.
- **maybe_rotate_signing_key** — given a `User`, if its `jwt_signing_key` is
  older than the rotation window (~30 days, by `last_key_update`), replaces the
  key (`generate_signing_key`) and updates `last_key_update`, returning whether a
  rotation occurred (the **caller persists** via `users.update` — added in step
  002). Rotation invalidates all of that user's prior tokens.

## Definition of done
1. `[test]` `US-003.AC-1` — `create_access_token(user)` produces a JWT that
   `verify_token_signature` (with the user's own key) decodes to claims carrying
   `user_id`, `username`, `role`, and `type=="access"`. (Session issued for the
   user.)
2. `[test]` `US-004.AC-2` — an **expired** access token is rejected: passed to
   the verify/`get_current_user` path it yields a 401-class failure, never a
   valid user. (Expired session → request refused.)
3. `[test]` `US-003.AC-1` — a **refresh** token (`type=="refresh"`) is **not**
   accepted by `get_current_user` (only `type=="access"` authenticates); a
   refresh token cannot stand in for an access session.
4. `[test]` `US-003.AC-1` — **UC-003 alt flow**: after `maybe_rotate_signing_key`
   changes a user's key, a token minted with the **old** key fails
   `verify_token_signature`/`get_current_user` (rotation invalidates
   pre-rotation sessions).
5. `[test]` `US-004.AC-1` — a token for a **disabled** user (`pwdhash is None`)
   is rejected by `get_current_user` (401) even though its signature is valid
   (further requests require re-auth).
