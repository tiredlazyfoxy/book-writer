# Step 001 — step-specific context

Feature-wide framing, D1, and the layer rules live in `context.md` — read it first.

Narrow to this step:

- **Engine access.** `db/schema.py` obtains the async engine through the seam
  `db/engine.py` exposes (the same engine `init_db()` runs `create_all` against — see
  `docs/plans/001.backend-scaffold/002.db-engine-core.md`). The skeleton freezes exactly
  which symbol yields it; introspection runs
  `async with engine.connect() as conn: await conn.run_sync(lambda c: inspect(c)…)`.
- **Expected vs actual are compared by column NAME sets in this step.** Type-level
  comparison is not part of the ok/drift/missing decision here; `introspect()` still
  captures type info because step 002's `add_columns` needs it, but the status computation
  keys off column-name set equality only.
- **Test scenario construction.** Tests build drift/missing scenarios in a temporary DB:
  init the tables (via the existing `init_db()`/`DbConfig` temp-DB fixture from
  `docs/architecture/backend.md`'s pytest harness), then create drift with a raw
  `ALTER TABLE … ADD COLUMN` on one table, and create a "missing" case by targeting a
  table not present (dropped, or a metadata table with no live counterpart). Tests read
  expected structure the same way the service does (`SQLModel.metadata`) — they must not
  assume a fixed hardcoded table list, since the registered set (`users`, `llm_servers`)
  is established by prior features and may grow.
- **`DbAdminError` case set** is introduced here but only report/validation cases must be
  raisable now; steps 002–004 raise the remediation/rebuild cases. Keep the discriminator
  a stable, closed set the route layer (step 005) maps to statuses.
