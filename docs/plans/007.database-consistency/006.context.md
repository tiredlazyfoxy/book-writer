# Step 006 — step-specific context

D7 and the frontend conventions are in `context.md`.

Narrow to this step:

- **Blob download and multipart upload both bypass `request<T>`** — that wrapper is JSON-
  only (`204 → undefined`, JSON parse on success). Export reads `res.blob()`; import sends
  `FormData`. Both still read the token from the shared auth accessor (`auth.ts`
  `getToken()`) and set `Authorization: Bearer <token>` by hand.
- **Precedent to mirror for multipart** — `frontend/src/api/auth.ts::setupImport` from
  `docs/plans/003.first-run-bootstrap/005.frontend-first-run-wizard.md`: `FormData` field
  named `file`, no `Content-Type` header (browser sets the multipart boundary), Bearer via
  the token accessor, direct `fetch` (not `request<T>`). Match the field name `file` exactly
  — the backend `UploadFile` field is `file` (step 005).
- **Blob download has no precedent** — it is the frontend's first. The object-URL +
  anchor-click + revoke pattern is standard; keep it inside `exportDatabase()` in
  `api/db.ts` (no `fetch` outside `api/`).
- **JSON endpoints (`report`, `create`, `sync`, `rebuild`)** go through the shared
  `request<T>` from `api/client.ts` normally — only export/import are special-cased.
- **Import refusal surfacing** — a 400 from the import endpoint must reject so the page
  (step 007) can show the refusal (US-019.AC-3). Since `request<T>` isn't used for import,
  the helper checks `res.ok` and throws/rejects with the error detail itself.
- No tests: no frontend test runner exists (context.md). All DoD is `[manual/live]`.
