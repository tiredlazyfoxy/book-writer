# 008 — step context

Feature-wide facts (the `"book"` group decision, the no-backfill decision, the carve-out) are in
`context.md` → decisions 4, 9 and 10, and are not repeated here.

## Where each thing lives today

- **`ToolDef`** is a frozen dataclass in `backend/app/services/tools.py`: `name`, `description`,
  `args_schema`, `group`, `callable=None`, `binder=None`. Groups in use are `"web"`, `"codex"` and
  `"book"`; `TOOL_REGISTRY` currently holds 18 entries.
- **`ToolContext`** is a **non-frozen** dataclass in the same module with **seven** fields today:
  `book_id`, `access`, `subject`, `emit_frame`, `selection_text`, `active_notes_proposal`,
  `codex_creates_this_turn`. **This step adds none.**
- **`BASE_TOOL_NAMES` lives in `backend/app/services/assistant_runtime.py`, not in `tools.py`** — it is
  `("web_search",)` today. That module also holds `ResolvedSubject`, `NO_SUBJECT`, `determine_mode`,
  `allowed_tool_names`, `resolve_turn_tools` and `_CODEX_LIST_MODES`, none of which this step touches.
- **`seed_default_modes()`** (`db/assistant_modes.py`) is check-then-create over `DEFAULT_MODE_KEYS`
  (`edit-character`, `edit-location`, `edit-fact`, `write-chapter`, `close-chapter`), taking prompts
  from `DEFAULT_MODE_SYSTEM_PROMPTS`; **a present key is left entirely untouched**.
- **`seed_default_mode_tools()`** (`db/mode_tools.py`) seeds from
  `DEFAULT_MODE_TOOL_NAMES: dict[str, tuple[str, ...]]` and is idempotent **per mode**
  (`if await list_by_mode(mode_key): continue`). Both seeders are called from `services/setup.py`.

## The bound-tool template

`backend/app/services/chapter_tools.py`. Each tool is
`async def <name>(context: "ToolContext", ...) -> str` returning a **refusal string, never raising**,
with a one-line binder `def bind_<name>(context) -> Callable[..., object]: return functools.partial(<name>, context)`.
Tool modules define callables, schemas and binders only; the `ToolDef(...)` entries are constructed in
`tools.py`, which imports them.

**The one thing NOT to copy:** `chapter_tools.py`'s `_refuse_write` chain runs chapter-resolved →
chapter open → `access.book_state == BookState.archived` → proposal mode. `create_memo` has **no
archived-book link and no proposal-mode link** — memos are the named carve-out and collaboration mode
does not apply to them. DoD-9 is the test that catches a copied chain.

## Why both halves — BASE **and** the seeded rows

They do different jobs and the feature needs both:

- **BASE** covers the **no-mode** case. Product put memos outside FEAT-020's mode set on purpose, so the
  memos list, Book state, the chapters / variants / chats lists and any `planned` or `closed` chapter
  all fall into gating **case 2**. With `create_memo` mode-gated only, asking for a memo would fail **on
  the memos list itself** — the same shape as the lore-list defect feature `025` fixed.
- **The seeded `mode_tool` rows** are what keep **US-129.AC-5 reachable**: an administrator can still
  edit a mode down and remove `create_memo`, and the visible refusal is then observable rather than
  vacuous. **BASE does not override a mode's allowlist.**

## Why the database write is safe here

Every existing context-bearing write tool — `write_codex_draft` and the three `chapter_tools` writes —
**persists nothing**: it validates, emits one `canvas` frame, and the author saves. `create_memo`
writes the row outright, because product is explicit that there is **no draft and no save step**
(US-129.AC-1).

This does **not** break `domain-chat.md`'s "there is no chat → codex write path, by construction". That
was never a rule about tools in general — it is a **codex** rule, load-bearing because a codex entry is
book content subject to collaboration mode, a version token and an owner's review. A memo has none of
those and no second reader, so there is nothing for a draft-and-save step to protect.

## Deliberate absences to preserve

- **No `get_memos` tool and no `edit_memo` tool.** Every active memo is already in the composed prompt
  (step 006), so a fetch tool would be a second path to bytes the model already has, and the two could
  disagree. Product states the same absence from the requirements side (UC-109's postcondition).
- **No new SSE frame and no widened frame.** `tool_call` / `tool_result` are emitted by the **generic
  wrapper around every bound tool** (feature `024`), so visibility comes free.
- **No `ResolvedSubject` member and no `determine_mode` branch.** The memos list is not a mode-bearing
  subject. The last two mode-bearing surfaces each cost one; this one costs none.

## US-130 is prompt-enforced, honestly

The seeded guidance mirrors US-121.AC-3's precedent and inherits its caveat: **an administrator who
rewrites a mode prompt can weaken it.** DoD-11 therefore pins that the guidance **ships in the seeded
prompts**, not that any model obeys it — writing a test that claims otherwise would be claiming a
guarantee the design explicitly does not make.

## Test seeding

`backend/tests/services/test_memo_tools.py` (new) builds a `ToolContext` directly with a constructed
`BookAccess`, as the chapter-tool specs do; **no network, no live model**. The two existing files get
additions only: `test_tools.py` for the registry entry and the group-validity assertion,
`backend/tests/db/test_mode_tools_seed.py` for the seeded name and the per-mode idempotence.
