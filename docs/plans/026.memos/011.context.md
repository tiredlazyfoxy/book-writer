# 011 — step context

Feature-wide facts (the MobX rules, the server-is-truth rule, the jsdom/dnd-kit constraint) are in
`context.md` and are not repeated here. Step 010's context carries the page's own shape.

## The template, named exactly

`frontend/src/work/components/chapters/ChapterOrderList.tsx` and
`frontend/src/work/pages/chaptersPageState.ts`:

- `DndContext collisionDetection={closestCenter} onDragEnd={…}` wrapping
  `SortableContext items={ids} strategy={verticalListSortingStrategy}`;
- a `SortableRow` calling `@dnd-kit`'s **own** `useSortable({ id, disabled: <in flight> })`;
- `handleDragEnd` computing `arrayMove` and funnelling into the **same** persist function the arrow
  buttons use;
- arrow buttons carrying `aria-label={`Move "…" up`}` and disabled at the ends;
- `applyChapterOrder` setting an optimistic `pendingOrder` + `reorderStatus`, calling the api **once**
  with the whole id list, **re-seeding from the server's returned list** on success, and **discarding
  `pendingOrder` on failure** so the view snaps back to server truth;
- `moveChapter(state, bookId, id, "up" | "down")` computing the full swapped list locally and delegating
  to that same persist path.

`@dnd-kit/core` and `@dnd-kit/sortable` are already runtime dependencies (added by feature `014`) — no
package change is needed.

## The one naming difference from the chapters precedent

A chapter has a **title** to put in an arrow's accessible name; a memo has **body text only, which may
be empty**. Step 010's context fixes the rule: derive the name from something stable that survives an
empty body. Whatever step 010 chose for the row's other controls, the arrows must use the **same**
convention — two naming schemes in one row is a spec-authoring trap.

## What the persist call sends

The **full ordered id list of the caller's non-archived memos** — backend step 004 refuses anything
else with a `400` (a short list, a long one, a duplicate, an archived id, another author's id). So:

- never send a partial list or a single moved id;
- never include an archived memo's id;
- never send the archived section's ids when the show-archived filter is on — the filter is a **view**
  concern and does not change what the working list is.

## jsdom and the drag gesture

jsdom has no pointer-event pipeline that `@dnd-kit`'s sensor can drive, and
`frontend/tests/work/ChaptersPageReorder.test.tsx` already records the resolution: mark the drag gesture
`[manual/live]` and test the **arrow** path, on the premise that both affordances funnel into one
persist call. That premise is only true if the component is built that way — which is why DoD-1 asserts
the **single** call and the shared path, not merely that the order changed.

## Test harness facts

Same as step 010: mock `../../src/api/memos` wholesale, render through `renderWithProviders`, query by
role and accessible name, import every primitive from `"vitest"`, import `ApiError` real from
`../../src/api/client`.

For DoD-5 and DoD-6 the api mock must be controllable — a deferred promise resolved or rejected by the
spec — so the optimistic window and the rollback are both observable. For DoD-2 the mock's resolved
value must differ in order from the local computation, so a page that renders its own optimistic result
instead of the server's fails.
