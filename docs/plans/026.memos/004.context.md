# 004 — step context

Feature-wide facts (the ordinal rules, the wire contract, the status taxonomy) are in `context.md` and
are not repeated here.

## The precedent to copy, in full

`PUT /{book_id}/chapters/order` — `backend/app/routes/chapters.py` plus
`backend/app/services/chapters.py::reorder_chapters`. Copy all of it:

- the route is declared at **line 158**, *before* `@router.get("/{book_id}/chapters/{chapter_id}")` at
  line 184, with a comment stating that route ordering is load-bearing because FastAPI matches in
  declaration order;
- the service loads the current set, builds a `by_id` lookup, and refuses when
  `len(submitted) != len(current)` **or** `len(set(submitted)) != len(submitted)` **or**
  `any(id not in by_id)`, with an `invalid_reorder_set`-style reason → **400** (not 422 — the body is
  structurally valid; it is a business-rule refusal);
- on success it loops `enumerate(submitted, start=1)`, setting `ordinal` and `modified_at` and calling
  the ordinary per-row `db` update;
- **there is deliberately no bulk `db/` writer** — that would move the `1..N` rule out of the service.

## The one difference from the chapters precedent

`services/chapters.py::reorder_chapters` calls `authz.require(access, Capability.set_chapter_order)`,
because chapter order is owner-only (US-033.AC-2).

**Memos must not.** There is no capability and no matrix row for memos; the caller reorders **their
own** list, so membership plus the `access.user_id` scoping is the whole rule (`authorization.md` → the
fourth row-ownership rule). Copying the `authz.require` line would invent an owner-only gate over an
author's private notes.

## Which rows are "the current set"

The caller's **non-archived** memos in this book — the same read the working list uses. Archived memos
are deliberately outside the submitted set:

- they are not in the list the author is dragging, so a client could not name them;
- `domain-book.md` fixes that archiving **leaves a gap and never renumbers**, and that a restore
  **appends last** rather than returning to its old slot. A reorder that renumbered archived rows would
  quietly make those two rules unobservable.

An archived row may therefore end up sharing an ordinal with a live one. That is inert and expected
(`context.md` → decision 2) — do not "repair" it here.

## Why the refusal is one reason, not four

A missing id, an extra id, a duplicate, another author's id and an archived id are all *the submitted
set is not your set*. Keeping them one reason also keeps the existence-hiding property: a caller cannot
probe whether some id exists by watching the refusal change shape.

## Test seeding

Service specs construct a `BookAccess` directly; route specs use the local `_seed_user` / `_seed_book` /
`_auth_header` helpers and a real JWT (see `context.md` → "Testing facts").

For DoD-5 seed at least three memos, archive one **through the `db/` layer or by writing the flag**
(step 005's routes do not exist for this step's tests to depend on), then assert both halves: the
archived id is refused inside a submitted list, and after a successful reorder of the survivors the
archived row's ordinal is unchanged.

For DoD-6 the route-level assertion is that `PUT …/memos/order` does **not** answer the body-update
handler's shape — the cheapest signal is that a well-formed reorder body succeeds while the same path
with a malformed body is not interpreted as a memo id.
