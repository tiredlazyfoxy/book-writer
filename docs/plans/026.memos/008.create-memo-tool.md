# 008 — The `create_memo` tool: registry entry, base set, seeded modes

## Goal

Let the assistant create a memo on the author's direct request — one bound tool in the `"book"` group
that **persists a row**, widened into `BASE_TOOL_NAMES` so mode-less surfaces can call it and seeded
into all five modes so a mode edited down to zero can visibly refuse it.

## Interface intent

**`backend/app/services/memo_tools.py`** (new) — the module defines the callable, its args schema and
its binder; the `ToolDef` itself is constructed in `tools.py`. `backend/app/services/chapter_tools.py`
is the template for all three.

- **An args schema** — a Pydantic model with a single required body string, colocated here beside the
  tool rather than in `models/schemas/`, as the chapter and close tools do.
- **The tool callable** — `async def`, taking the per-turn tool context first and the body, returning
  **a string**: a short confirmation on success, or a **refusal string on failure — never an
  exception**, because a raising tool aborts the whole turn. It creates the memo for
  `(context.book_id, context.access.user_id)` by calling **step 002's create entry point** with the
  context's access, so the append-at-`max + 1` rule and the active default live in exactly one place.
- **A one-line binder** — `functools.partial` over the context, matching `chapter_tools.py`'s
  `bind_<name>` shape.
- **Refusal chain: `access` absent, and that is all.** The module docstring must state **explicitly
  that there is no archived-book link**, unlike the neighbouring `chapter_tools.py` chain — per
  `authorization.md`, memos stay writable on an archived book and the assistant is refused by the same
  rule as the author, which here means not refused at all. A reader copying the neighbouring chain is
  the failure this sentence exists to prevent.
- **It reads no subject.** `book_id` comes from the tool context (which comes from the route) and the
  author from `access.user_id` — **never** from the resolved subject. That is what keeps the cross-book
  rule untouched and what makes widening the base set safe.

**`backend/app/services/tools.py`** — one added `TOOL_REGISTRY` entry: the name `create_memo`, a
description the model reads, the args schema, **group `"book"`** (the existing group — no new group and
no widening of the valid-group set), and the **binder** set with the plain callable left unset.
**`ToolContext` gains no field**: `book_id` and `access` are already on it.

**`backend/app/services/assistant_runtime.py`** — `BASE_TOOL_NAMES` goes from one entry to two:
`web_search` **and** `create_memo`. Nothing else in the module changes — no `ResolvedSubject` member, no
`determine_mode` branch, no change to the three gating cases.

**`backend/app/db/mode_tools.py`** — `DEFAULT_MODE_TOOL_NAMES` gains `create_memo` for **all five**
modes. The seeding function itself is untouched and stays idempotent per mode.

**`backend/app/db/assistant_modes.py`** — the five default system prompts gain the **US-130 guidance**:
the assistant creates a memo **only on the author's direct request, never unasked**. This is
prompt-enforced, not structural, and inherits US-121.AC-3's honest caveat — an administrator who
rewrites a mode prompt can weaken it. `seed_default_modes()`'s check-then-create logic is untouched.

## Definition of done

1. `[test]` (US-129.AC-1) Calling the tool creates a memo for the turn's author in the route's book, and
   it appears in that author's list.
2. `[test]` (US-129.AC-2) The created memo is **active**.
3. `[test]` (US-129.AC-3) It is **at the end of the list**, by the same append rule a manual create uses
   — the tool reaches it through the memo service rather than recomputing an ordinal.
4. `[test]` (US-129.AC-4) The tool reads **no subject**: with no subject resolved, with the memos list as
   the subject, and with an unrelated subject, it creates the memo just the same, and always into the
   book the route named.
5. `[test]` (US-129.AC-5) A mode whose `mode_tool` rows exclude `create_memo` does not get the tool in
   its resolved allowlist — so the request is refused visibly rather than silently succeeding. (Gating,
   not the tool: an allowlist the admin edited down still means what it says.)
6. `[test]` *(architecture — `assistant-runtime.md` → "`BASE_TOOL_NAMES` widens to two entries")*
   `BASE_TOOL_NAMES` holds exactly `web_search` and `create_memo`, so a **mode-less** surface — the
   memos list, Book state, the chapters / variants / chats lists, a `planned` or `closed` chapter, or no
   subject at all — resolves to an allowlist containing `create_memo`.
7. `[test]` *(architecture — the seeding bullet in `assistant-config.md`)* `DEFAULT_MODE_TOOL_NAMES`
   names `create_memo` for all five modes, and seeding remains **idempotent per mode** — a mode that
   already has rows is left entirely untouched, which is exactly why an existing install needs an
   administrator to add it by hand (`context.md` → decision 10).
8. `[test]` (UC-102 / US-129.AC-5 — the visible-refusal path) The tool **never raises**: an absent
   access, a caller who is not a member, and a service-level refusal each come back as a **refusal
   string** the model can read and respond to.
9. `[test]` *(architecture — `authorization.md` → the archived-book carve-out)* The tool **succeeds** on
   a book whose state is `archived` — there is no archived-book link in its refusal chain.
10. `[test]` *(architecture — `quick-reference.md` → `TOOL_REGISTRY`)* The registry entry declares the
    name `create_memo`, group `"book"`, a binder and no plain callable; every registry entry still
    declares a valid group; and **`ToolContext` still has the same field count it had before this
    step** — no seventh (or eighth) field was added.
11. `[test]` (US-130.AC-1) Each of the five seeded mode prompts carries guidance that a memo is created
    **only on the author's direct request**. Enforcement is the prompt's, not the code's — the test
    pins that the guidance ships, not that the model obeys it.
12. `[test]` *(architecture — `assistant-runtime.md` → the frame vocabulary)* The SSE vocabulary is
    unchanged — still seven frames, none widened: `tool_call` / `tool_result` visibility comes free from
    the generic wrapper around every bound tool, and this tool emits nothing itself.
