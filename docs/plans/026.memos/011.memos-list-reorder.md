# 011 — Reorder in the memos list: drag and arrows, one persist path

## Goal

Let the author set their memos' order by dragging a row or nudging it with an arrow control — both
funnelling into **one** persist call that sends the whole id list, applied optimistically and rolled
back to server truth on failure.

## Interface intent

**`MemoOrderList.tsx`** (new) — the drag surface and the arrow controls, wrapping the rows step 010
built. `frontend/src/work/components/chapters/ChapterOrderList.tsx` is the template and should be copied
rather than re-derived.

- A **`DndContext`** with closest-centre collision detection and a drag-end handler, wrapping a
  **`SortableContext`** over the working list's ids with the vertical sorting strategy.
- A **sortable row wrapper** calling `@dnd-kit`'s own `useSortable` hook, **disabled while a reorder is
  in flight**. Calling a library's hook is explicitly **not** a breach of the no-custom-hooks rule,
  which forbids *authoring* hooks.
- **Per-row up/down arrow controls**, disabled at the ends of the list, each carrying an accessible name
  naming the memo it moves.
- The drag-end handler computes the moved list (`arrayMove`) and funnels it into **the same persist
  function the arrow controls use**. One persist path, two affordances.
- The component renders each memo through step 010's row; it owns no memo state of its own.

**`memosListPageState.ts`** — two added effectful functions plus the optimistic slots they need.

- **A persist function** taking the whole ordered id list: it sets an optimistic pending order and a
  reorder status, calls the api **once** with the complete list, **re-seeds from the server's returned
  list** on success, and **discards the pending order on failure** so the view snaps back to server
  truth with an author-facing message.
- **A move-one function** taking a memo id and a direction: it computes the fully swapped id list
  locally and delegates to the persist function above — it never calls the api itself.
- A computed that resolves the displayed working list to the pending order while one is in flight and to
  the server's order otherwise.

**`MemosListPage.tsx`** — render the working list through `MemoOrderList` and pass the two functions
down. The **archived section is not reorderable** and is rendered as it already is.

## Definition of done

1. `[test]` (US-126.AC-2) Using a row's arrow control moves that memo **one position** in that direction
   and persists the **whole** id list in a **single** api call.
2. `[test]` (US-126.AC-2) After a successful reorder the list renders in the server's returned order —
   the page shows server truth, not the local computation.
3. `[test]` (US-126.AC-2) The up arrow is disabled on the first memo and the down arrow on the last, and
   each control carries an accessible name identifying its memo.
4. `[manual/live]` (US-126.AC-1) Dragging a memo to a new position reorders the list. **jsdom cannot
   drive `@dnd-kit`'s pointer sensor** — the `ChaptersPageReorder.test.tsx` precedent — so the gesture
   is verified live; the persistence it funnels into is covered by DoD-1, which both affordances share.
5. `[test]` (US-126.AC-2) The new order is applied **optimistically** — the list reorders before the
   call resolves.
6. `[test]` (UC-105 failure handling — no separate AC) A failed reorder **rolls back** to the server's
   order and surfaces an author-facing message; no partial order survives.
7. `[test]` (US-128.AC-1) The submitted id list contains **only non-archived memos**, and the archived
   section offers **no reorder controls** at all.
8. `[test]` (UC-105 — no separate AC) While a reorder is in flight the row's controls are disabled, so a
   second reorder cannot interleave into an order nobody chose.
