# 009 — step context

Feature-wide facts (the wire contract, the frontend conventions, the subject decision) are in
`context.md` → decisions 11 and 12, and are not repeated here.

## The exact shapes this step extends

- **`navItems.ts`** exports `type WorkPaneTarget = "content" | "chat"` and
  `interface WorkNavItem { path; label; icon; extraActiveSegments?; paneTarget }`, plus
  `WORK_NAV_ITEMS` — currently **seven** entries, **all `paneTarget: "content"`**. `path` is the
  **basename- and book-id-stripped segment with a leading slash**, e.g. `"/state"`, `"/chats"`; so the
  memos entry's path is `"/memos"`. The pure helpers `workNavHref` and `isWorkNavItemActive` need no
  change — an entry with no `extraActiveSegments` is already the common case.
- **`subject.ts`** exports `SubjectKind` (ten members today), `LoadedSubject`,
  `EditableRegion` (`"none" | "whole" | "book-state-notes" | "chapter-sketch" | "chapter-own-prompt" | "chapter-text"`),
  `Editability` (`{ editable: EditableRegion; readOnlyReason: string | null }`), `WriteRegion`,
  `resolveEditability` and `checkWritePermission`. Every **list** kind today returns
  `{ editable: "none", readOnlyReason: "This is a list view and cannot be edited." }` — the memos branch
  is the first list that does not.
- **`routes.tsx`** mounts list pages with no item id **directly**
  (`<Route path="chats" element={<ChatsListPage />} />`); only item routes use a wrapper with
  `key={id}`. Memos needs no wrapper.
- **`api/client.ts`** exports `request<T>(url, opts)` alongside `ApiError`, `authHeaders` and
  `RequestOptions`. Every `api/*.ts` module forwards through it and unwraps `{ items: [...] }`
  envelopes at the call site, because list envelopes are deliberately not modelled in `.d.ts`.

## The placeholder page, stated plainly

`frontend/src/work/pages/MemosListPage.tsx` is created here **only** so `routes.tsx` compiles: an
`observer` component with a heading and a labelled empty state naming step 010 as its owner. That is
the repo's established convention (the navigator was built whole at feature `010` with labelled empty
states naming each section's owning feature), not an improvised stub.

**Do not** build state, api calls, effects or memo rendering into it here. Step 010 replaces the body,
and any work done twice is work the verifier will attribute to the wrong step.

## Gotcha — the two `SubjectKind` lists must stay identical

`frontend/src/types/chats.d.ts` carries a comment saying its `SubjectKind` must stay **structurally
identical** to `src/work/subject.ts`'s. Both get `"memos"` in this step, and DoD-5 pins the pair. The
backend `Literal` in `app/models/schemas/chats.py` is the third copy — **it is step 006's file, not
this step's, and it already carries `memos` by the time this runs**; if it does not, that is a blocker
to surface, not a file to edit from here.

## Gotcha — `memos` changes no routing, deliberately

Adding the kind is **wire honesty**: the memos page registers its subject like every other content-pane
page, so `TurnRequest.subject_kind` carries `memos` rather than `null`. Behaviour is **identical either
way** — nothing keys a mode off `memos`, and the turn lands in tool-gating case 2 regardless. Do not add
a mode mapping, a `ResolvedSubject` member or a `determine_mode` branch on either side of the wire.

## What the editability branch is for, honestly

It is kept for **table completeness, not for symmetry**. `subject.ts` exists so the author and the
assistant are refused by the same rule (US-097.AC-2); memos have no such symmetry to enforce, because
`create_memo` creates a **new** row and never writes into a displayed memo. The branch's value is that
`frontend-workspace.md`'s editability table stays literally the single enforcement point — a subject
missing from it is drift.

## Test harness facts particular to this step

The three existing specs each pin their own contract and all three import from `"vitest"` explicitly
(`globals: false`):

- `frontend/tests/work/navItems.test.ts` looks items up **by their author-facing label**, not by `path`
  — the skeleton does not freeze the exact `path` string form. Add the Memos assertions in that idiom.
- `frontend/tests/work/subject.test.ts` is a pure unit spec over `resolveEditability` /
  `checkWritePermission`.
- `frontend/tests/work/routes.test.tsx` renders through `renderWithProviders` with a `route` option and
  asserts by role and accessible name; routes passed there are **basename-stripped**.

For DoD-8, an api-module spec mocks `../../src/api/client` (not `fetch`) and asserts the url, method and
body each function hands to `request<T>`.
