## Why the version pin is a criterion and not a number in this plan

The planner cannot read `frontend/package.json` and cannot reach the npm registry, and a wrong major
here fails at install time in a way that is expensive to unwind (TipTap 2 and TipTap 3 have different
package names for parts of the ProseMirror bundle, and `@mantine/tiptap` targets one of them per
Mantine major).

So the plan states the **rule** — pin inside `@mantine/tiptap`'s declared peer range for the Mantine
version already in this repo — and DoD-1 makes verifying it the work. `frontend.md` records Mantine
v7.17 as the stack version; confirm against `package.json` rather than against that document, which is
a snapshot.

`tiptap-markdown` is a separate publisher on a separate cadence. It must target the **same** TipTap
major; if no release does, that is a genuine blocker — stop and re-route rather than mixing majors or
hand-rolling a Markdown serializer.

## The prop seam is frozen by the skeleton agent and mocked by three later steps

Steps 006, 007 and 012 render `ChapterPage`, which mounts this component. Their specs **mock this
module** with a trivial stub (`context.md` → "The one testing decision this feature has to make"). That
makes these props a contract, not an implementation detail:

- initial Markdown, read once at mount;
- a change callback receiving Markdown;
- a selection-change callback receiving the selected text;
- an accessible label.

Adding a prop later is cheap; **changing the meaning of one of these four is not** — three specs bind
to them.

## D15 in one sentence, because this is where it bites

The component reads its initial Markdown **once**. The page remounts it (via a key that changes on
every external draft write) when the assistant writes, when undo pops, when a buffer restores, and when
a reconciliation resolves. The component therefore needs **no** prop-watching effect, no `autorun` and
no imperative handle — all three of which `frontend.md` either forbids or reserves for page level.

Do not add a `useEffect` here. Do not accept a ref. Do not expose an imperative `setContent`.

## jsdom and ProseMirror

ProseMirror needs DOM APIs jsdom does not implement — `Range.getClientRects`,
`Element.getBoundingClientRect` returning real geometry, and in some versions `document.elementFromPoint`.
Mounting usually works; **typing and selection do not** reliably.

That is why DoD-2/3/4 are the only `[test]` items and DoD-5/6/7 are `[manual/live]`. If mounting itself
fails under jsdom, the spec may install minimal stubs **at the top of its own file** —
`frontend/tests/support/` and `vitest.config.ts` are in **no** step's source or test list and must not
be touched.

Do not test the emitted Markdown string in jsdom by faking editor internals: that would test the test
(the same reasoning 014 used for `@dnd-kit`'s drag gesture).

## Folder placement

`frontend/src/work/components/chapter/` is a **new** folder. `frontend.md`'s layout puts working-page
components under `src/work/components/<area>/`; `components/shell/` and `components/chat/` are the two
that exist. A third area folder for the chapter surfaces is the pattern, not a new idea.

## Styling

`frontend.md`: *"Styling is Mantine's built-in system plus a single `global.css` and a `theme.ts`. No
Tailwind, no CSS modules, no styled-components."* A vendored stylesheet import from the library that
owns the widget is none of those, and importing it from the component keeps it out of the entry files.
`outcome.md` records the addition so it is sanctioned rather than drift.
