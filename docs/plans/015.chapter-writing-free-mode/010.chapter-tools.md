# 010 — The four chapter tools and the assistant's refusal mirror

## Goal

Add the chapter read path and the three shared-canvas write tools to `TOOL_REGISTRY` — each emitting one
frame, persisting nothing, and refusing with a string the model can read rather than an exception that
would abort the turn.

*This step has no product id: FEAT-013 / UC-054 / UC-055 are parked under "Mapped later" by the
roadmap, so its criteria are self-contained and cite none (`context.md` → "Known product gaps").*

## Interface intent

**`backend/app/services/chapter_tools.py`** (new) — the chapter half of the shared canvas, mirroring
`services/codex_tools.py` file for file. Every tool is **context-bearing**: it needs the book, the
resolved chapter subject, the caller's access and the frame emitter, none of which a plain module
function can know, so each is registered with a **binder** (`ToolBinder`, `tools.py:146`) that builds its
callable from the per-turn `ToolContext` (`tools.py:93-139`).

- **A private refusal mirror**, the chapter counterpart of `codex_tools.py::_refuse_write`. It returns
  **a string the model reads**, or nothing when the write is allowed, and it **never raises** — a
  raising tool aborts the turn. It refuses when: the turn's subject is not a chapter; the chapter is not
  in state `open`; the book is `archived`; or the caller is a co-author in a `proposal`-mode book. The
  last two read straight off **`ToolContext.access`**, which already carries `book_state`,
  `collaboration_mode` and `role` — no new plumbing. These are the same four rules
  `services/chapters.py` enforces for the author's save, spoken in the other vocabulary
  (`frontend-workspace.md` → "Two implementations, two vocabularies, on purpose").
- **A read tool** — returns the chapter's **saved** body text to the model. Subject to the same
  subject-resolution rule as the writes but **not** to the write refusals: a `closed` chapter can be
  read. It states in its description that it returns the saved body, so the model does not present it
  as the author's current draft (`context.md` → D4's accepted limitation).
- **A whole-body write tool** — takes the new body, emits **one** frame with the replace operation.
- **A selection write tool** — takes the replacement text, emits **one** frame with the
  replace-selection operation. Its description tells the model the selection is the author's current
  one, supplied with the turn, and that it must not attempt to describe where the text goes.
- **An append tool** — takes the text to add, emits **one** frame with the append operation.
- All three writes carry the resolved chapter's id and the **`"body"`** `CanvasField` — a chapter's body
  is the same principal text field a codex entry's is, and `CanvasField` was **not** widened
  (`context.md` → D17). **None of them touches the database.** There is no code path from a chat turn to
  the `chapters`, `chapter_changes` or `chapter_text_revisions` tables, and that absence is the
  guarantee — not a check (`assistant-runtime.md`'s structural-property argument for the codex tools,
  which holds here unchanged).
- Each tool has a Pydantic argument schema — one text field each — per the typing rule.

**`backend/app/services/tools.py`** — four new `ToolDef` entries in `TOOL_REGISTRY`, with stable string
names, descriptions written for the model, their argument schemas and their binders. Nothing else in
this module changes: no existing entry, no builder, no registry ordering rule, and **not `ToolContext`**
(step 009 widened it).

**No `mode_tool` row is seeded** (`context.md` → D4). An admin selects these tools for the
`write-chapter` mode in `012.assistant-config-editor`'s mode editor; a mode with zero rows grants none,
which is the settled rule. **The `write-chapter` `AssistantMode` row itself already exists** — see
`context.md` → "Mode seeding"; nothing here seeds a mode either.

## Definition of done

1. `[test]` All four tools are in `TOOL_REGISTRY` with distinct, stable names that collide with no
   existing entry, each carrying exactly one of a callable or a binder, and each with a Pydantic
   argument schema.
2. `[test]` The read tool returns the chapter's **saved** body text for a resolved chapter subject, in
   every chapter state including `closed`.
3. `[test]` Each of the three write tools emits **exactly one** canvas frame, carrying the chapter's id,
   the `"body"` field, the text it was given, and its own operation — replace, replace-selection and
   append respectively.
4. `[test]` **No write tool touches the database.** After every one of them runs, the chapter's stored
   body, its version and its modified timestamp are unchanged, and no `ChapterChange` and no
   `ChapterTextRevision` row exists.
5. `[test]` A write tool invoked when the turn has **no chapter subject** returns a refusal **string**,
   emits no frame, and raises nothing.
6. `[test]` A write tool invoked on a chapter that is `planned`, `closing` or `closed` returns a refusal
   string naming the chapter's state, emits no frame, and raises nothing — the assistant is refused by
   the same rule as the author.
7. `[test]` A write tool invoked on an **archived** book returns a refusal string, emits no frame, and
   raises nothing — **D10**, in the assistant's vocabulary, read off `ToolContext.access.book_state`.
8. `[test]` A write tool invoked by a **co-author in a proposal-mode book** returns a refusal string
   naming FEAT-010 as unbuilt, emits no frame, and raises nothing; the same call as the **owner**
   succeeds — **D11**, in the assistant's vocabulary.
9. `[test]` The read tool is refused on a chapter in **another book**, by subject resolution rather than
   by a check inside the tool.
10. `[test]` A tool offered with **no** tool context is skipped and logged rather than raising — the
    existing bound-tool rule, exercised for these four.
11. `[test]` No refusal path anywhere in this module raises: every failure and every refusal comes back
    as a short string.
12. `[test]` With **no `mode_tool` rows** for the `write-chapter` mode, a turn whose subject is the
    book's `open` chapter is offered **none** of these four tools — registration alone grants nothing.
    This is the shipped-unreachable state `context.md` → D4 describes, asserted rather than assumed.
13. `[manual/live]` **The admin-selects-then-the-tool-fires path, end to end.** Starting from a fresh
    install: the chapter tools are invisible to a chapter turn; an admin selects them for the
    `write-chapter` mode in the Assistant Modes editor; a turn taken while the book's `open` chapter is
    the content-pane subject then offers exactly those four plus the mode's other selections; and a
    model call to each of the three writes lands its frame. Taking a chapter out of `open` removes them
    again.
