# 004 — The body DTOs and the five write functions in `api/chapters.ts`

## Goal

Extend the shared chapter DTOs with the body shapes and `api/chapters.ts` with the five functions the
working page's write surfaces call.

## Source files

```
frontend/src/types/chapters.d.ts
frontend/src/api/chapters.ts
```

## Test files

```
frontend/tests/user/chaptersWriteApi.test.ts
```

## Interface intent

**`frontend/src/types/chapters.d.ts`** — two new hand-written DTOs beside 014's, matching
`context.md` → "The wire contract" exactly. Wire-exact `snake_case`, ids typed `string`, no `any`:

- the **chapter text response** — the chapter id as a string, the chapter state (reusing the wire-level
  state union 014 declares in this same file), the body text, the **version as a `number`**, and the
  modified timestamp using `common.d.ts`'s existing ISO alias;
- the **body update request** — the whole text and the expected version as a `number`.

**`version` is a `number`, not a `string`.** The string-id rule exists because snowflakes exceed
JavaScript's safe-integer range; a monotonically incremented counter does not. Do not widen it to
`string` "for consistency" — it would then have to be parsed at every comparison, and the buffer's
`BufferBaseVersion` already accepts `number` for exactly this field.

014's DTOs are not touched.

**`frontend/src/api/chapters.ts`** — five new functions on 014's module, each taking the book id first
and `signal?: AbortSignal` last, each going through the shared `request<T>` wrapper:

- **read the body** — book id and chapter id, returns the body response;
- **save the body** — book id, chapter id and the body update request, returns the body response;
- **open**, **close** and **reopen** — book id and chapter id, each returning 014's chapter response.
  All three issue a `POST` with **no request body**.

014's eight functions are unchanged, and **the list function still returns the whole envelope** — the
departure from `api/codex.ts` that 014 pinned survives this step.

No error handling, no retry, no refusal parsing lives here: `request<T>` normalizes a non-2xx into an
`ApiError`, and the pages read `status` and the server's reason text off it.

## Definition of done

1. `[test]` Each of the five functions calls the exact path and HTTP method fixed by `context.md` →
   "Endpoints added", with the book id and chapter id interpolated into the right segments.
2. `[test]` Each of the five forwards the abort signal it is given.
3. `[test]` The body save sends the text and the expected version in the request body, and returns the
   response shape unmodified — the api layer neither unwraps nor reshapes it.
4. `[test]` The three transition functions send **no request body**.
5. `[test]` A non-2xx from any of the five surfaces as an `ApiError` carrying the server's status, so a
   caller can distinguish `409` from `403` — the two the pages branch on.
6. `[test]` 014's existing chapter functions are unchanged, and the list function still returns the
   envelope including its reorder hint rather than a bare array.
7. `[manual/live]` `cd frontend && npm run build` and `cd frontend && npm run test:types` both pass —
   no `any` reaches the new DTOs or the new functions.
