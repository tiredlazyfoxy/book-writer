## `determine_mode` has no chapter branch — this step writes one

Confirmed, in full:

```python
if subject.entry is None:
    return None
return _mode_for_codex_kind(subject.entry.kind)
```

with `_CODEX_KIND_MODES` mapping only `character` / `location` / `fact`. The function's docstring says
outright that `write-chapter` / `close-chapter` "belong to `015` / `016`".

**"Already correct, no change" is not a possible outcome for DoD-6 through DoD-9.** Each of them
asserts behaviour that does not exist before this step.

Note the shape of the existing guard: it keys off `subject.entry is None`. A chapter subject will have
`entry` null and the new chapter member set, so the early return has to become a check that the subject
resolved to **nothing at all**, not to "no codex entry". Getting that wrong is the one way to make the
chapter branch unreachable while every codex test still passes.

## Why the operation field and not a new event name or an encoded field name

Three options were on the table:

1. **a new SSE event per operation** — the vocabulary is deliberately narrow and already documented as
   "a floor, not the design"; three events for one concept would make the frontend's dispatcher branch
   on names instead of on data;
2. **encoding the operation into `field`** (`"text.append"`) — rejected for the reason
   `domain-chapter.md` gives for storing placement as a discriminator plus columns: *"a discriminator
   keeps the 'which columns are meaningful' question answerable without parsing"*;
3. **a defaulted operation field** — chosen. `assistant-runtime.md` notes the frame needed **no route
   change** to be added at all, and a defaulted field needs none either.

The default is load-bearing: it is what lets `context.md` → D2's "`CodexEntryPage` is not reworked"
survive contact with a widened protocol, on both sides of the wire.

## Selection is text, and only text — and it is a flat field

`context.md` → D5. Do not add offsets, line numbers, a range object or an anchor id, and do not reach
for `ChapterChange.line_from` / `line_to` — those exist for a stored change's placement, not for a live
caret, and snapping character offsets onto line numbers is exactly the lossy step the design refuses.

**`TurnRequest` has no subject object** — `prompt`, `subject_kind`, `subject_id`, `codex_kind` are four
flat optional fields (`chats.py:187-216`). The selection is a **fifth flat field**, not a member of
anything. (The frontend has a `TurnSubject` helper interface at `types/chats.d.ts:144-148` with **no
backend counterpart**; it is a client-side convenience and gains nothing — that is step 012's note.)

The model uses the selection text as **content to rewrite**; the *placement* of the rewrite is resolved
entirely on the client, against the selection the editor still holds (step 012).

## `ToolContext.access` is already there, and it is what makes step 010 cheap

`ToolContext` is a frozen dataclass carrying `book_id: int`, **`access: authz.BookAccess | None`**,
`subject: ResolvedSubject | None`, `emit_frame: FrameEmitter | None`. The `access` field already gives a
bound tool the caller's role, the book's state and its collaboration mode — so step 010's refusal mirror
for D10 and D11 needs **no new plumbing**, only field reads. Do not add role, mode or book-state fields
to the context.

## The cross-book rule already has a precedent

`assistant-runtime.md`: *"A `subject_id` naming an entry in another book resolves to no subject, not to
that entry's mode. Mode determination reads a row, so it would otherwise be a cross-book read dressed
as a routing hint. No subject means no mode, which means the base tool set — a safe, non-leaking
fallback."*

DoD-9 is that rule applied to chapters. Copy the codex implementation's shape rather than inventing a
second cross-book check.

**`planned` and `closed` chapters get no mode**, deliberately: FEAT-020's five modes name five
activities, and neither of those is one of them. The consequence is `BASE_TOOL_NAMES` — **exactly
`("web_search",)`** (`assistant_runtime.py:62`) — not an empty allowlist. `assistant-runtime.md` calls
that distinction "the load-bearing part" of the three-case gating, because a null mode meaning "no
tools" would silently strip web search from every non-mode subject. DoD-8 asserts the concrete value,
not the concept.

## DoD-12 is a seeding *assertion*, not seeding work

`context.md` → "Mode seeding" establishes that all five `AssistantMode` rows are seeded by
`seed_default_modes()`, wired into both `services/setup.py::create_database` and `import_database`, and
idempotent by `key`. **This step seeds nothing and must not add a seed call.**

DoD-12 exists only because the failure it guards against is silent: `determine_mode` returning
`"write-chapter"` with no such row would give an empty mode prompt and an empty `mode_tool` lookup
(`db/mode_tools.py:36-43`) and raise nothing. One assertion on a freshly initialised database converts
the documented claim into a checked one.
