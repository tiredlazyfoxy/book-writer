# 012 — The chapter page applies canvas frames, pushes undo, and sends its selection

## Goal

Close the loop: the chapter page registers itself as a writable canvas target, applies the assistant's
three operations to its draft after snapshotting for undo, offers an undo control, and the chat pane
carries the author's current selection on every turn.

*This step has no product id (FEAT-013 / UC-055, parked); its criteria are self-contained.*

## Interface intent

**`frontend/src/work/pages/chapterPageState.ts`**

- **A bound apply-draft entry point**, following `codexEntryPageState.ts`'s — a method bound to the
  instance and **excluded from `makeAutoObservable`** — taking the field, the text and the frame's
  operation. It:
  1. **pushes the current body draft onto the undo stack before applying anything**
     (`context.md` → D6) — the snapshot is of what the author is about to lose;
  2. applies the operation to the body draft: replace the whole draft; append to its end; or replace the
     currently-registered selection's text within it;
  3. routes the result through step 006's single draft-edit path, so the restore buffer is written
     exactly as a keystroke would write it;
  4. **bumps the editor generation counter**, so the editor remounts on the new draft
     (`context.md` → D15).
- **Selection state** — the author's current selection, updated from the editor's selection callback and
  pushed into the module-level selection registry. It is never persisted and never saved
  (`context.md` → D5).
- **A replace-selection frame arriving with no active selection is not applied.** It is reported to the
  author as an unapplied assistant write and nothing is changed — writing at a location nobody chose is
  the failure `domain-chapter.md` refuses. No fallback to append, ever.
- **An undo entry point** — pops the most recent snapshot for this chapter, sets it as the body draft
  through the same draft-edit path, and bumps the generation counter. It pushes nothing.

**`frontend/src/work/pages/ChapterPage.tsx`**

- The mount effect **registers the page as the content-pane subject with its apply-draft callback** and
  unregisters on unmount, extending the registration 014 already puts here — a chapter item is now a
  **writable** canvas target, where 014 registered it as a subject only.
- The editor's selection callback feeds the page's selection state.
- An **undo control** beside the body editor, enabled only when the stack for this chapter has depth,
  labelled for what it undoes (the assistant's last write), and a short surface for an unapplied
  selection write.

**`frontend/src/types/chats.d.ts`** — the **turn-request** twin only. `TurnRequest` (`:159-164`) gains
the optional selection text, mirroring the backend field step 009 adds at `chats.py:187-216`. It is a
**flat field** beside `subject_kind` / `subject_id` / `codex_kind`, matching the backend's flat shape.

**The frontend-only `TurnSubject` helper interface (`:144-148`) gains nothing** — it has no backend
counterpart, and the selection is not part of the subject. The `CanvasFrame` twin at `:191-196` is step
011's and is not touched here.

**`frontend/src/api/chats.ts`** — the turn-request body it builds carries the new field. No other
change: the SSE reader, the frame handlers and the streaming conventions are untouched.

**`frontend/src/work/components/chat/chatPaneState.ts`** — the send and retry paths read the selection
from the module registry **at send time**, exactly as they already read the subject, and put it on the
turn request. **The pane gains no selection field and no observer relationship to the content pane** —
`frontend-work-drafts.md`'s rule that "the panes stay independent because nothing links them but a
function call" holds unchanged.

## Definition of done

1. `[test]` The page registers itself as the content-pane subject **with an apply-draft callback** on
   mount and unregisters on unmount; a chapter that is not `open` registers a subject but offers no
   writable target.
2. `[test]` A replace frame sets the whole body draft; an append frame adds to its end; a
   replace-selection frame replaces exactly the currently-selected text within it.
3. `[test]` Every applied frame **pushes the pre-write draft onto the undo stack first**, and the undo
   control then restores exactly that text.
4. `[test]` An applied frame writes the restore buffer the same way a keystroke does, and **reaches the
   server not at all** — no save call results from an assistant write.
5. `[test]` The editor remounts on an applied frame and on an undo, and does not remount on a keystroke
   — **D15**.
6. `[test]` A replace-selection frame arriving with **no active selection** changes nothing and is
   reported to the author; it is never appended and never applied at position zero.
7. `[test]` The undo control is unavailable when the stack is empty, and after 20 assistant writes only
   the most recent 20 states are reachable.
8. `[test]` Moving the selection in the editor updates the module-level selection registry, and leaving
   the page clears it.
9. `[test]` A turn sent while a chapter is in view carries the current selection text as a **flat field**
   on the request, carries none when nothing is selected, and the pane holds no selection field of its
   own.
10. `[test]` The selection is never saved: applying frames and moving selections produce no write call,
    and a subsequent body save sends only the text and the version.
11. `[manual/live]` With the chapter tools selected for the `write-chapter` mode, a live turn that calls
    each of the three write tools lands its text in the editor without touching the server, the author
    saves once, and the saved body is what the editor showed.
12. `[manual/live]` `cd frontend && npm run build`, `cd frontend && npm test` and
    `cd frontend && npm run test:types` all pass.
