# 004 — step context

Feature-wide facts (the wire contract, the endpoint list, the `api/` and `types/` conventions, the
frontend test harness, the build gates) are in `context.md` and are not repeated here.

## Both files are 014's and already exist by the time this step runs

014 step 005 creates `frontend/src/types/chapters.d.ts` (seven DTOs plus a wire-level chapter-state
union) and `frontend/src/api/chapters.ts` (eight functions: list, read one, create, update sketch,
remove, reorder, read own chapter prompt, update own chapter prompt).

**Extend both. Rename nothing, re-export nothing, and do not touch the eight existing functions.**
DoD-6 exists to pin that, because the list function's unwrapped-envelope behaviour is exactly the kind
of thing a tidy-up pass removes.

## The state union already exists here

014 declares the wire-level chapter-state union in this file and notes that it must not collide with
the identically-valued `ChapterState` in `frontend/src/work/subject.ts`. **Reuse whatever 014 named
it**; do not declare a second union for the body response's `state` field, and do not import
`work/subject.ts` from `src/types/` — that would couple the wire to the working page's pane model,
which 014 explicitly refused.

## `api/books.ts` and `api/codex.ts` are the naming references

- `api/codex.ts` is the book-nested-resource precedent: book id first, `signal?` trailing.
- 014 named its prompt pair after `api/books.ts`'s `getOwnSystemPrompt` / `updateOwnSystemPrompt`.

Name the five here for what they act on — the chapter's **text**, and the chapter's **state** — not for
the verb alone, so `open` does not read as opening a page.

## `request<T>` and the `204` question

None of the five endpoints answers `204`: the body pair returns the body response and the three
transitions return the chapter response. So no empty-body tolerance is needed here (014's remove
function is the one that needs it, and it already has it).

## Testing

`frontend/tests/user/chaptersWriteApi.test.ts` is created from scratch and sits beside 014's
`frontend/tests/user/chaptersApi.test.ts`. The location follows 014's — the api module is shared at
`src/` root, and its spec lives under `tests/user/` — even though this feature's callers are all in the
`work` entry. Consistency with the sibling spec beats topical placement for a file that tests a shared
module.

This spec tests the **api module itself**, so it mocks the shared `request<T>` wrapper in
`../../src/api/client` rather than the chapters module, and asserts the path, the method, the body and
the forwarded signal. `ApiError` is imported real from the same module for DoD-5.

`vitest.config.ts` has `globals: false`, so import `describe` / `it` / `expect` / `vi` from `"vitest"`.
