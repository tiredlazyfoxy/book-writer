# 012 — step context

Feature-wide facts (D5, D6, D15, D17, D18, the harvested declaration-site table, the module-tier facts,
the mock-the-editor testing decision, the build gates) are in `context.md` and are not repeated here.

## The turn request is four flat fields, and the selection is a fifth

Confirmed on both sides:

- backend `TurnRequest` (`backend/app/models/schemas/chats.py:187-216`) — `prompt`, `subject_kind`,
  `subject_id`, `codex_kind`. **There is no subject object.**
- frontend twin (`frontend/src/types/chats.d.ts:159-164`) — the same four.
- frontend-only **`TurnSubject`** helper interface (`frontend/src/types/chats.d.ts:144-148`) — **no
  backend counterpart.** It is a client-side convenience for assembling the three subject fields.

**The selection goes on `TurnRequest` as a flat field. It does NOT go on `TurnSubject`.** A selection is
not part of the subject's identity — the same chapter can be in view with any selection or none — and
putting it there would give the client a shape the wire does not have. DoD-9 asserts the flat placement.

`frontend/src/types/chats.d.ts` is also in **step 011's** source list, for the `CanvasFrame` twin at
`:191-196`. The two steps run in sequence and touch different declarations; `CanvasField` (`:172`) is
touched by neither.

## `codexEntryPageState.ts`'s applier is the shape to copy

Harvested: *"a bound `applyDraft` excluded from `makeAutoObservable`"*. The exclusion matters — MobX
would otherwise try to make a bound method observable, and the registry holds the function itself across
the module boundary.

013's step 012 described its purpose exactly as this step needs it: *"a method that sets one field's
draft text from an external source and runs the same dirty/buffer path a keystroke does. It exists here
so the assistant's canvas draft can be handed to the page without the page knowing where it came from."*

The chapter's version differs in one way: it takes an **operation** as well, and two of the three
operations are relative to the draft it already holds.

## The apply order is not arbitrary

Snapshot **first**, then apply, then route through the draft-edit path, then bump the generation
counter. Any other order loses something:

- applying before snapshotting stores the post-write text and makes undo a no-op;
- bypassing the draft-edit path skips the restore-buffer write, so an assistant draft would be lost on a
  reload — precisely what `frontend-work-drafts.md` calls "a writer with no base version" and expects to
  land in the buffer;
- bumping the counter before applying remounts the editor on the old draft.

## Why a selection frame with no selection is refused rather than placed

`domain-chapter.md`, on stale changes: *"Guessing where a stale change now belongs would write text into
a location nobody chose, and the failure would be silent; a refusal is loud."* The same argument, one
layer up. Appending instead would be a silent wrong placement in the author's own document.

This is a **page-level** refusal, not a tool-level one: at tool-call time the selection may have existed
and the author may have cleared it while the model was writing. The server cannot know that, which is
why the check lives here.

## The chat pane reads the selection at send time and holds none

`frontend-work-drafts.md`: *"`ChatPaneState` gained no subject field. It reads the registry **at send
time**, so the turn always carries whatever is open at the moment the author sends, and no observer
relationship exists between the two panes. The panes stay independent (UC-083) because nothing links
them but a function call."*

Copy that for the selection, in the same call site that already reads the subject. **Do not add a
selection field to `ChatPaneState`**, do not make the chat pane an observer of the content page, and do
not pass the selection down through the shell. DoD-9 pins it.

`api/chats.ts` gained the `canvas` frame in feature 013 **without opening `sse.ts` at all**, because the
reader has a generic event branch; this step likewise touches neither `sse.ts` nor the frame handlers —
only the request body's shape.

## The undo control's label

It undoes **the assistant's last write**, not "the last change" — the author's own typing is undone
inside the editor by ProseMirror's history (`context.md` → D6). Labelling it generically would promise
something it does not do, and the author would find the two undo affordances inconsistent.

## What this step does not touch

`frontend/src/work/contentSubject.ts`, `subject.ts`, `chapterUndo.ts` and `restoreBuffer.ts` are all
**called** here and are in no source list for this step — step 011 owns the first three, and the buffer
is owned by nobody in this feature. `CodexEntryPage.tsx` and `codexEntryPageState.ts` are untouched
across the whole feature.

## Testing

`frontend/tests/work/ChapterPageCanvas.test.tsx` is created from scratch. Mocks, as in steps 006–008:
the whole `api/chapters` module and the `ChapterBodyEditor` component. The stub editor must expose a way
to drive the **selection** callback as well as the change callback — DoD-2, DoD-6 and DoD-8 all need it.

`contentSubject.ts`, `chapterUndo.ts` and `restoreBuffer.ts` are used **real**, not mocked: the frames
are delivered by calling the real dispatcher, which is what makes DoD-1's registration assertion
meaningful. Clear `localStorage` and the undo stacks between tests.

DoD-9 needs the chat pane's send path exercised; mock `api/chats.ts`'s stream function and assert the
request body it was handed — specifically that the selection is a **top-level** property of the request,
not nested inside a subject object. Do not open a real stream and do not use `support/sseFixture.ts` for
this — the assertion is about the request, not the response.

DoD-11 is `[manual/live]` because it needs a real model calling real tools **and** an admin selection of
those tools for the `write-chapter` mode (step 010's DoD-13 covers the selection half); there is no
automated version of it that would not be asserting against a fixture of itself.
