# 008 — Open, close and reopen on the chapter page

## Goal

Put the three state transitions on the chapter item page, gated on the chapter's own state, with the
server's refusal surfaced where the client cannot predict it.

## Source files

```
frontend/src/work/pages/chapterPageState.ts
frontend/src/work/pages/ChapterPage.tsx
```

## Test files

```
frontend/tests/work/ChapterPageStateControls.test.tsx
```

## Interface intent

**`frontend/src/work/pages/chapterPageState.ts`** — transition state and effects.

- **Transition status and a server-error holder**, separate from the body's and the sketch's. A
  transition that is refused stores the server's message; it never clears the body draft.
- **Pure `get` computeds** for which single transition is offered, derived from the **loaded chapter's
  state alone** (`context.md` → **D14**): `planned` → open; `open` → close; `closed` → reopen;
  `closing` → none, with a stated reason naming the close gate as not yet built.
- **Three external effect functions** `(state, bookId, chapterId, signal?)` using `runInAction`, one per
  transition. On success each **re-seeds the chapter trio and the body trio from the server**, so the
  page's editability, its editor mount and its read-only branch all follow the new state without a
  navigation. On an `ApiError` each stores the server's message and changes nothing.

**`frontend/src/work/pages/ChapterPage.tsx`** — one transition control, rendered beside the chapter's
state, with an accessible name naming the action and the chapter, plus a refusal surface beside it.

**The control is offered to every member**, gated on chapter state only. A non-owner's attempt is
refused `403` by the server and the message is surfaced — `context.md` → **D14** carries the reasoning
and the accepted cost. Do not manufacture a caller-role signal, do not fetch the chapter list for its
reorder hint, and do not add a caller-relative field to any DTO.

No confirmation dialog. Closing a chapter is reversible by reopening it, and 016 is what adds a gate.

## Definition of done

1. `[test]` On a **`planned`** chapter the page offers exactly one transition control — open — and
   using it calls the open function and then shows the chapter as `open`, with the body editor now
   mounted — **US-036.AC-1**, **UC-035**.
2. `[test]` On an **`open`** chapter the only control offered is close; using it calls the close
   function and the page then shows the chapter as **`closed`** with the body read-only and no save
   control — **US-038.AC-1**.
3. `[test]` On a **`closed`** chapter the only control offered is reopen; using it calls the reopen
   function and the page then shows the chapter as `open` — **US-039.AC-1**, **UC-037**.
4. `[test]` On a chapter in **`closing`** no transition control is offered and a stated reason is shown
   — the close gate is `016`'s.
5. `[test]` A `403` from any transition — a co-author's attempt, or an archived book — surfaces the
   server's message and leaves the chapter's state on screen unchanged — **US-036.AC-2**,
   **US-038.AC-2**, **D10**.
6. `[test]` A `409` from open or reopen — another chapter already holds the slot — surfaces the
   server's message and leaves both this chapter's state and the body region unchanged —
   **US-037.AC-2**, **US-039.AC-2**, **US-038.AC-4**.
7. `[test]` A successful transition re-seeds the chapter **and the body** from the server, so the body
   region's editability follows without a page navigation or a manual reload.
8. `[test]` A refused transition never clears or alters the body draft, and never clears the restore
   buffer.
9. `[test]` Each control carries an accessible name naming both the action and the chapter, so it is
   reachable by role and label.
10. `[manual/live]` `cd frontend && npm run build`, `cd frontend && npm test` and
    `cd frontend && npm run test:types` all pass.

## Dependencies

- **004** — the three transition functions.
- **006** — the body trio and the editability the transitions have to move.
