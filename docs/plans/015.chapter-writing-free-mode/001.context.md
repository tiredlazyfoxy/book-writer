# 001 — step context

Feature-wide facts (D1, D7, D9, D10, D11, D13, the wire contract, the status taxonomy, the layer rules,
the backend test harness, the build gates) are in `context.md` and are not repeated here.

## What this step is extending, and what it must not disturb

014's `services/chapters.py` ships `list_chapters`, `get_chapter`, `add_chapter`, `update_sketch`,
`remove_chapter` and `reorder_chapters`, plus a **private response mapper** and a **private chapter
resolver** (given the access context and a chapter id: load the row, raise not-found when missing or
when `chapter.book_id != access.book_id`).

**Reuse both. Do not write a second resolver and do not write a second `ChapterResponse` mapper.** The
body response needs its own mapper because it is a different DTO, not because the existing one is
insufficient.

014's reason enum has exactly three members (not-found, not-planned, invalid-order-set). This step
appends four; step 002 appends two more. **Do not renumber, rename or reorder the existing three** —
`routes/chapters.py`'s status map keys off them.

## `db/chapter_changes.py` and `db/chapter_text_revisions.py` already exist and need nothing

Both ship `create`, `get_by_id`, `list_by_chapter` (harvested). This step calls `create` on each and
adds **no** function to either module. `db/chapters.py::update` is 014 step 001's and is called, not
written.

Every `db/` function opens its own session, so the three writes are three commits. That is the accepted
shape (`context.md` → D7) — do not try to thread a session through, and do not add a
`db/chapter_writes.py`.

## The model columns this step fills

Harvested, and none of them are nullable-with-a-default in the way a coder might assume:

- **`ChapterChange`** — `id` (snowflake default factory), `chapter_id`, `author_id`, `placement_kind`
  (`append` / `range`), `line_from` / `line_to` (nullable ints, **set only for `range`**),
  `base_version`, `text`, `status` (`pending` / `applied` / `rejected`), `applied_at`, `applied_by`,
  `created_at`.
- **`ChapterTextRevision`** — `id`, `chapter_id`, `applied_change_id` (**non-null FK** — this is what
  forces the change to be written first), `text_before`, `applied_by` (**non-null**), `applied_at`.
- **`Chapter`** — `version: int = 1` at the model default; `text` is required. 014's `add_chapter`
  initialises `text` to `""`, so a freshly created chapter's loaded body is the empty string and the
  first save always takes D9's append branch.

`PlacementKind` and `ChangeStatus` are declared in `backend/app/models/chapter_change.py`;
`ChapterState` in `backend/app/models/chapter.py`. Import the enums, never their string values.

## Line counting

`line_to` is `len(loaded_text.splitlines())`. `splitlines()` and not `count("\n") + 1`: a body ending
in a newline would otherwise report a phantom trailing line, and `018` will diff against these bounds.

The `range` branch is unreachable when the loaded body is `""` (every string starts with `""`), so the
count is always at least 1. **Do not add a clamp** — a clamp would hide a genuine bug if the
starts-with rule were ever changed.

## Guard order, and why it is not observable

`context.md` fixes: `authz.require` → archived guard → mode guard → resolve → state → version.

A reader on an archived book gets the *authorization* refusal rather than the *archived* one. Both are
`403`, so the status is identical; only the message differs, and telling a reader they lack the
capability is the more accurate of the two. Keeping `require` first is what keeps every guarded service
function in this codebase shaped alike, and it is what stops a `404`/`403` from being distinguishable
by which check ran first (014's step-002 reasoning, which still binds).

The **mode guard exempts the owner.** `services/codex.py::_require_writable_mode` is the shape to copy,
including the message naming FEAT-010 as unbuilt — the refusal text is what the frontend surfaces
verbatim (`CodexEntryPage`'s `serverRefusalText` reads `details.detail.message`).

## The stale check compares an int, not a timestamp

Codex compares `modified_at`; chapters compare `Chapter.version`, an int. Do not copy codex's
timestamp comparison or its tolerance handling — an int equality check is the whole rule
(`domain-chapter.md` → "Concurrency", rule 1: "`Chapter.version` is bumped on every applied change. It
is the single authority on 'has this body moved'").

## Testing

`backend/tests/services/test_chapter_text.py` is created from scratch. Construct `BookAccess` instances
directly — it is a frozen dataclass with `book_id`, `user_id`, `role`, `book_state`, `visibility`,
`collaboration_mode`. Seed users, books, memberships and chapters through the sibling `db/` modules with
the `db` fixture. No route, no HTTP client, no JWT at this layer — those are step 003's.

DoD-9 needs chapters in `planned`, `closing` and `closed`; **write the state directly through
`db/chapters.py`**. This step ships no transition (that is 002), and `closing` can only ever be reached
this way in this feature (`context.md` → D8).

DoD-6 and DoD-7 need the change and revision **rows**, so read them back through
`db/chapter_changes.list_by_chapter` and `db/chapter_text_revisions.list_by_chapter`.

DoD-14 asserts against `_CAPABILITY_MATRIX` directly. The harvest recorded 014's four additions as
planned but not their final names; bind to whatever 014 shipped and assert only that **no existing
row's role set changed**, rather than enumerating the whole matrix.
