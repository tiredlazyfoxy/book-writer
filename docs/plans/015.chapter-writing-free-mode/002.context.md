# 002 — step context

Feature-wide facts (D8, D10, the close seam, the status taxonomy, the layer rules, the test harness) are
in `context.md` and are not repeated here.

## The one-open-chapter guard reads two states, and that is the whole of 016's foothold

`domain-chapter.md`: *"At most one `open` chapter per book (US-037). **`closing` still holds that
slot** — the chapter has not been released, it is waiting on the owner."* And CF1: *"A reopen (UC-037)
is refused if any chapter in the book is `open` or `closing`."*

Product's UC-035 exception flow says the same for **open**, by symmetry with UC-037 (round 7, divergence
4). So both transitions run the same guard. Writing the guard once and calling it from both is what
makes DoD-3/4 and DoD-12/13 assert the same rule rather than two drifting copies.

This feature never produces a `closing` chapter, so the `closing` half of the guard is unreachable in
production today and is reachable only from a seeded row. **That is not a reason to leave it out** —
016 makes it live, and a guard retro-fitted after 016 ships would be a bug that only shows up on a
half-closed chapter.

## The book's chapters come from `db/chapters.list_by_book`

Harvested and already exists. The guard loads the book's chapters and inspects their states; it does
not need a dedicated "is anything open" `db/` query, and adding one would put a domain rule in `db/`.

The guard must **exclude the chapter being acted on**. For `open` this is moot (the chapter is
`planned`), but for `reopen` it is not: the chapter itself is `closed`, so it never matches — still,
excluding it explicitly keeps the guard honest if 016 ever calls it from a `closing` chapter's approve
path.

## Why close writes `closed` and not `closing`

`domain-chapter.md` states it directly: *"The close gate is a **Stage-4 behaviour** (Stage 2 ships an
ungated close, per the roadmap's explicit close-gate seam), but the `closing` value and the status
columns below **land at Stage 2**."* The value exists in the enum and in the column; nothing in this
feature writes it.

`brief.md`'s only open question for the planner is this seam. It is answered in `context.md` → "The
close seam", including exactly what 016 changes. **Do not add a comment, a flag, a parameter or a
config switch anticipating 016** — the seam is a destination constant in one function, and 016 changes
it in one place.

**US-038.AC-3 is cited by no DoD item in this feature.** If a test wants to assert something about
`closing`, the only sanctioned use is DoD-4 and DoD-13's seeded-row case, which are US-038.AC-4.

## A reopen writes no history

`domain-chapter.md`: *"Editing after a **reopen** is a *fix*, and produces variant history — see
`ChapterTextRevision`."* The history comes from the **edit**, which is step 001's ordinary save path —
not from the reopen itself. DoD-17 pins this so nobody adds a "reopened" marker row that `018` would
then have to interpret.

## Testing

`backend/tests/services/test_chapter_states.py` is created from scratch, beside step 001's
`test_chapter_text.py`. The two share no fixtures — the per-file helper convention holds
(`context.md` → "Testing facts").

DoD-5 ("across any sequence") is a sequence test, not a property test: open A, close A, open B, close B,
reopen A, and assert the invariant after each call. There is no hypothesis/property-testing dependency
in this project and none is added.

DoD-4, DoD-13 and DoD-9's `closing` case all need a chapter seeded into `closing` through
`db/chapters.py` with the `db` fixture, before the transition is exercised.

DoD-17 reads the chapter row back and compares every other column, and reads
`db/chapter_changes.list_by_chapter` / `db/chapter_text_revisions.list_by_chapter` to assert both are
empty.
