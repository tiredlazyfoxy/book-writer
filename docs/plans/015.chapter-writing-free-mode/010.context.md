# 010 — step context

Feature-wide facts (D4, D5, D10, D11, D17, the harvested declaration-site table, "Mode seeding", the

## `services/codex_tools.py` is the file to mirror, and it is not edited here

Harvested: it defines the codex tools and `_refuse_write(context, field) -> str | None`, which returns
**a tool string the model reads**, never raises, *"because a raising tool aborts the turn"*. Its single
`canvas` emission is at `codex_tools.py:689-706`.

`chapter_tools.py` is its sibling, not its extension. **Do not import from it, do not generalise it into
a shared base, and do not edit it** — no step of this feature edits that file at all.

Two files with parallel structure is the right shape here: the two subjects refuse for overlapping but
not identical reasons (a codex entry refuses when archived; a chapter refuses on three states and on a
book-level archive), and a shared abstraction over two members is premature.

## `ToolContext` gives the refusal mirror everything it needs

Confirmed, `backend/app/services/tools.py:93-139` — a **frozen dataclass**:

```
book_id    : int
access     : authz.BookAccess | None
subject    : ResolvedSubject | None
emit_frame : FrameEmitter | None
```

plus the selection text step 009 adds. `BookAccess` is the same frozen dataclass the services use, so
`access.role`, `access.book_state` and `access.collaboration_mode` are all directly readable.
**D10 and D11's assistant-side mirrors are therefore field reads, not new plumbing** — do not add role,
mode or book-state fields to the context, and do not resolve a second `BookAccess`.

`emit_frame` is a per-turn closure (`chat_turn.py:493-494`) that puts a `TurnFrame(event, data)`
(`chat_turn.py:286-299`) onto the queue `run_turn` pumps. `ToolBinder` is
`Callable[[ToolContext], Callable[..., object]]` (`tools.py:146`).

## The four rules the mirror enforces, and where each comes from

| Refusal | Source |
|---|---|
| the subject is not a chapter | subject resolution + `determine_mode`'s chapter branch (step 009) |
| the chapter is not `open` | `domain-chapter.md` — *"`closing` and `closed` both refuse all writes to `text` — from a member and from the assistant alike (US-097.AC-2, US-059.AC-3)"*; `planned` has no body yet |
| the book is `archived` | `context.md` → D10, read off `access.book_state` |
| co-author in a `proposal`-mode book | `context.md` → D11, read off `access.role` + `access.collaboration_mode` |

`frontend-workspace.md` states the symmetry explicitly: *"a read-only subject refuses the author and the
assistant alike"*, with the author refused in HTTP statuses and the assistant in tool strings. DoD-6,
DoD-7 and DoD-8 are that symmetry, one rule at a time.

## Descriptions are part of the contract

`ToolDef.description` is what the model reads to decide whether and how to call the tool. Three of them
carry a fact the model would otherwise get wrong:

- the **read** tool returns the **saved** body, which may lag the author's unsaved draft
  (`context.md` → D4);
- the **selection** tool replaces *the author's current selection*, supplied with the turn — the model
  must not try to describe a location, quote surrounding text as an anchor, or ask for offsets
  (`context.md` → D5);
- the **append** tool adds to the **end** of the body and cannot place text anywhere else.

These are not stylistic notes. Getting them wrong makes the model attempt placement negotiation the
protocol deliberately does not support.

## The tools ship unreachable, and DoD-12 asserts it rather than leaving it to be discovered

`allowed_tool_names(mode_key)` (`assistant_runtime.py:247-274`) returns the mode's `mode_tool` rows via
`db/mode_tools.py::list_by_mode` (`:36-43`) over the `ModeTool` table (`models/mode_tool.py:21-42`).
**Zero rows is an empty allowlist**, so a registered-but-unselected tool is invisible to every turn.

This feature seeds **no** `mode_tool` rows (`context.md` → D4), so on a fresh install the chapter editor
works and the assistant cannot write into it until an admin selects the four tools for `write-chapter`.
That is the same position the codex tools have been in since `013.codex`.

DoD-12 pins the negative (registration alone grants nothing) automatically; DoD-13 covers the positive
end to end and is `[manual/live]` because it needs a real model, a real admin selection and a real
streamed turn.

**The `write-chapter` `AssistantMode` row already exists** — `context.md` → "Mode seeding" — and step
009's DoD-12 asserts it. Nothing here seeds a mode or a selection.

## The variant flow needs nothing here

`context.md` → D4: *"give me 3 variants"* → the model writes candidates **into the transcript** →
*"use v2"* → the model calls the whole-body or selection tool. **No tool for variants, no persistence,
no `ChapterChange` with status `pending`.** FEAT-014's stored variants are `018`'s. Do not add a fourth
write tool for them.

## Emission goes onto the queue `run_turn` already pumps

`assistant-runtime.md`: *"the canvas tool **emits its frame onto the same `asyncio.Queue` `run_turn`
already pumps** for `thinking` and `delta`, so a tool can reach the wire without the loop surfacing
anything per-step."* That is why the shared-canvas write did **not** force the `chat_with_tools` seam
open, and it must not force it open here either — **do not introduce a manual `chat`-in-a-loop driver.**

Accepted consequence, unchanged from the codex: **the draft arrives whole, not streamed**, because
`chat_with_tools` hands a tool its arguments only after the model has finished emitting them.
Token-level canvas streaming stays deferred.

## Testing

`backend/tests/services/test_chapter_tools.py` is created from scratch.

**No LLM server is contacted.** Build the `ToolContext` directly and invoke the bound callables as
functions — that is how the codex tool tests reach the same code, and it is what keeps DoD-3's
"exactly one frame" assertion precise. Capture emitted frames with an in-memory sink standing in for
the turn's queue (the `emit_frame` slot takes a callable).

DoD-4 is the load-bearing one: after each write tool runs, read the chapter back through
`db/chapters.py` and list `db/chapter_changes.py` / `db/chapter_text_revisions.py` and assert all three
are untouched. This is the structural property the design leans on, so assert it rather than trusting
it.

DoD-6 needs chapters seeded into `planned`, `closing` and `closed` through `db/chapters.py`.
DoD-7 needs an archived book; DoD-8 needs a proposal-mode book with a co-author and with the owner —
both expressed by constructing the `BookAccess` on the context, not by going through HTTP.

DoD-12 exercises `allowed_tool_names("write-chapter")` on a database with no `mode_tool` rows and
asserts none of the four names appear.
