# 008 — step context

Feature-wide facts (D8, D14, D19, the close seam, the status taxonomy, the MobX rules, the
mock-the-editor testing decision, the build gates) are in `context.md` and are not repeated here.

## Only this page gets the controls

`context.md` → **D19**. `ChaptersPage.tsx`, `chaptersPageState.ts`, the Shell's `BookHubPage.tsx` and
the navigator are in **no** step's source list in this whole feature. 014's D2 fixed that all skeleton
*editing* lives on the working page and the Shell hub is read-only; the transitions follow the same
rule, and putting an Open control on both the list and the item would give one action two surfaces —
exactly what the one-editing-surface rule exists to prevent.

`frontend-workspace.md`'s Shell route table still says the book hub carries "open / reopen
(UC-035..037)". 014's `outcome.md` item 7 is already correcting that row; this feature's `outcome.md`
finishes it.

## Why the control is state-gated and not role-gated

The page has **no caller-role signal**: `ChapterResponse` and `ChapterTextResponse` carry none (D14),
the workspace shell's book detail is not readable from a page (no React context, no cross-page warm
start), and 014's `can_reorder` lives on the chapter **list** envelope, which this page never fetches.

`013.codex` set the precedent this follows: the collaboration-mode nuance is applied **server-side**,
the client shows the affordance, and the refusal text is what the author reads
(`frontend-workspace.md` — *"the nuance is applied server-side … so `subject.ts` needed no change at
all"*). `CodexEntryPage`'s `serverRefusalText(err)` helper — reading `err.details.detail.message` /
`.reason` — is the harvested shape for pulling that text off an `ApiError`.

Accepted cost, stated once: a co-author sees an Open control that will be refused. DoD-5 is what makes
that refusal legible instead of mysterious.

## Only one control is ever offered

The state machine admits exactly one transition per state, so the page renders one control, not three
with two disabled. A disabled control invites the question "why"; an absent one with the state shown
beside it does not. The `closing` case is the exception and gets a **stated reason** rather than
silence, because `closing` is a state the author cannot currently produce and will not recognise.

## Re-seeding after a transition

A successful transition changes the chapter's `state`, which changes:

- `resolveEditability`'s verdict for the body,
- whether the editor is mounted at all (`context.md` → D16),
- which transition control is offered next,
- 014's sketch editor's enablement (sketches are `planned`-only).

Re-seeding **both** the chapter trio and the body trio from the server is what makes all four follow at
once. Do not patch the loaded chapter's `state` field locally — `context.md`'s "the backend is the
source of truth" rule, and a locally-patched state would leave the body response's own `state` field
disagreeing with it.

DoD-8 exists because re-seeding the body trio must **not** re-seed the body **draft** if the author has
one: a refused transition must not destroy unsaved work, and a successful one must not either. Reload
the trio; leave the draft and the buffer to steps 006 and 007's rules.

## Testing

`frontend/tests/work/ChapterPageStateControls.test.tsx` is created from scratch. Same two module mocks
as step 006 — the whole `api/chapters` module (enumerating **every** export, including 014's and step
004's) and the `ChapterBodyEditor` component.

`ApiError` is imported real; DoD-5 needs a `403` carrying a message and DoD-6 a `409`.

DoD-1, 2, 3 and 4 each need the chapter and body api calls armed to return a chapter in the relevant
state, then re-armed to return the post-transition state so DoD-7's re-seed is observable.

Queries are by **role or label only** — DoD-9 is what makes that possible, and it is a real requirement
rather than a test convenience: a bare "Open" button on a page that also lists other actions is
ambiguous to a screen reader too.
