# 003 — step context

Feature-wide facts (the endpoint list, the status taxonomy, the route/service error idiom, the layer
rules, the test harness) are in `context.md` and are not repeated here.

## The router already exists — this step adds handlers, not a module

014 step 003 creates `backend/app/routes/chapters.py` with the prefix
`/api/books/{book_id}/chapters`, a module-scope `_*_ERROR_STATUS` map, a `_map_*_error` helper, and
six handlers. `main.py` already includes the router.

**Do not create a second router, a second prefix or a second error mapper.** Do not touch `main.py`.

`backend/app/routes/books.py` remains the shape reference for the two-`except` chain;
`backend/app/routes/codex.py` is the closer reference for a family that produces `409` and `403` from
typed reasons.

## Why the transitions are `POST` with no body

They are **commands**, not representations. A `PUT` implies a replaceable representation and would
invite a body; a `PATCH` implies a partial update of the chapter, which is what 014's sketch handler
already is. `POST /{chapter_id}/open` reads as "perform this transition" and cannot be confused with
either. FastAPI accepts a `POST` handler with no body parameter; DoD-17 pins that a request with no
body works.

## Path shapes, spelled out so no handler improvises one

```
GET  /api/books/{book_id}/chapters/{chapter_id}/text
PUT  /api/books/{book_id}/chapters/{chapter_id}/text
POST /api/books/{book_id}/chapters/{chapter_id}/open
POST /api/books/{book_id}/chapters/{chapter_id}/close
POST /api/books/{book_id}/chapters/{chapter_id}/reopen
```

014's `/order` is `PUT /api/books/{book_id}/chapters/order` — a literal segment where `{chapter_id}`
also matches, which is why 014 declares it first. **These five are all `/{chapter_id}/<literal>`**, so
none of them can shadow or be shadowed by anything in the family. No declaration-order rule applies to
them beyond readability.

## `403` on a public book, `404` on a private one — both come from upstream

Unchanged from 014's step 003 and **not re-derived here**:

- a private book the caller has no relationship to → the `book_access` dependency raises `404` before
  any handler body runs;
- a logged-in non-member of a **public** book resolves to the `reader` role, reaches the service, and
  is refused by `authz.require`, which the shared mapper turns into `403`.

DoD-13, DoD-14 and DoD-15 therefore need a **public** book, a **private** book and **no token**
respectively — three distinct fixtures. Conflating them makes the assertions meaningless.

## The two `403`s the service produces are not the authorization error

The archived refusal and the proposal-mode refusal are **chapter errors**, not
`BookAuthorizationError`s, and they reach `403` through this module's own reason→status map. That
matters for the message: the frontend reads `details.detail.message` and surfaces the reason text
verbatim (DoD-6 asserts FEAT-010 is named). A refusal routed through the shared authz mapper would lose
that text.

## Testing

Two spec files, split by concern. Both are created from scratch and both copy the per-file seeding
helpers from `backend/tests/routes/test_book_settings.py` (`_now`, `_auth_header`, `_seed_user`,
`_seed_author`, `_create_book`, `_add_co_author`) rather than importing them — they are deliberately not
shared fixtures.

- `test_chapter_text.py` — DoD 1–7, 13–17 for the body path.
- `test_chapter_states.py` — DoD 8–12, plus the transition halves of 13–17.

**Auth is real** — seed a user row and mint a real JWT. `http_client` drives the real app lifespan over
`httpx.ASGITransport`, so the whole request path including the `book_access` dependency runs.

A spec needing a chapter in `open`, `closing` or `closed` **without** going through the transition
routes writes the state directly through `backend/app/db/chapters.py` with the `db` fixture. The body
specs must do this rather than calling `POST /open` first — a body test that depends on the transition
route fails for the wrong reason when the transition breaks.

Setting a book's **collaboration mode** and its **archived state**: use the existing book routes /
`db/books.py` the way `backend/tests/routes/test_book_settings.py` already does. DoD-6 and DoD-7 both
need them.

DoD-16 needs **two** books with the caller as a member of both, so the `404` is provably the
book-scoping check and not an authorization failure.
