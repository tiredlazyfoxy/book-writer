# 001 — Chapter body DTOs, the two write capabilities, and the read/save service

## Goal

Add the body request/response DTOs, the two `Capability` members that put an enum behind
`authorization.md`'s remaining chapter matrix rows, and the service that reads a chapter's body and
saves a whole new body against a version token — writing one `ChapterChange`, one
`ChapterTextRevision` and one chapter update, in that order.

## Source files

```
backend/app/models/schemas/chapters.py
backend/app/services/authz.py
backend/app/services/chapters.py
```

backend/tests/services/test_chapter_text.py

## Interface intent

**`backend/app/models/schemas/chapters.py`** — two new Pydantic DTOs beside 014's five. Declarative,
no logic. Field sets are fixed by `context.md` → "The wire contract" and are not restated here.

- **`ChapterTextResponse`** — the chapter's id (a string), its state, its body text, its version (an
  ordinary JSON number) and its modified timestamp.
- **`UpdateChapterTextRequest`** — the whole new body and the version it was composed against. The
  body has **no** constraint — an empty body is a legitimate value (D9's degenerate case). The version
  is required; there is no "force" flag and no way to opt out of the check.

014's five DTOs are **not** touched. In particular `ChapterResponse` gains **no** `text` field
(`context.md` → D13).

**`backend/app/services/authz.py`** — two new `Capability` members and their two `_CAPABILITY_MATRIX`
rows, and nothing else:

| Capability | Roles |
|---|---|
| open / close / reopen a chapter (one member for the one matrix row) | **owner only** |
| write into the open chapter | owner, co-author |

No existing member, row or function changes. `BookAccess` gains no field. **No capability is minted
for the archived-book gate or the collaboration-mode gate** — both are service-level, per
`context.md` → "Capabilities added".

**`backend/app/services/chapters.py`** — extends 014's module; its existing entry points, its private
response mapper and its private chapter resolver are reused unchanged.

- **Four new reason members** on 014's reason enum: the chapter is not open; the caller's version is
  stale; the book is archived; a co-author may not write in a proposal-mode book. (Step 002 adds the
  remaining two.)
- **A private archived-book guard** — raises the archived reason when the access context's book state
  is archived. Called by every write path in this feature, including step 002's transitions.
- **A private write-mode guard** — raises the proposal-mode reason when the book's collaboration mode
  is `proposal` **and the caller is not the owner**. Its message names FEAT-010 as unbuilt, following
  `services/codex.py::_require_writable_mode` (D11). It is called by the body save only; transitions
  are owner-only and are never held for review.
- **A private body response mapper** — the single place a chapter row becomes a `ChapterTextResponse`,
  and the single place its id becomes a string.
- **A private placement computation** — given the loaded body and the new body, returns the placement
  kind and, for a range placement, the line bounds and the change text. Exactly the rules in
  `context.md` → **D9**, including all three degenerate cases. It is pure: no session, no clock, no
  row.
- **`get_chapter_text`** — requires the existing **read** capability, resolves the chapter through
  014's resolver, maps it to the body response. **No archived gate and no mode gate** — reads work on
  an archived book (D10).
- **`save_chapter_text`** — the whole write path, in this order:
  1. require the **write** capability;
  2. the archived guard, then the write-mode guard;
  3. resolve the chapter (a chapter from another book is not-found, 014's rule);
  4. refuse with the not-open reason unless the chapter's state is `open` — `planned`, `closing` and
     `closed` all refuse, which is what makes US-040.AC-3 and the second half of US-038.AC-1 true;
  5. refuse with the stale reason unless the submitted version equals the chapter's current version;
  6. compute the placement from the **loaded** body and the submitted body;
  7. create the `ChapterChange` — status applied, `base_version` = the submitted version, `author_id`
     = the access context's user, `applied_by` = the same user, `applied_at` and `created_at` stamped
     here;
  8. create the `ChapterTextRevision` — `applied_change_id` = the change just created, `text_before` =
     the **loaded** body, `applied_by` and `applied_at` stamped here;
  9. update the chapter — new text, version incremented by one, `modified_at` stamped here;
  10. return the body response built from the stored chapter.

  **Nothing is written before step 5 passes**, and the three writes happen in exactly the order above
  (`context.md` → D7). Steps 7–9 are three separate `db/` calls in three separate sessions; do not
  attempt to share a session or add a cross-entity `db/` module.

The service never receives a book id as an argument — it comes from the access context.

## Definition of done

1. `[test]` `get_chapter_text` returns the chapter's stored body, its state, its version and its id as
   a string, for the owner, for a co-author and on an **archived** book — reads are never refused by
   the archive gate (**D10**).
2. `[test]` A co-author saves a new body into an `open` chapter in a **free-mode** book and it becomes
   the chapter's body immediately, with the chapter's version incremented by exactly one —
   **US-040.AC-1**.
3. `[test]` The `ChapterChange` written by that save carries the **saving member** as its author —
   **US-040.AC-2**.
4. `[test]` A save whose new body **starts with** the loaded body writes a change with placement
   `append`, no line bounds, and the appended remainder as its text; a save whose new body does not
   writes a change with placement `range`, `line_from` 1, `line_to` equal to the loaded body's line
   count, and the whole new body as its text — **D9**.
5. `[test]` The three degenerate cases in **D9** behave exactly as specified: a save into an empty body
   is an `append` carrying the whole body; clearing a non-empty body to `""` is a `range` carrying
   `""`; re-saving an unchanged body is an `append` carrying `""` and still bumps the version.
6. `[test]` A successful save writes exactly **one** `ChapterChange` (status applied, `base_version`
   equal to the submitted version, `applied_by` set) and exactly **one** `ChapterTextRevision` whose
   `applied_change_id` names that change and whose `text_before` is the body as it stood **before** the
   save — **D7**, and the record `018` reads back.
7. `[test]` A save carrying a version that is not the chapter's current version is refused with the
   stale reason, and **nothing is written**: the body, the version, and the change and revision counts
   are all unchanged — **US-041.AC-1**, **UC-039**.
8. `[test]` After that refusal, a save of a body containing **both** members' text, carrying the
   **current** version, succeeds and becomes the chapter's body — **US-041.AC-2**, **US-040.AC-4**
   (the mechanism; the merging is the author's, per `context.md` → "Known product gaps").
9. `[test]` A save into a chapter whose state is `planned`, `closing` or `closed` is refused with the
   not-open reason and writes nothing — **US-040.AC-3**, and the "no longer editable" half of
   **US-038.AC-1**.
10. `[test]` A **reader** and a caller with no relationship are refused `save_chapter_text` by the
    authorization error, and a reader may still call `get_chapter_text` on a public book.
11. `[test]` A **co-author** saving into a **proposal**-mode book is refused with the proposal reason
    and writes nothing, while the **owner** saving into the same book succeeds — **D11**.
12. `[test]` Every save path and the state-transition guard alike are refused with the archived reason
    on a book whose state is `archived`, and nothing is written — **D10**.
13. `[test]` A chapter id belonging to **another book** is not-found on both entry points — not a
    permission failure — reusing 014's resolver.
14. `[test]` The two new `Capability` members exist with exactly the roles in the table above, and no
    existing capability's role set changed.
