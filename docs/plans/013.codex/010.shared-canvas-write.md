# 010 — Shared-canvas write: the `write_codex_draft` tool and the `canvas` frame

## Goal

Let the assistant write a draft into the codex entry open in the content pane: a mode-gated
`write_codex_draft` tool that persists nothing, emits a new `canvas` SSE frame through the queue
`run_turn` already pumps, and refuses a read-only subject exactly as the author would be refused.
Delivers the backend half of UC-076 / UC-077.

## Interface intent

**`backend/app/models/schemas/chats.py`** — add **`CanvasFrame`** beside `ThinkingFrame` /
`DeltaFrame` / `DoneFrame` / `ErrorFrame`: the subject kind, the subject id (a string, **null** for a
blank entry that has no row yet), the field being written, and the text. `field` exists because a
character entry has both a `name` and a `body`.

**`backend/app/services/tools.py`** — the tool context from step 009 is widened to also carry the
turn's **resolved subject** (from step 007's resolution) and a **frame emitter** — a callable that
puts a `TurnFrame` onto the queue `run_turn` already owns. One new bound `TOOL_REGISTRY` entry,
`write_codex_draft`, mode-gated like any other.

**`backend/app/services/codex_tools.py`** — the tool callable.

- **arguments**: which field to write (`name` or `body`) and the text to write.
- **server-side editability validation**, mirroring
  `frontend/src/work/subject.ts:checkWritePermission`, because `frontend-workspace.md` requires a
  read-only subject to refuse "the author and the assistant alike":
  - the turn's subject must be a codex entry — any other subject, or no subject, is refused;
  - an **archived** entry is refused with the archived reason;
  - a **co-author** in a `proposal`-mode book is refused with the reason naming FEAT-010 as unbuilt
    (`context.md` decision 3 — the same rule the save path applies, applied at the same place in the
    author's mental model);
  - writing a **name** to a `fact` subject is refused (US-078.AC-2 symmetry).
- **it touches no database at all** — no read of `codex_entries` beyond what step 007 already
  resolved, no write, no version row. There is no code path from a chat to the `codex_entries` table.
- on success it pushes exactly one `CanvasFrame` onto the queue and returns a **short confirmation
  string** to the model so `chat_with_tools` keeps looping.
- **it never raises**: every refusal and every failure returns a string.

**`backend/app/services/chat_turn.py`** — build the tool context with the resolved subject and an
emitter bound to the turn's existing `asyncio.Queue`. **No change to
`backend/app/routes/chats.py`**: its serializer at line ~227 already writes any frame as
`f"event: {frame.event}\ndata: {frame.data.model_dump_json()}\n\n"`, so a `TurnFrame` whose event is
`canvas` is emitted correctly with no route edit. Say so rather than touching the route.

## Definition of done

1. `[test]` Invoking the tool with an editable codex-entry subject pushes exactly **one** frame whose
   event is `canvas` and whose payload carries the subject kind, subject id, field and text.
   (US-086.AC-1, US-087.AC-1)
2. `[test]` The frame reaches the HTTP stream serialized as `event: canvas` with the model's JSON
   payload, interleaved with the turn's ordinary `delta` frames — with no change to
   `routes/chats.py`. (`context.md` → shared-canvas design point 2)
3. `[test]` After a turn that invoked the tool, the `codex_entries` and `codex_entry_versions` tables
   are **byte-for-byte unchanged** — nothing was persisted. (US-086.AC-2, US-087.AC-2, US-088.AC-2)
4. `[test]` The tool returns a non-empty confirmation string to the model, so the tool loop
   continues rather than terminating. (`llm` loop contract)
5. `[test]` With an **archived** entry as the subject the write is refused, a string is returned, and
   **no** canvas frame is emitted. (`frontend-workspace.md` — a read-only subject refuses author and
   assistant alike)
6. `[test]` With a book-state, list, chapter or absent subject the write is refused with a string and
   no frame is emitted. (`frontend-workspace.md` → content-pane editability table)
7. `[test]` A co-author in a **proposal**-mode book is refused, and the returned string names FEAT-010
   as the unbuilt mechanism. (decision 3; US-079.AC-2 knowingly unmet)
8. `[test]` The **owner** of a proposal-mode book is **not** refused. (decision 3)
9. `[test]` With a blank entry as the subject (no id), the write is allowed and the frame carries a
   null subject id. (UC-076 — a blank entry has no row yet)
10. `[test]` Writing a `name` to a `fact` subject is refused; writing a `body` to it is allowed.
    (US-078.AC-2 symmetry)
11. `[test]` The tool never raises on any path, including a queue failure. (`web_search` contract —
    a raising tool aborts the whole loop)
12. `[test]` The tool is only reachable when the running mode selects it — a mode without the
    `mode_tool` row builds no `write_codex_draft` definition. (US-111.AC-2)

Steps 007 (the resolved subject on the turn) and 009 (the tool context and the binder).
