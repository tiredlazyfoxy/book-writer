# 013 — step context

The shared-canvas write design — including why the registry lives at the module tier and why the
restore buffer is the fallback — is in `context.md` → "The shared-canvas write design", point 4. The
`work` tree's shape, api conventions and test gotchas are in `011.context.md`; `restoreBuffer.ts`'s
and `subject.ts`'s exact exports are in `012.context.md`. None of that is repeated here.

## Why a registry and not the obvious alternatives

All three obvious designs are banned by `frontend.md`:

- **React context** to share the subject between the pane and the page — no React context anywhere in
  this repo.
- **A cross-page callback** from the entry page up to the shell — pages do not call each other; the
  backend is the source of truth and pages load their own data.
- **A custom `useCanvasTarget()` hook** — no custom `useX` hooks.

The module tier is the sanctioned fourth option: `frontend.md`'s state ladder puts app-lifetime state
at module level, `auth.ts` is the existing precedent, and `restoreBuffer.ts` + `activeChat.ts` are the
two the `work` entry already added. The registry joins them as **plain functions**, not a reactive
store — the same treatment `frontend-workspace.md` prescribes for the buffer.

## `chatPaneState.ts` as `011` shipped it

`class ChatPaneState` holds the trios `chats` / `chatsStatus` / `chatsError`, `modelOptions` / …,
`messages` / …, plus `activeChatId`, `showArchived`, `newChatDraft`, `settingsDraft`, `serverErrors`,
`createStatus`, `archiveStatus`, `settingsStatus`, `streamingContent`, `streamingThinking`,
`turnStatus`, `turnError`, `pendingPrompt`, `turnController`.

External functions: `loadChatPane(state, bookId, signal?)`, `pickChat`, `createChatFromDraft`,
`setChatArchived`, `saveChatSettings`, `loadChatMessages`, `sendChatTurn(state, bookId, text)`,
`retryChatTurn`, `stopChatTurn`.

**`ChatPaneState` has no subject field and must not gain one.** `WorkspaceShell.tsx:27` owns the
single instance via `useState(() => new ChatPaneState())` and renders
`<ChatPaneSlot bookId={id} state={chatPaneState}/>`. The pane reads the current subject from the
registry **at send time**, which is also what keeps it correct when the author navigates between
sending and retrying. `WorkspaceShell.tsx` therefore needs no change.

## `streamChatTurn`'s existing shape — the one sanctioned convention break

`frontend/src/api/chats.ts` exposes
`interface TurnStreamHandlers { onThinking; onDelta; onDone; onError }` and
`async function streamChatTurn(bookId, chatId, prompt: string | null, handlers): Promise<AbortController>`.

It awaits `refreshAuthToken()` first (because `sse.ts:streamPost` uses raw `fetch` + `authHeaders()`
and bypasses `request<T>`'s on-401 silent refresh), then calls `streamPost`, which **owns and
returns** the `AbortController`. That is the one sanctioned break of the trailing-`signal`
convention — keep it; do not add a `signal` parameter while adding `onCanvas`.

`frontend/src/api/sse.ts` special-cases `done` (→ `onDone`) and `error` (→ `onError`) and routes every
other event name to a generic handler. `011`'s `outcome.md` item 21 calls that generic path "the
first concrete piece of the deferred FEAT-013 event protocol"; the `canvas` event uses it, so
**`sse.ts` is not in this step's source list and must not be edited**.

Note the shape `011` recorded and this step inherits: `streamPost` calls `onDone()` **with no
argument**, which is why `sendChatTurn` reloads the chat on `done`. Nothing here changes that.

## Which subject fields go on the wire

The backend's `TurnRequest` gained `subject_kind`, `subject_id` and `codex_kind` in step 007, all
optional. Map from `LoadedSubject`:

| `LoadedSubject` | wire fields |
|---|---|
| `{ kind: "codex-entry", entityId: "123", codexArchived: false }` | subject kind `codex-entry`, subject id `"123"`, codex kind from the loaded entry |
| a blank entry | subject kind `codex-entry`, subject id `null`, codex kind from the `/codex/new` query param |
| `{ kind: "characters" }` etc. | subject kind only |
| nothing registered | all three absent |

`codex_kind` is only meaningful for the blank case (the backend ignores it when the row exists), but
sending it always is simpler and harmless.

## The buffer fallback key

`restoreBufferKey(bookId, "codex-entry", subjectId)` — the same key step 012's page reads on load, so
a fallback-buffered draft surfaces through the path that already exists with no extra code on the page
side. Its `baseVersion` is the entry's `modified_at` as known to the frame's sender; when the
dispatcher has no `modified_at` to hand, buffer against the value the page last loaded, and accept
that a stale one simply routes the author into step 012's reconciliation view — which is the correct
outcome, not a bug.

## Registration guarding

Two pages can briefly overlap during a route transition (the new page mounts before the old one's
cleanup runs, or vice versa). Unregister must therefore be **identity-guarded**: clearing only takes
effect if the registration still belongs to the caller. DoD-9 tests exactly this.
