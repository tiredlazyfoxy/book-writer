# 009 — step context

Feature-wide facts (the binder decision and its reasoning, decision 2 on lexical-vs-semantic search,
the never-raise tool contract, test harness) are in `context.md`. `services/tools.py`'s and
`services/chat_turn.py`'s shipped shapes are in `007.context.md`; the `llm` client's tool-dispatch
constraints are in `008.context.md` and bind here identically.

## Why the tool context exists

The `llm` client validates a tool callable's arguments against `inspect.signature(func).parameters`
and applies them as `func(**kwargs)`. There is **no per-request context argument**, so the book id
must be closed over at binding time. `011`'s `context.md` records the same constraint: "anything a
tool needs (book id, user, session) must be bound by a closure or `functools.partial` default."

The binder field is additive precisely so `web_search` — the one shipped registry entry — keeps its
plain `callable` and needs no edit.

## What UC-078 asks for and what stays open

UC-078's postcondition carries an unresolved product `_TBD:`: "what makes an entry *relevant* enough
to reach the chat — no measurable criterion offered; see challenge C27." `retrieval.md` likewise
picks no threshold and explicitly lists it out of scope.

This step therefore ships **pull-only** semantic search — the model asks, the tool answers — and sets
**no score threshold**. A result limit is a bounded-output concern, not a relevance criterion. Do not
introduce a minimum-score cutoff; that would close the `_TBD:` by design.

Automatic push of "relevant" codex entries into the prompt (context assembly, US-057) is **not** part
of this feature at all — `assistant-config.md` and `domain-chat.md` both keep it deferred.

## Search scope is not a model-supplied argument

`retrieval.md`: "`book_id` is a **hard filter**, never a ranking preference. Cross-book leakage would
break the members-only codex rule (US-085) and the book-scoped authorization model outright — a hit
from another book is not a worse result, it is a permission violation."

The consequence for the arg schema: **there is no book parameter**. The model cannot request another
book's codex because the tool exposes no way to name one. The same applies to the read tool — it
takes an entry id and validates the entry's `book_id` against the context's, rather than trusting the
id.

## The sidecar surface this step calls

Step 005's `search` takes `(book_id, query_vector, kinds, limit)` and returns hits carrying
`source_kind`, `source_id`, `chunk_index`, `text`, `score`. `source_id` is a **string**. The
`retrieval.md` note applies: "a hit carries its `source_id` so a consumer can load the authoritative
row from SQLite rather than trusting the indexed copy for anything beyond the snippet" — which is
exactly the division of labour between the two tools here.

## Reading entries

Use `backend/app/db/codex_entries.get_by_id` and check `book_id` against the context. Do **not** call
`services/codex.py` — it requires a `BookAccess` the tool context does not carry, and its capability
check has already been satisfied upstream by the chat turn's own `book_access` dependency.

## Result formatting

The tool's return value is a **string** the model reads. Keep it compact and stable: one block per
hit, entry id first so a follow-up read is unambiguous, and the chunk text (not the whole entry) as
the snippet. Deterministic formatting matters for testability.

## Test approach

Mock step 004's embed call. Drive step 005's sidecar for real against a `tmp_path` vector dir with
fixed short vectors so ordering is predictable, seed codex rows in two different books, and assert on
the returned string's content. No network anywhere.
