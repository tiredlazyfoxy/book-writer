## `frontend/src/work/restoreBuffer.ts` — complete, unit-tested, consumed unchanged

- `RESTORE_BUFFER_KEY_PREFIX = "bookwriter.restore-buffer"`
- `type BufferBaseVersion = number | string` — `Chapter.version` for a chapter, the codex entry's
  **`modified_at` ISO string** for a codex entry
- `interface BufferedDraft { draft: string; baseVersion: BufferBaseVersion; writtenAt: string }`
- `type WriteResult = { status: "saved" } | { status: "saved-after-eviction"; evictedKeys: string[] }
  | { status: "failed" }`
- `restoreBufferKey(bookId, subjectKind, subjectId)`, `readBuffer(key)`,
  `writeBuffer(key, draft, baseVersion)`, `clearBuffer(key)`

`BufferedDraft.draft` is a **single string**. A codex entry has two editable fields (`name` and
`body`). The buffered draft is therefore the **body** — the substantive content and the only field
large enough for the loss the buffer exists to prevent. The name is small, always visible, and is not
buffered. Record this in `outcome.md`; do not widen `restoreBuffer.ts`'s shape to hold a pair.

`writeBuffer`'s eviction contract is already implemented — the current item's buffer is never the
eviction victim — so DoD-13 is about **surfacing** the `saved-after-eviction` result, not
implementing eviction.

## Concurrency contract with the backend

- The update request carries the **loaded** `modified_at`; the backend compares it and answers **409**
  when it is stale (step 002 / 003).
- The response's `modified_at` is the new base version — after a successful save the state must adopt
  it, or the *next* save will 409 against a value the client itself produced.
- `frontend-workspace.md`: "A save carrying a stale base version is refused by the server with
  **409**; the client's job is to turn that refusal into the reconciliation view rather than a raw
  error. This is also what US-041's 'warn the second author' looks like in the UI — the warning *is*
  the divergence view."

## Errors from the api layer

`src/api/client.ts` throws `ApiError(status, message, details?)`. Branch on `status` (409 vs 403 vs
the rest) and read the backend's typed reason out of `details` — step 003 puts the reason value in
the detail body precisely so the client can branch on it rather than on message text.

## Forms

Drafts live in state, validation is `get` computeds, and server errors are merged separately. **Do
not use Mantine `useForm`** — it is banned by `frontend.md`.

## Test gotchas

Beyond the shared ones in `011.context.md`: `frontend/tests/setup.ts` clears `localStorage` in
`afterEach`, so a buffer must be seeded inside the test that needs it. Mount the page directly (not
through `WorkRoutes`) where possible to avoid needing the `api/chats` mock; where the route is under
test, mock `../../src/api/chats` as usual.
