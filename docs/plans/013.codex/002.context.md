# 002 — step context

Feature-wide facts (layer rules, DTO conventions, the collaboration-mode decision and its reasoning,
test harness) are in `context.md`. The two db modules' current and widened shapes are in
`001.context.md` — read that for the exact function inventory this service calls.

## The error-class shape to copy

`backend/app/services/chats.py` defines `ChatErrorReason` (a `str` enum) plus a `ChatError` exception
carrying the reason. Copy that pairing exactly — the router in step 003 binds to it through a
module-level reason→status dict. Do not invent a different error protocol.

## What the service may and may not touch

- `services/` may **not** import `AsyncSession`, call `select()`, `session.exec()` or `session.add()`.
  Every read and write goes through `app.db.codex_entries` / `app.db.codex_entry_versions`, imported
  as namespace modules.
- The service **is** allowed to import `app.services.authz` and call
  `authz.require(access, Capability.X)`.
- `BookAccess.collaboration_mode` is already resolved on the access context handed in by the route
  dependency — the service does **not** re-read the book to learn the mode.
- `BookAccess.role` is the `AccessRole` enum (`owner` / `co_author` / `reader` / `none`); the
  proposal-mode rule branches on `role == co_author`, not on "not owner", so a future admin/reader
  path cannot slip through it.

## Ordering that is load-bearing in `update`

The version row must be written **before** the entry row is mutated, because it carries the *prior*
content. Writing it afterwards would either need a second read or would capture the new content —
the exact bug `domain-codex.md` warns about when it says version rows carry "the entry's content **as
it stood** at that version".

`generation` comes from the db layer's next-generation lookup (step 001), not from
`len(list_by_entry(...))` — the latter is a read-modify-write with a wider race window and gives the
wrong answer if a row is ever removed.

## Optimistic concurrency

The update request's expected-`modified_at` is compared against `CodexEntry.modified_at`. Both are
`datetime`; the DTO field is serialized as an ISO string on the wire and parsed by Pydantic. A `None`
stored `modified_at` (an entry never edited since creation) must still compare correctly — decide the
comparison on the stored value, and treat a mismatch of any shape as stale.

The frontend's restore buffer uses this exact field as its `baseVersion`
(`frontend/src/work/restoreBuffer.ts`: `type BufferBaseVersion = number | string`, the string case
being "codex `modified_at` ISO string"), so the value the response DTO emits and the value the update
request expects must be the **same serialization**.

## `author_id` vs `modified_by`

`CodexEntry.author_id` is non-null and is the **original creator** — it is set once at create and
never rewritten. `modified_by` is nullable and is set on every edit. The version row's `author_id` is
"who produced that version" (`domain-codex.md`), i.e. the user performing the edit that *supersedes*
that content — set it to the acting user of the edit that writes the row.

## Nothing here touches the index

Vector indexing on create/edit is **step 006's** wiring, deliberately layered on top of this service
afterwards so the SQLite write commits first and an embedding failure can never block the author's
save (`retrieval.md`). Do not call anything embedding- or vector-shaped from this step.

## Size note

This step is at the top of the 50–200 LoC band (roughly 70 lines of schemas and 130 of service). It
is one contract — the DTOs, their sole mapper, and the six rules that guard them — and splitting the
schema module away would leave a frozen interface with no behaviour behind it for a whole pipeline
run. If implementation pushes materially past 200, hand back rather than trimming a rule.
