## The frame path that already exists — nothing in it needs changing

- `services/chat_turn.py` defines `@dataclass(frozen=True) class TurnFrame: event: str; data:
  BaseModel` (line 231) and pumps frames over an `asyncio.Queue` from the inner `drive()` coroutine
  out through `run_turn`'s generator.
- `backend/app/routes/chats.py:194` `POST /{book_id}/chats/{chat_id}/turn` returns a
  `StreamingResponse(event_stream(), media_type="text/event-stream")`; each frame is serialized at
  line ~227 as `f"event: {frame.event}\ndata: {frame.data.model_dump_json()}\n\n"`. The serializer is
  **generic over the event name** — a new frame type needs no route change.
- The frame vocabulary shipped by `011` is `thinking` / `delta` / `done` / `error`; `canvas` is the
  fifth and the first piece of the shared-canvas protocol.
- On the client, `frontend/src/api/sse.ts` already special-cases `done` and `error` and routes every
  other event name to a generic handler — which is why the frontend half (step 013) also needs no
  change to `sse.ts`.

## Why the draft arrives whole

`chat_with_tools` hands a tool its arguments only once the model has finished emitting them, so the
entry fills in one jump while the chat's own prose streams normally. Token-level canvas streaming
would require driving the loop manually — which `assistant-config.md` names as the later swap and
`context.md` puts out of scope. Do not attempt partial-argument streaming.

## Emitting from inside a tool callable

The tool runs inside `drive()`, i.e. inside the same task that already puts `thinking` and `delta`
frames on the queue. The emitter closed over in the tool context should therefore be the **same**
put-onto-the-queue path, so ordering with the surrounding `delta` frames is natural and no second
transport exists. A queue failure must still be caught and turned into a returned string — DoD-11.
