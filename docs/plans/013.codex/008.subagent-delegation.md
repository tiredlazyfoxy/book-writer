# 008 — Sub-agent delegation as synthetic tools

## Goal

Expose a mode's allowed, non-disabled sub-agents to the parent assistant as synthetic tools whose
invocation runs a nested, bounded `chat_with_tools` with the sub-agent's own prompt, its own
tools-only allowlist and its own resolved model — one level deep, by construction.

## Interface intent

**`backend/app/services/subagent_delegation.py`** — new module.

- **a parent-turn value** — what a delegation needs from the turn it is nested inside: the parent's
  `LlmServer`, its resolved api key and its model name, so a sub-agent with a null model assignment
  can inherit them (US-113.AC-6). Frozen dataclass.
- **a nested loop bound** — a module constant for the sub-agent's own `max_loops`, separate from
  `chat_turn.MAX_LOOPS`, so tuning the parent's loop does not silently change delegation depth.
- **a synthetic-tool builder** — given a mode key and the parent-turn value, returns a list of
  `ToolDef`s, one per invokable sub-agent:
  - reads the mode's `mode_subagent` rows, loads each `SubAgent`, and **excludes `disabled` ones**
    (both because their links should already be gone and because a stale row must not be a hole —
    `assistant-config.md`);
  - derives a stable, model-safe tool name from the sub-agent's name (lowercased, non-alphanumerics
    collapsed, a fixed prefix marking it as a delegation);
  - **collision guard**: a derived name that collides with a real `TOOL_REGISTRY` name, or with an
    earlier synthetic name in the same build, is **skipped and logged** — the real tool always wins,
    because the registry is the code-defined source of truth;
  - the args schema is a single free-text task instruction — the parent describes what it wants done;
  - the description carries the sub-agent's name so the model can choose sensibly.
- **the delegation callable** — for one sub-agent: resolve its tool allowlist from its
  `subagent_tool` rows against `TOOL_REGISTRY` (**tools only, never another sub-agent**, so the
  nested loop cannot delegate); resolve its model — its own `(llm_server_id, model_name)` when both
  are set, otherwise the parent's server/key/model; construct a client through
  `services/llm_servers.py`'s existing model-bound path, entered as `async with`, **one client per
  delegation** (see `context.md` for why not cached); run `chat_with_tools` with the sub-agent's own
  `system_prompt` **alone** — no base, mode, book or chapter composition — and the nested loop bound;
  return the nested call's final string to the parent.
  It **never raises**: any failure (unreachable model, an unusable server assignment, loop
  exhaustion) returns a short error string, exactly as `services/web_search.py:web_search` does,
  because a raising tool aborts the whole parent loop.

**`backend/app/services/assistant_runtime.py`** — the runtime's tool resolution grows a second half:
alongside the real `TOOL_REGISTRY` tools it now also returns the mode's synthetic delegation tools,
so `chat_turn` has one place to ask "what tools does this turn have". With **no** mode there are no
synthetic tools at all.

**`backend/app/services/chat_turn.py`** — pass the parent-turn value into that resolution and hand
the combined tool list to `build_tool_bindings`, so real and synthetic tools land in the **same**
`tools_definitions` / `tools` maps. No other change; the `llm` client's pre-flight requires the two
maps to be built together.

## Definition of done

1. `[test]` A mode's non-disabled sub-agents appear as synthetic tools in the same definitions and
   callable maps as the real registry tools, and every definition name has a matching callable key.
   (US-112.AC-3; `llm` pre-flight)
2. `[test]` A `disabled` sub-agent is excluded even when a stale `mode_subagent` row still references
   it. (US-114.AC-2)
3. `[test]` A sub-agent that is **not** in the mode's set is not built and cannot be invoked.
   (US-112.AC-3)
4. `[test]` With **no** mode, no synthetic delegation tools are built. (`assistant-config.md`:
   delegation is a mode concept)
5. `[test]` Invoking a synthetic tool runs a nested `chat_with_tools` whose `system` is the
   sub-agent's own `system_prompt` **alone** — the parent's composed base/mode/book prompt does not
   appear in it. (`assistant-config.md` → Sub-agent delegation)
6. `[test]` The nested call's tools are exactly the sub-agent's `subagent_tool` allowlist resolved
   against `TOOL_REGISTRY`, and **no** synthetic delegation tool is ever passed into it — the nested
   loop cannot delegate. (structural one-level bound)
7. `[test]` A `subagent_tool` row naming a tool absent from `TOOL_REGISTRY` is skipped and logged.
   (`assistant-config.md`)
8. `[test]` A sub-agent with both `llm_server_id` and `model_name` set gets a client constructed for
   that server and model through the existing construction path. (US-113.AC-5)
9. `[test]` A sub-agent with a **null** assignment inherits the parent turn's server, resolved key
   and model. (US-113.AC-6)
10. `[test]` A sub-agent whose assigned `LlmServer` no longer exists or is unusable returns an error
    string to the parent rather than raising. (`012` outcome item 4's accepted consequence)
11. `[test]` The nested call is bounded by the module's own loop constant, independent of
    `chat_turn.MAX_LOOPS`.
12. `[test]` A synthetic name colliding with a real registry tool name is skipped and logged, and the
    real tool survives in the maps. (registry is source of truth)
13. `[test]` Two sub-agents whose names derive to the same tool name produce one tool, with the
    second skipped and logged.
14. `[test]` Any failure inside the nested call — transport error, LLM error, loop exhaustion —
    returns an error string to the parent loop and never raises. (`web_search` contract)
15. `[test]` The nested client is constructed per delegation and exited through its async context
    manager on every path, including failure. (`LLMClient` has no standalone `close()`)
16. `[manual/live]` With a configured sub-agent and a live model, a parent turn that delegates
    returns the sub-agent's answer inside the parent's reply.
