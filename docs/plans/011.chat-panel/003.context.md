# 003 — step context

Feature-wide facts (layer rules, the `llm` client contract and its option allowlist, the SSE frame
vocabulary, the privacy rule, the deployment requirement, test harness, gates) are in `context.md`.
Only what this step alone needs is below.

## The reasoning gap — verified, and it is why the splitter exists

`chat_with_tools(stream=True)` routes through the library's `_stream_openai_tools_response`, which
reads **only** `delta["tool_calls"]` and `delta["content"]`. It never reads `reasoning_content`,
has no `<think>` handling and no `in_reasoning` state. **Reasoning arriving as a separate SSE field
is silently discarded inside the library** — it reaches neither `on_delta`, nor the return value, nor
the trace.

The reasoning-aware parser `_stream_openai_chat_response` — which *does* emit `<think>` / `</think>`
markers glued onto the first reasoning delta and the first post-reasoning content delta — is
reachable **only** from plain `chat()`, which has no tool loop. We need the tool loop, so we cannot
use it.

Hence decision 7: the server inlines the tags into `content` (`--reasoning-format none`) and this
step splits them itself. Note the shape that parser produces when it *is* used — a tag glued onto the
first delta of each side — because that is exactly the adversarial case DoD-1 pins.

## `on_delta` vs the return value — not equivalent

`chat_with_tools` returns **only the final round's content**, while `on_delta` receives content from
**every** round including intermediate tool-calling rounds. Build the persisted assistant message
from the streamed content deltas (which is also the only place thinking text exists), not from the
return value. If the coder finds a reason to prefer the return value for content, that reason must be
written into the module — it is not the default.

## The existing client construction path

`services/llm_servers.py:_create_client(server, resolved_key) -> LLMClient` constructs
`OpenAIAPIClient` or `LlamaSwapAPIClient` **directly** (not via `get_llm_client`) with `model=""`,
because it exists only to serve `list_models()`. It is documented as the **monkeypatch seam the
existing LLM-server tests bind to** — keep its name and its current behaviour working.

There is **no `backend_type` → `server_type` string mapping** anywhere in the repo, and none is
needed while the direct-construction bypass is kept; the stored values are `"llama-swap"` (hyphen)
and `"openai"`.

`services/llm_servers.py:get_server()` **masks the api key**, so runtime code reads the row through
`db.llm_servers.get_by_id` and resolves the key itself — `probe_models` is the precedent.

Error taxonomy to extend or mirror: `LlmServerErrorReason(invalid_backend_type | missing_field |
not_found | env_not_set | probe_failed)` → 400 / 400 / 404 / 400 / 502.

**Known pre-existing leak, do not silently inherit it:** `_create_client`'s clients are never closed,
so `list_models()` leaks an `aiohttp.ClientSession` per call. `LLMClient` has `__aenter__` /
`__aexit__` and **no standalone `close()`**. The new path must be used as an async context manager.
Fixing the existing `list_models` leak is **out of scope** for this step; it is recorded for the
architect in `outcome.md`.

## Frames and the client that reads them

`frontend/src/api/sse.ts:streamPost()` splits the body on `\n\n`, parses `event:` / `data:` lines,
JSON-parses `data`, and routes `error` → `onError`, `done` → `onDone`, everything else → `onEvent`.
So `data:` must always be valid JSON, one frame per `\n\n`-terminated block, and the four names are
fixed. There are **zero call sites today** — step 005 writes the first, and it is the only consumer
this endpoint has to satisfy.

There is no existing SSE endpoint on the backend either; this route is the first, so nothing
constrains its response construction beyond the frame format above.

## Retry semantics — why the prompt is optional

UC-056 / US-060 want "retry the same request" without retyping. Persisting the user message **first**
makes the stored history the source of truth: a retry is simply "run the assistant over what is
already stored", which is why the turn request's prompt is optional rather than there being a second
endpoint. A retry after a *successful* turn is not a defined operation and needs no special handling
— it just appends another assistant message over the same history.

## Bounds and the deferred interior

- `max_loops` is bounded per call (`assistant-config.md` → "The tool / function-call protocol"). Pick
  a small bound and name it as a module constant.
- The whole `chat_with_tools` call is the **replaceable interior** the brief asks to be recorded: the
  config model, the tool registry, gating and the prompt composition are all independent of it, so
  swapping it for a manual `chat`-in-a-loop driver when the shared-canvas SSE protocol arrives
  touches nothing else. Keep the call behind the turn orchestrator's own boundary so that stays true,
  and see `outcome.md`.
- No sub-agent synthetic tools, no mode lookup, no context assembly. Null mode, whole registry.

## Ollama

`OllamaAPIClient` raises on `stream=True` and its `chat_with_tools` has no `on_delta` at all. The repo
supports only `llama-swap` and `openai`, so this is irrelevant — but do not write code that pretends
ollama works.

## Testing this step without a network

`asyncio_mode="auto"`. The client construction path is the seam: substitute a fake client whose
`chat_with_tools` invokes the supplied `on_delta` with a scripted list of chunks and then returns (or
raises). That is what makes DoD-1's adversarial chunkings, DoD-9's five failure classes and DoD-6's
per-backend option assertion all reachable with no network and no LLM. The splitter is a plain object
and is tested directly, not through the turn.
