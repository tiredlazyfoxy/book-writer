# 002 — tool registry, web search, prompt composition

## Goal

Ship the two pure halves of the assistant scaffold: the code-defined `TOOL_REGISTRY` with
`web_search` (Google Custom Search JSON API over `httpx`) as its first and only entry, and the
`base → mode → book → chapter` system-prompt composer. Both are unit-testable with no LLM and no
network. Slightly above the band (~250 lines) per the sizing call in `context.md`.

## Interface intent

- **`settings.py`** — two new fields following the existing `Field(default=...,
  validation_alias="BOOKWRITER_...")` convention: the Google Custom Search **api-key reference** and
  the **search-engine id**, both defaulting to unset so the app boots without them. The api-key field
  holds a **`$ENV_VAR` pointer, never a plaintext key**; both values are passed through
  `services/secrets.py:resolve_env_ref` at call time. Nothing else in `Settings` changes.
- **`models/schemas/tools.py`** (new) — the tool argument schemas, Pydantic only, no logic.
  - **`WebSearchArgs`** — the query string and an optional result count with a sane bound. Its field
    names are load-bearing: they become the JSON-schema property names *and* must be exactly the
    keyword parameters the callable accepts (`context.md` → tool callables).
- **`services/web_search.py`** (new) — the tool implementation.
  - An **async `web_search` callable** taking the `WebSearchArgs` fields as keyword parameters and
    returning a **single string** — a compact, model-readable rendering of the results (title,
    snippet and link per result, plus an explicit "no results" string when the search returns none).
  - It resolves the api key and engine id through `resolve_env_ref`, calls the Google Custom Search
    JSON API over `httpx` in an async client it owns and closes, and never logs or returns the
    resolved key.
  - **It catches its own failures and returns an error string instead of raising** — unset env var
    (`resolve_env_ref` raises), unconfigured settings, non-2xx, transport failure, malformed
    payload. Reason, stated in the module: a tool that raises is wrapped as `RuntimeError` by the
    `llm` client and **aborts the whole tool loop**, and the error is never fed back to the model, so
    a raising tool turns a recoverable search failure into a failed turn.
- **`services/tools.py`** (new) — the registry, mirroring `TABLE_REGISTRY` /
  `VECTOR_SOURCE_REGISTRY`: a plain module-level literal list, **no decorator and no register
  function**.
  - **`ToolDef`** — a frozen dataclass (the `BookAccess` precedent) with `name`, `description`,
    `args_schema` (a `BaseModel` subclass) and `callable`.
  - **`TOOL_REGISTRY`** — a module-level list whose only entry is `web_search`.
  - A **resolver** taking an optional allowed-name collection and returning the matching `ToolDef`s:
    **`None` (null mode) means the whole registry**; a name with no registry entry is **skipped and
    logged**, never an error (`assistant-config.md` → "the catalogue is source of truth"). Document
    in the module that the null-mode branch is the seam `013.codex` replaces with real `mode_tool`
    gating.
  - A **builder** turning a `ToolDef` list into the pair `chat_with_tools` wants: the OpenAI tool
    definitions (via `pydantic_to_openai_tool(name, description, args_schema)`) and the
    name → callable map. They are built together and always have identical key sets, because a
    mismatch makes the client raise `ValueError` at pre-flight.
- **`services/prompt_composition.py`** (new) — pure, no I/O, no db reads.
  - A module-level **base prompt constant** — the app-level assistant identity, non-empty, the only
    layer besides the book prompt that is ever populated in this feature.
  - A **composer** taking the four optional layers in order (base, mode, book, chapter) and
    returning one string: each non-empty layer rendered as its own delimited, labelled section in
    the fixed order; **an empty or absent layer contributes nothing at all** — no section, no
    separator, no blank block; all-empty yields an empty string. Whitespace-only counts as empty.

## Definition of done

1. `[test]` The composer emits the non-empty layers in the fixed order base → mode → book → chapter,
   each as its own delimited section (`assistant-config.md` → "System-prompt composition").
2. `[test]` An empty, whitespace-only or absent layer contributes nothing — no section header, no
   separator and no blank block appear for it; composing with only base and book (this feature's
   only live case) produces exactly two sections; composing nothing produces an empty string
   (`assistant-config.md` → "An empty or absent prompt contributes nothing").
3. `[test]` `TOOL_REGISTRY` contains exactly one entry, named `web_search`, with a non-empty
   description and a Pydantic args schema whose field names are exactly the keyword parameters the
   callable accepts — the property the `llm` client validates with `inspect.signature`
   (`context.md` → tool callables).
4. `[test]` The definition builder produces OpenAI tool definitions carrying each tool's name,
   description and JSON schema, plus a name → callable map with an **identical key set**, so the
   client's pre-flight cannot raise `ValueError` (`assistant-config.md` → "Tool gating").
5. `[test]` A null mode resolves to the whole registry; an explicit allow-list resolves to just those
   tools; a name with no registry entry is skipped rather than raising (`context.md` → decision 9;
   the `013.codex` seam).
6. `[test]` With the HTTP boundary mocked to return results, `web_search` returns one string
   containing each result's title, snippet and link, and a distinct "no results" string when the
   response carries none (UC-087, US-101.AC-1).
7. `[test]` `web_search` resolves its api key and engine id through `$ENV_VAR` indirection and the
   resolved key never appears in the returned string (`backend/persistence.md` → credential policy).
8. `[test]` Every failure mode returns an error string rather than raising: env var unset, settings
   unconfigured, non-2xx response, transport failure, malformed payload — because a raising tool
   aborts the entire loop (`context.md` → the `llm` client constraints).
9. `[test]` No test in this step performs real network I/O — the `httpx` boundary is mocked
   (`backend.md` → test harness).
10. `[manual/live]` `cd backend && .venv/Scripts/python -m pytest` green.
11. `[manual/live]` One live search against a real Google Custom Search key/engine returns results
    through the tool (the only path a mocked boundary cannot prove).
