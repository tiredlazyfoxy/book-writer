# 002 — step context

Feature-wide facts (layer rules, the `llm` client's tool contract and option allowlist, the null-mode
decision, test harness, gates) are in `context.md`. Only what this step alone needs is below.

## Nothing web-search-shaped exists yet

Verified: **no MCP client, no search SDK, no outbound-HTTP helper and no search settings** anywhere
in the backend. `httpx` is declared in `pyproject.toml` but is used **only in tests** today — this
step is its first application use, and it needs no dependency change.

**`TOOL_REGISTRY` does not exist.** It is referenced *by name only* in the docstrings of
`models/mode_tool.py` and `models/subagent_tool.py`, which store a `tool_name` string rather than an
FK precisely because a tool is not a row. Those two tables stay untouched here — this step creates
the catalogue they will one day point at.

## The registries to mirror

`TABLE_REGISTRY` (`services/db_import_export.py`) and `VECTOR_SOURCE_REGISTRY` (`db/vector.py`) are
both **plain module-level literal lists of tuples**, with no decorator, no registration function and
no import-time side effects. `assistant-config.md` names them explicitly as the shape `TOOL_REGISTRY`
copies. The one difference: `ToolDef` has four named members, so a frozen dataclass reads better than
a 4-tuple — `services/authz.py`'s frozen `BookAccess` is the in-repo precedent for a frozen dataclass
in `services/`.

The catalogue is **never exported** — only *selections* persist (`assistant-config.md` →
"Persistence and registry obligations"). Do not add anything to `TABLE_REGISTRY`.

## Settings and secrets

`backend/app/settings.py`: `Settings(BaseSettings)` with
`model_config = SettingsConfigDict(env_file=".env.local", extra="ignore")`; existing fields are
`db_path` (alias `BOOKWRITER_DB_PATH`), `lancedb_dir`, `node_id` (alias `BOOKWRITER_NODE_ID`); the
accessor is `@lru_cache def get_settings()`. Follow the same `Field(default=...,
validation_alias="BOOKWRITER_...")` form.

Because `get_settings()` is `lru_cache`d, tests that need different setting values clear the cache —
`conftest.py`'s `http_client` fixture already calls `get_settings.cache_clear()`.

`services/secrets.py: resolve_env_ref(value: str | None) -> str | None` is **sync**: `$NAME` →
`os.environ[NAME]`, raising `LlmServerError(LlmServerErrorReason.env_not_set, ...)` when the variable
is unset. `services/llm_servers.py` imports it **function-locally** to keep the module graph acyclic;
follow that convention if an import cycle threatens, otherwise a normal module import is fine here
(`services/web_search.py` is a leaf).

That raise is the reason DoD-8 lists "env var unset" as an error-string case: `resolve_env_ref` will
raise inside the tool callable, and the tool must swallow it.

## The Google Custom Search JSON API

One `GET` against the Custom Search endpoint with the api key, the search-engine id (`cx`), the query
and an optional result count; results arrive under an `items` array whose entries carry a title, a
snippet and a link. An empty result set means the `items` key is **absent**, not an empty array —
treat a missing key as "no results", not as a malformed payload.

Two settings, two `$ENV_VAR` pointers, no credential ever inlined and none logged. The export
credential policy (`backend/persistence.md`) is the governing stance: `$ENV` pointers may travel,
literal secrets may not — these settings are not exported at all, but the same reasoning applies to
what may sit in `.env.local`.

## Prompt layers — what is actually populated in this feature

| Layer | Source | State in this feature |
|---|---|---|
| base | a module constant in `services/prompt_composition.py` | **always non-empty** |
| mode | `AssistantMode.system_prompt` | **always null** — no mode-bearing subject exists (`context.md` → decision 9) |
| book | `Book.system_prompt` | **always non-empty** — the column is a required, non-nullable `str` on the table |
| chapter | `Chapter.system_prompt` | **always absent** — the column exists and is nullable, but there is no chapter subject yet |

So the live case is exactly two sections. The composer must still implement all four positions and
the skip rule, because `013.codex` populates mode and the chapter features populate chapter, and the
ordering argument (`assistant-config.md` → "Why this order": chapter *narrows* book, so it must read
after it) is what the tests pin.

**This step does not read the database.** The composer takes strings; step 003 is what loads
`Book.system_prompt` and hands it in. Keeping it pure is what makes DoD-1/2 testable with no
fixtures.

**Wire-gap note:** `Book.system_prompt` and `active_notes` exist on the table but appear in
**neither** the backend books schema nor `frontend/src/types/books.d.ts` — a gap `010.working-page`
already recorded. Composition reads the table server-side, so this feature does **not** need the DTO
widened; the gap is re-raised in `outcome.md` rather than closed here.

## Tool-callable binding — the constraint that shapes `web_search`'s signature

Repeated here only as the concrete consequence for this module: the `llm` client applies decoded
JSON args as `func(**kwargs)` and validates them against `inspect.signature(func).parameters`. So
`web_search`'s parameters must be exactly `WebSearchArgs`' field names, and **there is no way to pass
per-request context** (book id, user, session) as an extra argument. `web_search` needs none today —
it is stateless. A future tool that does need context must be bound with a closure or
`functools.partial` default, and `ToolDef.callable` is typed loosely enough to accept that.

## What this step does not do

- No LLM call, no client construction, no streaming — all of that is step 003.
- No `mode_tool` / `subagent_tool` reads, no `AssistantMode` lookup, no sub-agent synthetic tools.
- No route, no DTO on the API surface, no `main.py` change — nothing here is reachable over HTTP.
- No second tool. `web_search` is the whole catalogue at this feature.
