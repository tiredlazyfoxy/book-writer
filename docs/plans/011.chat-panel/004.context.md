# 004 — step context

Feature-wide facts (MobX/observer rules, the api + types conventions, the "chat id is never in the
URL" rule, the list-lives-in-the-chat-pane resolution, test harness, gates) are in `context.md`. Only
what this step alone needs is below.

## Nothing chat-shaped exists on the frontend

Verified: **zero "chat" hits anywhere under `frontend/`** apart from 010's placeholder. There is no
chat DTO and no `api/chats.ts`; `src/types/` holds `common.d.ts` (`ApiErrorBody`, `ISODateString`),
`auth`, `admin`, `books`, `llmServers`, `db`, `health`. This step creates both from scratch, so there
is no legacy shape to stay compatible with — only the step-001 wire shapes.

## The patterns to copy verbatim

- **State + external loader:** `src/user/pages/bookshelfPageState.ts` — a `makeAutoObservable` class
  holding async trios and **no effectful methods**, plus external
  `async function load…(state, signal?)` that uses `runInAction`, returns early when
  `signal?.aborted`, converts `ApiError` to a message, and **rethrows anything else**.
- **Component mount:** `const [state] = useState(() => new StateClass());`
  `useEffect(() => { const ctrl = new AbortController(); void load(state, ctrl.signal); return () => ctrl.abort(); }, [state]);`
  Here that effect lives in `WorkspaceShell`, which already owns exactly this shape for the book
  load — extend it rather than adding a second mount effect anywhere.
- **Draft forms:** the `<Thing>Draft` pattern (`createBookDraft.ts` and friends) — observable fields,
  `serverErrors: Record<string, string>`, a `submitStatus`, **pure `get` computeds**
  (`clientErrors` / `errors` / `canSubmit`), and an external `submit…(draft, onDone, signal?)`.
  `@mantine/form` and `@mantine/hooks` are installed but **banned by convention** — do not reach for
  them.
- **Component-level state precedent:** `AdminShellState` is declared in the same `.tsx` as
  `AdminShell`. This step deviates: `ChatPaneState` gets its own file beside the component (it carries
  two async trios and its effect functions), matching the `<page>PageState.ts` convention that
  010's `workspaceShellState.ts` already follows.

**There is no precedent in the repo for sharing one state instance between two components.** This
step establishes it: the shell owns the instance and passes it explicitly to `ChatPane` (and a
handler to `WorkNavigator`). That is exactly what `frontend.md` → Components prescribes ("stores and
slices are passed explicitly down the tree", no React context) — it simply has not been needed
before. Recorded in `outcome.md`.

## The 010 surfaces this step edits

- `WorkNavigator.tsx` renders the seven entries as in-SPA router links using the frozen
  `WorkNavItem` shape, which already carries a **`paneTarget: "content" | "chat"`** discriminator with
  **Chats set to `"chat"`**. 010 froze that field for exactly this purpose; use it as the branch
  rather than matching on the label or the path.
- `WorkspaceShell.tsx` lays out the three regions with Mantine `AppShell` and already runs one
  mount-only `useEffect` that loads the book and aborts on unmount.
- `ChatPaneSlot.tsx` renders a notice naming `011.chat-panel` as the pane's owner — that notice is
  what this step removes.
- `routes.tsx` renders `/chats` via 010's `SubjectPlaceholderPage` with the owner label
  `011.chat-panel`; the placeholder component itself stays (five other routes use it) and only the
  `/chats` element changes.

## Why the navigator entry is a control, not a link

US-095.AC-1 and UC-081 step 1 both say "**the chat pane's list**", and US-105.AC-3 says a picked chat
opens in the chat pane. `frontend-workspace.md`'s route-map row for `/work/:bookId/chats` reads as
though the *list* renders in the content pane; its own navigator section says Chats "does **not**
render into the content pane". Product settles it in favour of the pane, so the list is pane-owned,
the entry is a control over pane state, and the route degrades to a redirect. The doc tension is
recorded in `outcome.md` — do not try to satisfy both readings.

Deriving the pane's list visibility from the URL instead was considered and rejected: it would need
either a prop-watching `useEffect` (banned) or an override flag that goes stale after the first pick.

## Mantine surface notes

- `ScrollArea` is used exactly once in the repo (`ModelsModal.tsx`, `ScrollArea.Autosize mah={360}`)
  and has **no theme defaults** — the chat list needs its own explicit height bound.
- `Textarea` is used exactly once (`CreateBookModal.tsx`, direct field assignment from JSX, no
  autosize). The composer is step 005's, not this step's.
- `frontend/theme.ts` sits at the frontend **root** (imported as `"../../theme"` from `src/*/…`),
  `primaryColor: "steel"`, dark warm neutrals.

## Testing this step

Specs mock `../../src/api/chats` in module-factory form, enumerating **every** export the subject
imports, then `vi.mocked(...).mockResolvedValue(...)`. `renderWithProviders` supplies the
`MantineProvider`; pass `route` when the subject needs a router (the navigator entry test does).
Routes in tests are **basename-stripped** — `/:bookId/chats`, not `/work/:bookId/chats`.
`localStorage` is cleared in `afterEach`, so pointer tests start from a clean store.

## What this step does not do

- **No messages, no streaming, no composer, no markdown** — the conversation region is a stub that
  step 005 fills, and `streamPost` is not called here.
- No sampling control other than `temperature`.
- No chat delete. Archive is the removal semantic.
- No change to the six content-pane navigator entries or to any other route.
