## The editability table — implement it exactly

From `frontend-workspace.md` → "Content pane — subject and editability":

| Subject | Editable? |
|---|---|
| The book's **`open`** chapter | editable (US-097.AC-3) |
| A chapter in **`closing`** | **read-only** — the owner is approving continuity for this exact body |
| Any `planned` or `closed` chapter | **read-only** (US-097.AC-1) |
| A codex entry, not archived | editable, per collaboration mode (US-079) |
| Book state | state notes editable (UC-050); everything else read-only |
| Any list | read-only |

Notes bounding it:

- The chapter states come from `domain-chapter.md`: `planned | open | closing | closed`, at most one
  `open` per book, and **`closing` and `closed` both refuse all writes to `text`** — from a member
  and from the assistant alike.
- The **collaboration-mode nuance** on codex entries (`free` vs `proposal`) is `013.codex`'s to apply;
  here a non-archived entry is editable and an archived one is not. Do not model proposal routing.
- Read-only reasons are author-facing strings: say *warning*, never *flag*, if a reason mentions one.

## Buffer design — from `frontend-workspace.md`

| Property | Decision |
|---|---|
| Storage | **`localStorage`**, not `sessionStorage` — it must survive a full reload |
| Scope | one buffer **per item**, keyed `(bookId, subjectKind, subjectId)` |
| Contents | the draft text, the `Chapter.version` (or codex entry `modified_at`) it forked from, and when it was written |
| Privacy | private to the author on that device; invisible to co-authors; never server-side |
| Status | never a substitute for saving |
| Quota | evict oldest-first and tell the author; **never** evict the current item's buffer |

Why the base version is recorded: `domain-chapter.md` → "Concurrency". `Chapter.version` bumps on
every applied change; a save carrying a stale `base_version` is refused with **409**; a version
mismatch on returning to a buffered draft is a **visible merge problem, never an auto-merge**. The
buffer records the forked-from version so the mismatch is detectable on return without an extra
round-trip. **The reconciliation/divergence view itself is not built here** — see `context.md`'s
deferral table and the recorded deviation from the doc's wording.

## The module tier

`src/auth.ts` is the precedent: exported key constants, plain functions, no class and no MobX, and it
is today the **sole** runtime `localStorage` consumer (`sessionStorage` is used nowhere in the repo).
Mirror that shape. `frontend.md` sanctions this as the one exception to "URL query params are the
persistence layer": draft content is large, private, and must not travel in a link.

**Do not** add the active-chat pointer here. `frontend-workspace.md` places it in the same module
tier, but its only consumer is the chat pane — it belongs to `011.chat-panel`.

## Routes added by this step

`chapters`, `chapter/:id`, `characters`, `locations`, `facts`, `codex/:id`, `variants`,
`variants/:chapterId`, `chats` — all children of the `/:bookId` shell route from 002, all rendering
the shared placeholder. **The chat id is never in the URL** (`frontend-workspace.md`): there is no
`chat/:id` route, and its absence is what makes US-105.AC-3 structurally true in this feature — the
chat pane resolves its own active chat per book.

Path-param routes remount per `frontend.md`'s rule; the shell above them does not (002's DoD-7).

## Why the empty states name features, not endpoints

`backend/app/routes/books.py` exposes only `POST /`, `GET /`, `GET /shared`, `GET /{book_id}`,
`GET /{book_id}/read`, archive/unarchive/transfer, member add/remove and visibility. There are **no**
chapter, codex, continuity, variants, chat or assistant routes anywhere in the backend — feature 008
landed tables and `db/` modules only. Every list here is therefore an empty state, and the owner
labels in the step file are fixed strings: all four name a roadmap folder, the variants one being
`018.chapter-history-variants` (`roadmap.md`, Stage 6 — FEAT-014's list/compare/apply surface). Use
the folder name, not the bare product id, and do not mint a number for a folder that does not exist.

## Test notes specific to this step

- `tests/setup.ts` runs `localStorage.clear()` in `afterEach` — buffer specs can rely on a clean store
  per case, and must not assume state carries across cases.
- The reload case (DoD-8) is a fresh module read of the same store, not a new store.
- The quota case (DoD-11) needs a `setItem` that throws a quota error for a bounded number of calls;
  how that is simulated is the test-coder's call.
- `subject.ts` and `restoreBuffer.ts` are pure modules — their specs need no router and no
  `renderWithProviders`; only `subjectRoutes.test.tsx` renders.
