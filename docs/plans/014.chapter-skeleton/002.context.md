# 002 — step context

Feature-wide facts (the wire contract, the status taxonomy, the layer rules, the authorization
matrix, D4/D5/D6) are in `context.md` and are not repeated here.

## `services/authz.py` — what exists today, and exactly what this step adds

Harvested, current:

- `AccessRole` = `owner` | `co_author` | `reader` | `none`.
- `Capability` holds exactly nine members: `read_book`, `view_book_detail`, `archive_book`,
  `transfer_ownership`, `add_member`, `remove_member`, `set_visibility`, `browse_codex`,
  `edit_codex_entry`. **No chapter member.**
- `_CAPABILITY_MATRIX: dict[Capability, frozenset[AccessRole]]`.
- `@dataclass(frozen=True) class BookAccess` — `book_id: int`, `user_id: int`, `role: AccessRole`,
  `book_state: BookState`, `visibility: Visibility`, `collaboration_mode: CollaborationMode`.
- `class BookAuthorizationError(Exception).__init__(capability, role)`.
- `async def resolve_book_access(book_id, user) -> BookAccess`;
  `async def book_access(book_id, user = Depends(auth_service.get_current_user)) -> BookAccess` (the
  FastAPI dependency, which raises `404` for a missing book and for a non-member of a private one);
  `def require(access, capability) -> None`.
- **Nothing resolves a chapter id to a book id**, and nothing in this feature adds such a thing (D4).

**This step adds four `Capability` members and four `_CAPABILITY_MATRIX` rows. It changes no existing
member, no existing row, and no existing function.** `BookAccess` gains no field.

### `read_book` is reused, unread and unedited

The two read paths (`list_chapters`, `get_chapter`) guard on the **existing** `Capability.read_book`.
`authorization.md`'s chapter matrix gives "Read chapter text" to owner, co-author and a reader on a
public book — which is precisely what `read_book` names — so minting a `list_chapters` capability
would duplicate a row that already exists.

**The harvest recorded that `read_book` exists but not which roles its matrix row admits.** Do not
widen it, do not narrow it, and do not assert its reader behaviour here: the reader-facing surface is
the Reader SPA (`/read`), which is out of scope for this feature. DoD-3 and DoD-12 are written against
members and non-members only, and DoD-13 asserts `can_reorder` for a reader without asserting whether
the reader reached the list at all. If `read_book` turns out **not** to be a member of
`_CAPABILITY_MATRIX` at all, that is a genuine blocker — stop and re-route rather than inventing a row.

## `authz.require` is the first line, always

`services/books.py`'s idiom, and it is load-bearing: the capability check runs **before any db read**.
Doing it the other way round would make a `404` and a `403` distinguishable by timing and by which
error surfaces first, and would leak whether a chapter id exists to a caller who is not allowed to
ask.

Consequence for DoD-12: a caller who *has* the capability but names a chapter from another book gets
**not-found**, because the capability check has already passed and the resolver is what refuses.
A caller who lacks the capability gets the authorization error regardless of whether the chapter id is
real.

## `Chapter`'s required-without-default columns

`ordinal` and `state` are declared **required with no default** on the model
(`backend/app/models/chapter.py`, unchanged by this feature). Every insert this service performs must
supply both explicitly — `state = planned` and the computed next ordinal. There is no model-level
fallback to fall back on.

`text` is required too: `add_chapter` supplies an empty string for it. That is the only thing this
feature ever writes into a chapter body, and it is an initialisation, not a write in the
`domain-chapter.md` sense — no `ChapterChange` row, no version bump.

`version` keeps its model default of 1 and is **never touched by this step**.

## Computing the next ordinal

Derive it from the book's current chapters (`db/chapters.list_by_book`), not from a count: a book
whose middle chapter was removed has fewer chapters than its highest ordinal, and a count would
collide. "Next ordinal after the current highest" is the rule; an empty book yields 1.

**Removal deliberately leaves a gap.** Ordinals are not renumbered on delete — only `reorder_chapters`
rewrites them, and it rewrites all of them to `1..N`. Renumbering on delete would silently move every
later chapter for an operation the author framed as removing one, and `list_chapters` orders by
ordinal ascending, so a gap is invisible to every reader. DoD-2 must therefore be written against
"next after the highest", not "count + 1".

## The reorder transaction

`context.md` → D3 says the server "rewrites ordinals 1..N in one transaction". `db/chapters.py`
exposes only a per-row `update` (step 001), which commits per call. **Validate the whole submitted
list first, then write** — DoD-10 asserts that an invalid list changes *no* ordinal, and validating
up front is what makes that true without a transaction spanning the db module. Do not add a bulk
writer to `db/` to get a single commit; that would move the `1..N` rule out of the service.

A transient state in which some ordinals are rewritten and some are not is possible only if a write
fails mid-loop, which is the same exposure every other multi-row service operation in this codebase
already has. It is not worth a new `db/` primitive here.

## Collaboration mode does not apply

`BookAccess` carries `collaboration_mode`, and several rows in `authorization.md`'s matrix are marked
*(mode)* — a co-author's write is held as a proposal in `proposal` mode. **None of the chapter
skeleton rows are marked that way.** Adding a chapter, editing a sketch, removing a planned chapter
and reordering are all immediate. Do not add a mode check and do not copy `services/codex.py`'s
proposal refusal.

## Testing

Construct `BookAccess` instances directly — it is a frozen dataclass and needs no HTTP. Seed users,
books, memberships and chapters through the sibling `db/` modules with the `db` fixture, as the
existing `backend/tests/services/` specs do. No route, no client, no JWT at this layer — those are
step 003's.

DoD-11 needs a chapter forced into `open` state; write it directly through `db/chapters.py` (this
feature ships no open transition — that is `015`'s).
