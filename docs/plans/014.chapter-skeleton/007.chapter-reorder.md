# 007 — Reordering the skeleton: move buttons and drag-and-drop

## Goal

Let the book's owner set the chapter order from the working page, through ↑/↓ move buttons **and**
drag-and-drop, both driving the same bulk order `PUT`, with the co-author refusal surfaced when the
server says no.

## Interface intent

**`frontend/package.json`** — add `@dnd-kit/core` and `@dnd-kit/sortable` to the dependency set.
`package-lock.json` is **regenerated by `npm install`, never hand-edited**; it is listed only so the
coder is in scope to commit it.

**`frontend/src/work/pages/chaptersPageState.ts`** — additions only; the list trio, the add-form state
and the remove state from step 006 are untouched.

- A **reorder status and a reorder error holder**, so a refused reorder is surfaced separately from a
  refused add or remove.
- A **pending order**: the chapter-id sequence the author is currently arranging. It is what the list
  renders while a reorder is in flight, and it is **discarded and re-seeded from the server** on both
  success and failure — the server is the source of truth, and a failed `PUT` must snap the list back
  to the order the server still holds.
- Pure `get` computeds: whether the caller may reorder (already present from step 006, read off the
  list envelope's `can_reorder`); whether a given chapter can move up, and whether it can move down
  (false at the ends).
- **External effect functions** `(state, bookId, …, signal?)` using `runInAction`:
  - **move one chapter one position up or down** — computes the new full id sequence locally, then
    calls the single persist function below. There is no separate endpoint for a move.
  - **apply an arbitrary new order** — takes the full ordered id list (what the drag handler produces),
    calls the api's reorder function, and re-seeds the list from what the server returned. On an
    `ApiError` it stores the server's message in the reorder error holder and re-seeds from a fresh
    load, so the rendered order matches the server's again.

**`frontend/src/work/components/chapters/ChapterOrderList.tsx`** (new) — an `observer` component
taking the page state and rendering the ordered chapter rows. It is the single rendering site for a
chapter row in this page, so the two affordances cannot diverge:

- **↑ and ↓ controls per row**, each with an accessible name naming the chapter and the direction,
  disabled at the ends of the list and while a reorder is in flight;
- **a drag affordance** on each row, using `@dnd-kit/core`'s drag context plus `@dnd-kit/sortable`'s
  sortable list, whose drag-end handler produces the new full id sequence and calls the same apply
  effect the buttons call;
- the row content step 006 already renders — title, ordinal, state badge, link, remove control —
  moved here rather than duplicated.

When the caller may not reorder, **the move controls and the drag affordance are absent** and the rows
render as a plain ordered list. This mirrors the server's answer; it does not replace it.

**`frontend/src/work/pages/ChaptersPage.tsx`** — render `ChapterOrderList` in place of the inline row
rendering, and surface the reorder error. Nothing else about the page changes.

## Definition of done

1. `[test]` As the owner, moving a chapter **down** with its ↓ control sends the **full** ordered id
   list with that chapter one position later, and the rendered order afterwards is the order the
   server returned — **US-033.AC-1**.
2. `[test]` As the owner, moving a chapter **up** with its ↑ control does the mirror image, and the
   list order it sends is the complete current set, never a partial one.
3. `[test]` The ↑ control is unavailable on the first chapter and the ↓ control on the last; a
   one-chapter book offers neither.
4. `[test]` When the caller may not reorder — the list envelope says so — **no move control and no
   drag affordance is rendered**, while the rest of the list renders normally — **US-033.AC-2**,
   client affordance.
5. `[test]` When the server refuses a reorder, the refusal is surfaced to the author and the rendered
   order **returns to the server's** order rather than keeping the attempted one — **US-033.AC-2**,
   server authority.
6. `[test]` Both affordances call **one** persist path: the api's reorder function is the only chapter
   write a move triggers, and it is called once per move, with the whole ordered id list.
7. `[test]` Move controls are disabled while a reorder is in flight, so a second move cannot race the
   first.
8. `[test]` A reorder failure does not disturb the add form's drafts or the per-chapter removal
   messages — the three error surfaces are independent.
9. `[test]` The rows still carry everything step 006 rendered — title, state, chapter link, and the
   remove control on a `planned` chapter — after the move to `ChapterOrderList`.
10. `[manual/live]` Dragging a chapter row to a new position reorders the list and persists the same
    full ordered id list the buttons send; the drag affordance is absent for a caller who may not
    reorder. *(Not automated: `@dnd-kit`'s pointer-sensor interaction is not reliably drivable in
    jsdom, and `context.md` → D3 fixes the buttons as the tested path.)*
11. `[manual/live]` `cd frontend && npm run build`, `cd frontend && npm test` and
    `cd frontend && npm run test:types` all pass with the two new dependencies installed.
