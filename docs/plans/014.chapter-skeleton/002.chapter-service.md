# 002 — Chapter DTOs, the chapter service, and the four chapter capabilities

## Goal

Add the chapter request/response DTOs, the service that lists, reads, appends, re-sketches, removes
and reorders a book's chapters, and the four `Capability` members that put an enum behind
`authorization.md`'s existing chapter matrix rows.

## Source files

```
backend/app/models/schemas/chapters.py
backend/app/services/chapters.py
backend/app/services/authz.py
```

## Test files

```
backend/tests/services/test_chapters.py
```

## Interface intent

**`backend/app/models/schemas/chapters.py`** (new) — five Pydantic DTOs, declarative, no logic. Field
sets are fixed by `context.md` → "The wire contract" and are not restated here.

- **`CreateChapterRequest`** — a title and a sketch. The title carries a **non-blank** constraint
  expressed declaratively on the field so the framework answers `422`; the sketch has none, because
  an empty sketch is a legitimate starting state.
- **`UpdateChapterSketchRequest`** — a sketch only.
- **`ReorderChaptersRequest`** — the full ordered list of chapter ids, as **strings**.
- **`ChapterResponse`** — the chapter's identity, position, title, state, sketch, version and
  timestamps. Ids are strings. **No body text, no summary, no summary status** — `context.md` gives
  the reason.
- **`ChapterListResponse`** — the ordered chapter responses plus the caller-relative `can_reorder`
  hint.

**`backend/app/services/authz.py`** — four new `Capability` members and their four
`_CAPABILITY_MATRIX` rows, and nothing else:

| Capability | Roles |
|---|---|
| add a chapter | owner, co-author |
| edit a planned chapter's sketch | owner, co-author |
| remove a planned chapter | owner, co-author |
| **set chapter order** | **owner only** |

**No chapter→book resolver, no `chapter_access` dependency, no new `BookAccess` field, no capability
for the chapter prompt** — `context.md` → D4 and the authorization section. The existing `read_book`
capability is reused unchanged for the two read paths; **do not edit its matrix row.**

**`backend/app/services/chapters.py`** (new) — business logic and the chapter half's whole decision
surface.

- **A reason enum plus one exception class** carrying `(reason, message)`, following
  `services/books.py`'s typed-error shape. It needs exactly **three** reasons: the chapter is not
  found (missing, or belonging to another book); the chapter is not in the `planned` state; the
  submitted reorder list is not exactly the book's current chapter set. Do not invent more — every
  other refusal on these paths is either an `authz` capability failure or is produced upstream by the
  `book_access` dependency.
- **A private response mapper** — the single place a chapter row becomes a `ChapterResponse`, so no
  entry point can drift. It is also the single place a snowflake becomes a string.
- **A private chapter resolver** — given the access context and a chapter id, load the row and raise
  the not-found reason when it is missing **or when its `book_id` does not match `access.book_id`**.
  Every entry point that names a chapter goes through it. This is what replaces a `chapter_access`
  dependency (D4).
- **`list_chapters`** — requires the existing read capability, returns the book's chapters ordered by
  ordinal ascending, and sets `can_reorder` from whether the caller's role is the owner's.
- **`get_chapter`** — requires the existing read capability, resolves one chapter, maps it.
- **`add_chapter`** — requires the add capability, then **appends**: the new chapter takes the next
  ordinal after the book's current highest (the first chapter in an empty book takes ordinal 1), state
  `planned`, the submitted title and sketch, an empty body, version at its model default, and both
  timestamps stamped by this layer. Returns the stored chapter's response. (UC-031, US-032.AC-1.)
- **`update_sketch`** — requires the sketch capability, resolves the chapter, refuses with the
  not-planned reason when its state is anything but `planned`, then writes the new sketch and stamps
  `modified_at`. **It does not bump `version`** and takes no version token — D6. Returns the stored
  response.
- **`remove_chapter`** — requires the remove capability, resolves the chapter, refuses with the
  not-planned reason when its state is anything but `planned`, then deletes it. Returns nothing.
- **`reorder_chapters`** — requires the **owner-only** order capability, loads the book's current
  chapters, and **validates that the submitted id list is exactly that set** — same length, no
  duplicates, no unknown or foreign ids, nothing missing — raising the invalid-set reason otherwise
  **before any write happens**. Then rewrites every chapter's ordinal to its 1-based position in the
  submitted list and returns the freshly ordered list response. It touches `ordinal` and
  `modified_at` only: no state, no body, no version (D5).

The service never receives a book id as an argument — it comes from the access context, so no entry
point can be aimed at a book the caller was not resolved against.

## Definition of done

1. `[test]` `add_chapter` creates a chapter in the **`planned`** state carrying the submitted sketch,
   and a following `list_chapters` includes it — **US-032.AC-1**.
2. `[test]` `add_chapter` **appends**: the first chapter of an empty book takes ordinal 1, and each
   further chapter takes the next ordinal after the current highest, whatever order they were created
   in — **UC-031**.
3. `[test]` A **co-author** may `add_chapter`, `update_sketch` and `remove_chapter`; a `reader` and a
   caller with no relationship are refused on all three by the authorization error.
4. `[test]` `update_sketch` on a `planned` chapter stores the new sketch — **US-034.AC-1** — and
   leaves `version` unchanged, taking no version token; two sequential edits both succeed and the last
   one wins (D6).
5. `[test]` `update_sketch` on a chapter in `open`, `closing` or `closed` is refused with the
   not-planned reason and stores nothing — **US-034.AC-2**.
6. `[test]` `remove_chapter` on a `planned` chapter removes it, and it no longer appears in
   `list_chapters` — **US-035.AC-1**.
7. `[test]` `remove_chapter` on a chapter in `open`, `closing` or `closed` is refused with the
   not-planned reason and the chapter still exists — **US-035.AC-2**.
8. `[test]` `reorder_chapters` rewrites ordinals to `1..N` in the submitted order, and a following
   `list_chapters` returns the chapters in that order — **US-033.AC-1**.
9. `[test]` A **co-author** calling `reorder_chapters` is refused by the authorization error, and the
   ordinals are unchanged — **US-033.AC-2**.
10. `[test]` `reorder_chapters` refuses with the invalid-set reason, and changes **no** ordinal, when
    the submitted list omits a chapter, adds an unknown id, repeats an id, or names a chapter
    belonging to another book.
11. `[test]` `reorder_chapters` succeeds while one of the book's chapters is `open`, and that
    chapter's state, body and version are unchanged afterwards — D5's closure of UC-032's `_TBD`.
12. `[test]` Every entry point that names a chapter — read, sketch edit, remove — treats a chapter
    whose `book_id` differs from the access context's book as **not found**, not as a permission
    failure.
13. `[test]` `list_chapters` returns chapters ordered by ordinal ascending, and `can_reorder` is true
    for the owner and false for a co-author and for a reader.
14. `[test]` Every response carries its ids as strings and exposes no body text, summary or summary
    status; no ORM object reaches a caller of the service.
