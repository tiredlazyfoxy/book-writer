# 001 — step context

Feature-wide facts (decision D1's column list, the layer rules, the additive-schema rule, the codec
obligation, the test harness) are in `context.md` and are not repeated here.

## `backend/app/models/chapter.py` is already complete — do not touch it

Harvested, current. `Chapter` (`__tablename__ = "chapters"`) already declares: `id` (snowflake PK via
`generate_id`), `book_id` FK → `books.id`, `ordinal: int` (**required, no default**), `title: str`,
`state: ChapterState` (**required, no default**), `sketch: str` (required), `text: str` (required),
`summary: str | None`, `summary_status: SummaryStatus | None`, `system_prompt: str | None`,
`version: int = 1`, `created_at` / `modified_at: datetime | None`. The file also defines
`ChapterState(str, enum.Enum)` = `planned|open|closing|closed` and `SummaryStatus` =
`draft|approved|stale`.

**No schema change is needed for the skeleton half**, and `backend/app/models/chapter.py` is
deliberately **not** in this step's source list. In particular:

- `ordinal` and `state` being required with no default means every insert must supply both — that is
  step 002's service, not this step's.
- `Chapter.system_prompt` stays exactly as it is. Its in-code docstring says it appends to the book's,
  which feature `021` already flagged as stale and did not edit. **This feature does not edit it
  either** — the file is out of scope, and `outcome.md` records that the flag is still open.

## `db/chapters.py` as it stands

Only three functions: `create(row) -> Chapter`, `get_by_id(chapter_id) -> Chapter | None`,
`list_by_book(book_id) -> list[Chapter]`. There is no `update` and no `delete`.

The two idioms to copy, named exactly:

- **`backend/app/db/books.py` → `update(row: Book) -> None`** — `session.add(row)`, commit, refresh.
  That is the whole body; do not add a read-back, a timestamp, or a not-found branch.
- **`backend/app/db/book_members.py` → `delete(...) -> bool`** — the boolean-returning delete shape,
  including how it answers when nothing matched.

Whether `chapters.update` returns the row or nothing is the **skeleton agent's** call from the
`books.py` precedent; the plan fixes only that the stored state is what a following `get_by_id`
returns (DoD-9).

## The sibling to mirror, file for file

Feature `021` shipped the exact same quartet one level up. For this step the two files to read side by
side are `backend/app/models/book_author_prompt.py` and `backend/app/db/book_author_prompts.py`
(`create` / `get_by_book_and_user` / `update`). Substituting `chapter_id` for `book_id` throughout is
the whole difference.

## `TABLE_REGISTRY` — the position and why

`RegistryEntry = tuple[str, type[SQLModel], encoder, decoder]`; `TABLE_REGISTRY: list[RegistryEntry]`
is ordered by **FK dependency (import) order**.

`chapters` **already has a codec pair** — `_chapter_to_dict` / `_dict_to_chapter`, registered as
`("chapters", Chapter, …)`. Only the new prompt table needs one. It goes **immediately after the
`book_author_prompts` entry** (index 9-ish), because it references `chapters` and `users`, both
already earlier, and because keeping the two per-author-prompt tables adjacent is where a reader will
look for the second one.

DoD-8 asserts the ordering relative to `book_author_prompts` rather than an absolute index, so a
future insertion elsewhere in the list cannot make it fail for the wrong reason.

## Timestamps are not this layer's

The `db/` module persists the row it is handed and sets nothing. `create` does **not** stamp
`created_at`; `update` does **not** stamp `modified_at`. Step 004's service owns both. DoD-5 asserts
that `update` reflects **stored** state, which would pass for the wrong reason if the db layer were
quietly stamping rows.

## Testing

`backend/tests/db/test_chapters.py` does not exist and is created here; the same is true of both other
listed specs. Seed supporting rows (users, books, chapters) through the sibling `db/` modules with the
`db` fixture, as the existing `backend/tests/db/` specs do — no HTTP and no JWT at this layer.

DoD-3's unique-constraint assertion needs the database to raise; do not assert it by pre-reading and
branching, which would test the test rather than the constraint.

DoD-6 needs a database initialised through the ordinary `init_db()` path — not a hand-built
`create_all` over a hand-picked metadata subset, which would pass even if the registration seam were
never edited.
