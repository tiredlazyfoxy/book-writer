## `CodexListPage` is the list-page model

Copy its shape for: the mount `useEffect` and abort, the trio branches, and the
`registerContentSubject(source, applyDraft?)` / `unregisterContentSubject(source)` pair from
`frontend/src/work/contentSubject.ts`. A list subject registers **no `applyDraft`** — the pane model
already treats "Any list" as read-only (`frontend-workspace.md` → content-pane editability), and the
add/remove controls are page chrome, not a canvas region a shared-canvas write could target.

`contentSubject.ts` itself is **not** in this step's source list — this step calls it, it does not
change it. The same is true of `frontend/src/work/subject.ts`, whose `"chapters"` `SubjectKind`
member and `resolveSubjectPaneTarget` behaviour already exist and are correct for a list.

## Why the removal affordance is computed and the refusal is still surfaced

DoD-8 and DoD-9 look redundant and are not. `authorization.md` puts enforcement in the service, and
the chapter state machine is enforced on the server with `409` (`context.md` → status taxonomy). The
client-side "only a `planned` chapter shows a remove control" is an affordance that keeps the author
from aiming at something that cannot work; the server refusal is what makes **US-035.AC-2** true even
if the client's copy of the state is stale — which it will be, because a co-author can open a chapter
from another session between this page's load and the click.

The same split applies to the message placement: a page-level error banner would leave the author
guessing which chapter it concerned when a list is long.

## No optimistic mutation

`bookStatePageState.ts` and `bookSettingsPageState.ts` both re-seed from the server after a write and
mutate nothing optimistically. Follow that. DoD-3 asserts the rendered chapter came from the server
response, which an optimistic splice would satisfy for the wrong reason.

## The add form is the one form here with client validation

`context.md` records that this feature's prompt and sketch editors carry `…ServerErrors` with **no
`clientErrors` and no `errors` union**, per `021`'s observation. The **add form is different**: the
title must not be blank, so it has a real client rule and therefore a `clientErrors`-style computed
and a combined `canSubmit`. DoD-5 pins the whitespace-only case, which a bare truthiness check would
let through and which the server would then answer with a `422` the author cannot act on.

The sketch field has no client rule — an empty sketch is a legitimate starting state and the backend
accepts it (step 003's DoD-3).

## Step 007 edits two of these three files immediately afterwards

`chaptersPageState.ts` and `ChaptersPage.tsx` are extended by step 007 with the reorder controls. Two

- Leave the `can_reorder` value **read but unused** here (the computed exists; nothing renders off it

- Render the chapter rows through a structure that a sortable list can wrap later. Do not design the

## Testing

`frontend/tests/work/ChaptersPage.test.tsx` is created from scratch.
`frontend/tests/work/BookStatePage.test.tsx` is the reference for the module-factory api mock — the
factory must enumerate **every** export the page imports from `../../src/api/chapters`, including the
ones this step does not call, or the mock strips them and a later step's page fails for the wrong
reason.

`ApiError` is imported real from `../../src/api/client`; DoD-6 and DoD-9 both need a real one so the
message surfaces the way it will in production.

Queries are by **role or label only**. The state badge and the remove control must therefore be
reachable by accessible name — a remove control that is an unlabelled icon button is untestable here
and must carry an accessible label naming the chapter.
