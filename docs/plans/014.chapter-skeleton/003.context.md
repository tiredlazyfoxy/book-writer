# 003 — step context

Feature-wide facts (the endpoint list, the status taxonomy, the route/service error idiom, the layer
rules, the test harness) are in `context.md` and are not repeated here.

## The route module to copy, and the one to place beside

`backend/app/routes/books.py` is the shape: a `_*_ERROR_STATUS: dict[Reason, int]` at module scope, a
`_map_*_error(err) -> HTTPException` helper, and handlers that wrap their single service call in
`try/except authz.BookAuthorizationError → _map_authz_error` then `except <Domain>Error →
_map_*_error`. Copy that verbatim in shape; only the reason set differs.

`backend/app/routes/book_author_prompts.py` is the placement precedent — a book-scoped **sub-resource**
router with its own `/api/books/{book_id}/…` prefix rather than handlers bolted onto `routes/books.py`.
This family follows it.

## `main.py`'s current `include_router` sequence

Harvested, in order: `health, auth, books, chats, codex, book_author_prompts, admin_users,
admin_llm_servers, admin_db, admin_assistant_config`.

Mount `chapters` **among the book-scoped sub-resources** — after `books`, alongside `chats`, `codex`
and `book_author_prompts`, and before the `admin_*` group. FastAPI matches on full paths, so ordering
here is a readability rule, not a correctness one; put it where the next reader will look for it.

Step 004 also edits `main.py`, to mount the prompt router. The two steps run in sequence, so there is
no conflict, but do not pre-emptively add step 004's router here.

## Route declaration order inside the module *is* a correctness rule

`/order` is a literal segment sitting where `/{chapter_id}` also matches. FastAPI resolves routes in
declaration order, so `PUT /order` must be declared **before** any `PUT`/`PATCH`/`DELETE` on
`/{chapter_id}`. There is no `PUT /{chapter_id}` in this family, so the collision is latent rather
than live today — declare the literal first anyway, because the next feature to add a chapter `PUT`
will otherwise break the reorder path silently. DoD-16 pins it.

## Status codes that are decisions, not conventions

- **`409`** for a chapter that is not `planned` — `context.md` carries the reasoning. Do not reach for
  `403`; the caller has the capability.
- **`400`** for a reorder list that is not the book's chapter set. Not `422`: the body is
  *structurally* valid (a list of id strings) and the framework will accept it; what fails is a
  cross-row invariant only the service can check. `422` here would be a lie about where validation
  happened.
- **`201`** on create, **`204`** on delete. Everything else is `200`.
- **`404` for another book's chapter.** Produced by the service's own resolver, not by the
  `book_access` dependency — the dependency only ever sees `{book_id}`.

## The `403` on a public book, and the `404` on a private one

Both come from upstream and are **not re-derived here**:

- A private book the caller has no relationship to → the `book_access` dependency raises `404` before
  any handler body runs (existence hiding, `authorization.md` → "Failure modes").
- A logged-in non-member of a **public** book resolves to the `reader` role, reaches the service, and
  is refused by `authz.require` with the authorization error, which the shared mapper turns into
  `403`.

DoD-11, DoD-12 and DoD-13 need a **public** book, a **private** book, and no token respectively — three
distinct fixtures, and conflating them makes the assertions meaningless.

## Testing

`backend/tests/routes/test_chapters.py` does not exist and is created here.
`backend/tests/routes/test_book_settings.py` is the model for the seeding helpers — copy `_now`,
`_auth_header`, `_seed_user`, `_seed_author`, `_create_book`, `_add_co_author` per-file rather than
importing them; they are deliberately not shared fixtures.

**Auth is real** — seed a user row and mint a real JWT. `http_client` drives the real app lifespan
over `httpx.ASGITransport`, so the whole request path including the dependency runs.

This feature ships no state transition, so a spec needing an `open` or `closed` chapter writes the
state directly through `backend/app/db/chapters.py` with the `db` fixture before exercising the route.
DoD-5 and DoD-7 both need that.

DoD-14 needs **two** books with the caller as a member of both, so the refusal is provably the
book-scoping check and not an authorization failure.
