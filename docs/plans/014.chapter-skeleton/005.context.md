# 005 — step context

Feature-wide facts (the wire contract, the endpoint list, the MobX rules, the envelope-not-unwrapped
decision, the frontend test harness, the build gates) are in `context.md` and are not repeated here.

## The Shell has no book-hub route today

Harvested, current — `frontend/src/user/routes.tsx` declares exactly three routes:

- `/` → `BookshelfPage`
- `/health`
- `/books/:bookId/settings` → `BookSettingsPage`, `key={bookId}`

**There is no `/books/:bookId` route and no `BookHubPage`.** Both are created here. Follow the
settings route's `key={bookId}` pattern so the page remounts on a book change (DoD-6), and place the
new route so that it does not shadow the more specific settings path.

## This step is at the top of the size budget

Five source files, one of which is a `.d.ts`. Keep `BookHubPage.tsx` lean: it renders a heading, a
list, badges, two error branches, an empty state and two links, and **nothing else**. Anything not
named in a DoD item is out of scope. The api module and the DTOs are the reason this step is bigger
than the page it ships — steps 006, 007 and 008 all consume them unchanged, so they are proved once,
here, by the first surface that reads them.

## `api/codex.ts` is the precedent, with one deliberate departure

Harvested shape: `listCodexEntries(bookId, kind, needle?, includeArchived?, signal?)`,
`getCodexEntry(bookId, entryId, signal?)`, `createCodexEntry(bookId, body, signal?)`,
`updateCodexEntry(bookId, entryId, body, signal?)` — book id first, `signal?` trailing, and **the list
envelope unwrapped inside the api module**.

Copy all of that **except the unwrapping**. `context.md` fixes why: the chapter list envelope carries
`can_reorder`, and steps 006 and 007 need it. DoD-8 pins it so a later "tidy-up" cannot reintroduce
the unwrap.

`api/books.ts` is the naming precedent for the prompt pair — it already exports
`getOwnSystemPrompt(bookId, signal?)` / `updateOwnSystemPrompt(bookId, body, signal?)`. Name the
chapter pair the same way, one level down.

## The book-detail read function already exists

`bookSettingsPageState.ts` is a plain async trio — `detail` / `detailStatus` / `detailError` — plus
external effects shaped `(state, bookId, [body,] signal?)` that call the `booksApi.*` module. The
hub reuses **that same read function**. The harvest did not record its exact name; the skeleton agent
binds it. **Do not add a new function to `api/books.ts`** — `api/books.ts` is not in this step's
source list.

## `types/chapters.d.ts` does not exist

`frontend/src/types/` currently holds `common.d.ts`, `health.d.ts`, `auth.d.ts`, `admin.d.ts`,
`llmServers.d.ts`, `db.d.ts`, `assistantConfig.d.ts`, `codex.d.ts`, `chats.d.ts`, `books.d.ts`.

`books.d.ts` holds the two shapes to mirror one level down:

```
BookAuthorPromptResponse   { book_id: string; system_prompt: string; modified_at: ISODateString | null }
UpdateBookAuthorPromptRequest { system_prompt: string }
```

The chapter equivalents are the same with `chapter_id` in place of `book_id`. Reuse
`common.d.ts`'s ISO-timestamp alias rather than declaring a second one.

## The `ChapterState` name collision

`frontend/src/work/subject.ts` already declares
`ChapterState = "planned" | "open" | "closing" | "closed"` alongside `SubjectKind`, `LoadedSubject`,
`EditableRegion`, `Editability`, `WriteRegion` and `WriteDecision`.

That file is **entry-local to `work/`** and is not touched by this step (step 008 amends it, and only
`resolveEditability`). Declaring a second, identically-named type at shared `src/` root is legal but
would make two imports of the same name mean two different things. The plan requires only that the
wire union carries the four values and does not collide; the exact name is the skeleton agent's.

Do **not** resolve this by having `work/subject.ts` import from `types/chapters.d.ts` — that couples
the pane model to the wire, and the pane model is allowed to diverge from it (step 008 does not change
the value set, but `016` and `018` may).

## `frontend/tests/user/` and the mocking idiom

Both listed specs are created from scratch — there is no `BookHubPage` today, and no
`api/chapters.ts`.

`frontend/tests/work/BookStatePage.test.tsx` is the working reference for the module-factory api mock.
For the hub, the factory must enumerate **every** export the page imports from **both**
`../../src/api/chapters` and `../../src/api/books` — a missing export makes the page fail to render
for the wrong reason.

`frontend/tests/user/chaptersApi.test.ts` tests the api module itself (DoD-7, DoD-8, DoD-9), so it
mocks the shared `request<T>` wrapper in `../../src/api/client` rather than the chapters module, and
asserts the path, method and forwarded signal. `ApiError` is imported real from the same module
wherever a failure branch is needed.

`renderWithProviders(ui, { route? })` from `frontend/tests/support/render.tsx` supplies
`MantineProvider theme env="test"` + `MemoryRouter`; wrap it in a local `renderPage(route)` with a
`<Routes><Route path="/books/:bookId" …/></Routes>` shim so the page receives a real path param
(DoD-6 needs to change it).

Queries are by **role or label only** — no test-ids. A "state badge" must therefore be readable text,
not a colour.
