# 006 — The working page's chapter list: add and remove

## Goal

Replace the `/work/:bookId/chapters` placeholder with a real chapter list that appends a chapter with
a sketch and removes a planned one, surfacing the server's refusal when a chapter is not `planned`.

## Source files

```
frontend/src/work/pages/chaptersPageState.ts
frontend/src/work/pages/ChaptersPage.tsx
frontend/src/work/routes.tsx
```

## Test files

```
frontend/tests/work/ChaptersPage.test.tsx
```

## Interface intent

**`frontend/src/work/pages/chaptersPageState.ts`** (new) — a `ChaptersPageState` class plus its
external effect functions, following `bookStatePageState.ts`'s grain.

- An **async trio** for the chapter list, holding the whole envelope so `can_reorder` is available to
  step 007 without a second load.
- A pure `get` computed exposing the chapters in ordinal order for rendering, and one exposing
  whether the caller may reorder (read straight off the envelope; **step 007** is what consumes it).
- **Add-form state**: a title draft, a sketch draft, a `…ServerErrors` map, and a submit status.
  Because the title has a real client rule — it must not be blank — this one form *does* carry a
  client-validation computed alongside the server-error map, and a `canSubmit` computed combining
  them. This is the exception to `context.md`'s note that the prompt/sketch editors have no
  client-validation layer.
- **Remove state**: which chapter id is being removed, and a place for the server's refusal message so
  it can be shown against that chapter rather than at the top of the page.
- A pure `get` computed telling the view whether a given chapter may be removed at all — true only for
  a `planned` chapter. This drives the affordance; it never substitutes for the server's answer.
- **External effect functions** `(state, bookId, …, signal?)`, all using `runInAction`:
  - **load** the chapter list;
  - **add** a chapter from the drafts, then **re-seed the list from the server** (the create response
    plus a reload, or the reload alone — the server is the source of truth, never an optimistic
    splice), and clear the drafts on success only;
  - **remove** a chapter, then re-seed the list the same way; on an `ApiError` it stores the server's
    message against that chapter and **leaves the list untouched**.

**`frontend/src/work/pages/ChaptersPage.tsx`** (new) — an `observer` page component holding a
`ChaptersPageState` in `useState` and one mount `useEffect` that loads and aborts on unmount.

It renders: the trio's loading and error branches; the chapters in ordinal order with title, ordinal
and a readable state badge, each linking to `/work/:bookId/chapter/:id`; an empty state; an
**add-chapter form** with a title field, a multi-line sketch field, a submit control gated on the
computed, and a server-error surface; and a **remove control per chapter**, present only for a
`planned` chapter, with the server's refusal message rendered beside the chapter it belongs to.

The page **registers itself as the content-pane subject on mount and unregisters on unmount**, through
the existing `contentSubject` module, following `CodexListPage`'s registration. A list subject is
read-only in the pane model — the add and remove controls are page chrome, not a writable canvas
region — so it registers **no draft applier**.

Handlers are inner functions closing over the state; no extracted callbacks, no hooks beyond the one
`useState` and the one page-level `useEffect`.

**`frontend/src/work/routes.tsx`** — swap the `chapters` child route from the
`SubjectPlaceholderPage` (currently `heading="Chapters" owner="014.chapter-skeleton"`) to
`ChaptersPage`. **Only that one line changes**; the `chapter/:id` placeholder stays until step 008,
and every other child route is untouched.

**No navigator change is needed** — the Chapters entry already exists in
`frontend/src/work/components/shell/navItems.ts` with `extraActiveSegments: ["/chapter"]`, and
`WorkNavigator` is a pure render off it. `navItems.ts` and `WorkNavigator.tsx` are deliberately **not**
in this step's source list.

## Definition of done

1. `[test]` On mount the page loads the book's chapters and renders them in ordinal order, each with
   its state readable.
2. `[test]` A book with no chapters renders an empty state and a usable add form, not an error.
3. `[test]` Submitting the add form with a title and a sketch calls the create function with exactly
   those values, and the chapter then shown comes from the **server**, in the `planned` state, carrying
   the submitted sketch — **US-032.AC-1**.
4. `[test]` A newly added chapter appears **last** in the rendered order — **UC-031**.
5. `[test]` The submit control is unavailable while the title is blank and while a submit is in
   flight; a whitespace-only title does not count as filled.
6. `[test]` A refused add surfaces the server's message and **leaves both drafts intact** so nothing
   typed is lost; the drafts clear only on success.
7. `[test]` Removing a `planned` chapter calls the remove function and the chapter is gone from the
   rendered list afterwards — **US-035.AC-1**.
8. `[test]` A chapter that is `open`, `closing` or `closed` offers **no** remove control —
   **US-035.AC-2**, client affordance.
9. `[test]` When the server refuses a removal, the message is surfaced **beside the chapter it
   concerns** and that chapter stays in the list — **US-035.AC-2**, server authority.
10. `[test]` A failed list load renders the trio's error branch with a way to retry, and no add form
    bound to stale data.
11. `[test]` The route `/work/:bookId/chapters` renders this page and no longer renders the
    placeholder.
12. `[test]` The page registers itself as the content-pane subject on mount and unregisters on
    unmount.
13. `[manual/live]` `cd frontend && npm run build` and `cd frontend && npm run test:types` both pass.
