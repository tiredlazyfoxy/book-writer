# 005 — Chapter DTOs, `api/chapters.ts`, and the read-only Shell book hub

## Goal

Add the shared chapter DTOs and the single api module every later step calls, and give the Shell the
`/books/:bookId` book-hub route it does not have yet — a **read-only** ordered chapter list with state
badges and a way into the working page.

## Interface intent

**`frontend/src/types/chapters.d.ts`** (new) — hand-written DTOs matching `context.md` → "The wire
contract" exactly. Wire-exact `snake_case`, ids typed `string`, no `any`:

- the **chapter response**, the **chapter list response** (its array plus the `can_reorder` hint),
  the **create request**, the **sketch-update request**, the **reorder request**, the **chapter
  prompt response**, and the **chapter prompt update request**;
- a **wire-level union for the chapter state** (`planned` / `open` / `closing` / `closed`).
  It must **not** collide with the identically-valued `ChapterState` already declared in
  `frontend/src/work/subject.ts`. The two are structurally the same today but belong to different
  layers — one is the wire's vocabulary at shared `src/` root, the other is the working page's pane
  model, entry-local. `work/subject.ts` is **not** touched by this step; the naming that avoids the
  collision is the skeleton agent's to fix.

**`frontend/src/api/chapters.ts`** (new) — the one HTTP module for everything this feature calls,
following `frontend/src/api/codex.ts` as the book-nested-resource precedent. Every function takes the
book id first and `signal?: AbortSignal` last, and goes through the shared `request<T>` wrapper:

- **list** — takes a book id, returns the **whole list envelope**. It deliberately does *not* unwrap
  to a bare array the way `codex.ts` does, because the envelope carries `can_reorder`
  (`context.md` → cross-cutting frontend constraints).
- **read one** — book id and chapter id, returns one chapter.
- **create** — book id and the create body, returns the created chapter.
- **update sketch** — book id, chapter id and the sketch body, returns the stored chapter.
- **remove** — book id and chapter id, returns nothing (the endpoint answers `204`).
- **reorder** — book id and the ordered-id body, returns the list envelope.
- **read own chapter prompt** — book id and chapter id, returns the prompt response.
- **update own chapter prompt** — book id, chapter id and the prompt body, returns the prompt
  response.

The two prompt functions are named for the fact that they address the **caller's own** prompt, not the
chapter's, mirroring how `api/books.ts` names its book-level pair.

**`frontend/src/user/pages/bookHubPageState.ts`** (new) — a `BookHubPageState` class holding two async
trios and their loaders, following the file grain of `bookSettingsPageState.ts`:

- a trio for the **book detail**, loaded through the **existing** read function in `api/books.ts` —
  the same one `bookSettingsPageState.ts` already calls. **No function is added to `api/books.ts` in
  this step.**
- a trio for the **chapter list**, loaded through the new api module. The state keeps the whole
  envelope so nothing downstream has to re-fetch to learn `can_reorder`, even though this page ignores
  it.
- two external effect functions `(state, bookId, signal?)`, one per trio, each using `runInAction`.
  The two trios load and fail **independently**.

**`frontend/src/user/pages/BookHubPage.tsx`** (new) — an `observer` page component. It renders the
book's title as its heading, the chapters in ordinal order with a **state badge** on each, an
empty-state line when the book has no chapters yet, each trio's loading and error branches, a link to
each chapter's working-page route, and a prominent link into `/work/:bookId`.

**It is read-only.** No add form, no remove control, no reorder control, no editable field anywhere —
`context.md` → D2. The page owns one mount `useEffect` that starts both loads and aborts them on
unmount.

**`frontend/src/user/routes.tsx`** — one new route, `/books/:bookId` → `BookHubPage`, keyed on
`bookId` so a book change remounts the page. The existing `/`, `/health` and
`/books/:bookId/settings` routes are untouched, and the new route must not shadow the settings one.

## Definition of done

1. `[test]` Navigating to `/books/:bookId` renders the book hub: the book's title and its chapters in
   ordinal order, each with its state shown.
2. `[test]` A book with no chapters renders an empty state, not an error and not a blank list.
3. `[test]` The hub offers **no** control that adds, removes, reorders or edits a chapter, and no
   editable field — every chapter is presented read-only (D2).
4. `[test]` The hub links to the working page for the book and to each chapter's working-page route.
5. `[test]` The two loads fail independently: a failed chapter load renders its own error branch
   without destroying the book heading, and vice versa.
6. `[test]` Changing `:bookId` produces a fresh page state and re-loads both resources rather than
   showing the previous book's chapters.
7. `[test]` Each api function calls the path and method fixed by `context.md` → "Endpoints" and
   forwards the abort signal.
8. `[test]` The list function returns the **envelope** including `can_reorder`, not a bare array —
   the value steps 006 and 007 depend on survives the api layer.
9. `[test]` The remove function tolerates the endpoint's empty `204` body without attempting to parse
   a response.
10. `[manual/live]` `cd frontend && npm run build` and `cd frontend && npm run test:types` both pass —
    no `any` reaches the new DTOs, the api module or the new state.
