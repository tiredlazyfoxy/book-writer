# 007 — step context

Feature-wide facts (D3, the reorder endpoint contract, the `can_reorder` hint and why it rides on the
list envelope, the MobX rules, the frontend test harness, the build gates) are in `context.md` and are
not repeated here.

## There is no drag precedent in this repository

Harvested: `@dnd-kit/*`, `react-beautiful-dnd` and `@hello-pangea/dnd` are **all absent** from
`frontend/package.json`, and no existing surface reorders anything. This step introduces the first
one, so there is no house style to match — only `frontend.md`'s standing rules, which still bind:
`observer` on the new component, no custom hooks, no `useCallback`/`useMemo`, and all state on the
page-state class rather than in the library's own local state.

`@dnd-kit` supplies its own hooks (its sortable item hook, its sensor hooks). Those are **library
hooks, not custom `useX` hooks of ours**, and using them is not a breach of the no-custom-hooks rule —
the rule forbids *authoring* hooks, not consuming a library's API. Do not wrap them in a local hook of
our own; call them directly in the row component.

## Why the buttons are the tested path and the drag is not

`context.md` → D3 locks it, and the mechanical reason is worth having here: `@dnd-kit`'s pointer
sensor needs real pointer events with coordinates and element geometry, and jsdom reports zero-sized
rectangles for everything. Driving a drag in jsdom means either faking the library's internal
callbacks — which tests the test — or adding a keyboard-sensor path purely so a spec can reach it,
which is scope this feature did not ask for.

DoD-6 is what protects the invariant that matters: **both affordances funnel into one persist path**.
If that holds, testing the buttons tests the write path the drag also uses, and only the pointer
gesture itself remains manual (DoD-10).

## `can_reorder` is the affordance source — the server is the authority

The value comes from the list envelope (step 002 computes it from `access.role`; step 005 keeps the
envelope intact; step 006 lands it in state). **Do not derive owner-ness on the client from a book
DTO, from `auth.ts`, or from the workspace shell's loaded book detail.** The harvest did not record a
caller-relative role field on `BookDetailResponse`, and `ChaptersPageState` deliberately does not load
the book detail at all — that is exactly the coupling `can_reorder` exists to avoid.

DoD-4 and DoD-5 are the two halves of **US-033.AC-2** and both are required. The hint can go stale
(ownership can be transferred from another session between the load and the click), so the `403` path
must work even when the buttons rendered.

## The pending order must snap back

The list is rendered from the pending order while a reorder is in flight, which is a *rendering*
optimism, not a state optimism — nothing in the trio is mutated until the server answers. On failure
the pending order is discarded and the list re-seeded from a fresh load, which is what DoD-5 asserts.
Keeping the attempted order after a refusal would leave the author looking at an order the server does
not have, with no way to tell.

## One rendering site for a chapter row

Step 006 renders rows inline in `ChaptersPage.tsx`. This step **moves** that rendering into
`ChapterOrderList.tsx` rather than adding a second one. DoD-9 exists precisely to catch a move that
drops the remove control or the chapter link on the way. Re-read step 006's DoD-7, DoD-8 and DoD-9
before moving the markup — those behaviours must still hold afterwards, and step 006's spec will be
run again by the verifier.

## Installing the dependencies

`npm install @dnd-kit/core @dnd-kit/sortable` from `frontend/`. `@dnd-kit/sortable` requires
`@dnd-kit/core` as a peer, which is why both are listed. `package-lock.json` is regenerated by that
command and committed; **never hand-edit it**.

The frontend build is `npm run build` (= `tsc && vite build`) — a missing or mismatched type package
surfaces there, not in `npm test`. DoD-11 runs all three gates because a new dependency can break the
bundle, the specs and the test-only program independently.

## Testing

`frontend/tests/work/ChaptersPageReorder.test.tsx` is a **new** spec file, separate from step 006's
`ChaptersPage.test.tsx`, so the two steps' coverage stays attributable. It renders the same page and
must therefore repeat step 006's whole module-factory mock of `../../src/api/chapters` — enumerate
every export the page imports, not just the reorder function.

`ApiError` is imported real from `../../src/api/client` for DoD-5.

Queries are by **role or label only**. That is why the move controls must carry accessible names
naming the chapter and the direction — `getByRole("button", { name: /move .* up/i })` is the query
shape the spec will use, and an unlabelled icon button is untestable.

DoD-6 asserts the api function is called **once** per move with the full list; assert on the mock's
call count and payload, not on rendered order alone, or a double-submit would pass.
