# 008 — The chapter item page: sketch editor, own prompt editor, and the `planned` editability rule

## Goal

Replace the `/work/:bookId/chapter/:id` placeholder with a real chapter page carrying a sketch editor
enabled only for a `planned` chapter and an editor for **the caller's own** chapter system prompt, and
amend the working page's subject model so a `planned` chapter is editable in exactly those two
regions.

## Interface intent

**`frontend/src/work/subject.ts`** — amend `resolveEditability`'s `"chapter"` branch, and nothing
else in the file.

Today that branch returns: `open` → editable whole; `closing`, `planned` and `closed` → read-only,
each with its own author-facing reason. The `planned` case becomes **partially editable**: the
chapter's **sketch** and **the caller's own chapter system prompt** are editable regions, while the
chapter's **body text stays read-only** with the reason it already carries. `open`, `closing` and
`closed` are untouched.

`checkWritePermission` must keep refusing a `text` write on a `planned` chapter — the amendment widens
what is editable, it does not widen what may be written into the body.

If the `EditableRegion` / `WriteRegion` unions do not already carry members naming the sketch and the
prompt, add them — `subject.ts` is in this step's source list, so widening those unions here is in
scope. Do not add members for anything this feature does not ship.

**`frontend/src/work/pages/chapterPageState.ts`** (new) — a `ChapterPageState` class plus its external
effect functions, following `bookStatePageState.ts`'s grain.

- An **async trio** for the chapter itself.
- An **async trio** for the caller's own chapter prompt. The two load and fail **independently**.
- **Sketch editor state**: a draft, a `…ServerErrors` map, a submit status; pure `get` computeds for
  dirtiness, for whether the sketch may be edited at all (true only when the loaded chapter's state is
  `planned`), and for whether saving is currently allowed.
- **Prompt editor state**: a draft, a `…ServerErrors` map, a submit status; pure `get` computeds for
  dirtiness and submittability. **No editability gate** — a member may write their own prompt on a
  chapter in any state.
- Both editors follow `context.md`'s form-state shape: a server-error map with **no `clientErrors` and
  no `errors` union**, because every string including the empty one is valid on both fields.
- **External effect functions** `(state, bookId, chapterId, signal?)` using `runInAction`: load the
  chapter and seed the sketch draft from it; save the sketch and **re-seed from the response**; load
  the prompt and seed its draft; save the prompt and re-seed from the response. A refused save stores
  the server's message and **leaves the draft intact**.

**`frontend/src/work/pages/ChapterPage.tsx`** (new) — an `observer` page component holding a
`ChapterPageState` in `useState`, with one mount `useEffect` starting both loads and aborting both on
unmount.

It renders: the chapter's title, ordinal and readable state; each trio's loading and error branches; a
**sketch section** with a multi-line editor, a save control gated on the computed, and a server-error
surface — the editor disabled with a stated reason whenever the chapter is not `planned`; and a
**system-prompt section** with a multi-line editor, a save control, a server-error surface, and one
line of copy stating the prompt is **the caller's own** and is not shared with co-authors.

The page **registers itself as the content-pane subject on mount and unregisters on unmount** through
the existing `contentSubject` module, so the pane model's editability answer is about this chapter.

The chapter's **body text is not rendered and not editable here** — it is
`015.chapter-writing-free-mode`'s, and the DTO does not carry it (`context.md` → the wire contract).

**`frontend/src/work/routes.tsx`** — swap the `chapter/:id` child route's element from the
`SubjectPlaceholderPage` to `ChapterPage`, keeping the existing `ChapterItemRoute` wrapper and its
`key={id}` so a chapter change remounts the page. **Only that element changes**; every other child
route, including step 006's `chapters` line, is untouched.

## Definition of done

*Items 6–10 are the chapter-prompt half. It has no product id — FEAT-019's UC-094 / US-109 describe a
superseded model (`context.md` → "Product situation") — so they are written as self-contained
criteria.*

1. `[test]` The route `/work/:bookId/chapter/:id` renders this page, showing the chapter's title,
   ordinal and state, and no longer renders the placeholder.
2. `[test]` On a `planned` chapter the sketch editor is enabled, seeded with the stored sketch; saving
   sends the draft and the editor then shows the value the **server returned** — **US-034.AC-1**.
3. `[test]` On a chapter that is `open`, `closing` or `closed` the sketch editor is **disabled**, with
   a stated reason, and offers no save — **US-034.AC-2**, client affordance.
4. `[test]` When the server refuses a sketch save, the message is surfaced and the draft is left
   intact — **US-034.AC-2**, server authority.
5. `[test]` The sketch save control is unavailable while the draft matches the loaded value and while
   a save is in flight; saving an empty sketch is allowed.
6. `[test]` On mount the page loads the caller's own chapter prompt and shows its text in the prompt
   editor.
7. `[test]` A member with no stored prompt for the chapter sees an empty, editable field — the empty
   response is a normal state, not an error state.
8. `[test]` Editing and saving the prompt sends the draft and the editor then shows what the **server
   returned**; a refused save surfaces the message and leaves the draft intact.
9. `[test]` Saving an empty prompt is allowed and clears it — there is no delete control anywhere on
   the surface.
10. `[test]` The prompt editor is enabled on a chapter in **every** state, including `open` and
    `closed`, and the surface states that the prompt is the caller's own and not shared with
    co-authors.
11. `[test]` The two trios fail independently: a failed prompt load renders its own error branch
    without breaking the chapter view, and a failed chapter load does not hide the prompt section's
    own state.
12. `[test]` `resolveEditability` reports a `planned` chapter as editable in its **sketch** and in the
    caller's **own prompt**, and read-only in its **body text**; `open`, `closing` and `closed` keep
    the answers they give today.
13. `[test]` `checkWritePermission` still refuses a write to a `planned` chapter's body text — the
    amendment widened editability, not the body write path.
14. `[test]` The page registers itself as the content-pane subject on mount and unregisters on
    unmount, and changing `:id` produces a fresh page state rather than showing the previous
    chapter's drafts.
15. `[manual/live]` Two members opening the same chapter's page each see and edit their own system
    prompt, and neither sees the other's.
16. `[manual/live]` `cd frontend && npm run build` and `cd frontend && npm run test:types` both pass.
