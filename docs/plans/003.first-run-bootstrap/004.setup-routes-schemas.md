# Step 004 — Setup routes + schemas (HTTP surface)

## Goal
Expose the first-run HTTP surface — a status endpoint plus create/import setup
endpoints under `/api/auth` — with typed request/response schemas and
`SetupError`→HTTP-400 mapping, and mount the router on the app.

## Source files
backend/app/routes/auth.py
backend/app/models/schemas/auth.py
backend/app/main.py

## Test files
backend/tests/routes/test_setup.py

## Interface intent
- **`AuthStatusResponse`** (in `models/schemas/auth.py`) — a Pydantic response
  schema carrying `needs_setup` (bool).
- **`CreateDBRequest`** (in `models/schemas/auth.py`) — a Pydantic request schema
  carrying `admin_username`, `password`, and `password_confirm`.
- **`LoginResponse`** (in `models/schemas/auth.py`) — a Pydantic response schema
  carrying `token` (the minted JWT string).
- **auth router** (in `routes/auth.py`) — an `APIRouter` with
  `prefix="/api/auth"`, HTTP-only (parse request, call a service, return a
  schema; no business logic, no DB access). Endpoints:
  - **`GET /api/auth/status`** — returns `AuthStatusResponse(needs_setup=not
    is_db_ready())`. (Detection surface for the frontend.)
  - **`POST /api/auth/setup/create`** — body `CreateDBRequest`; calls
    `setup.create_database`, then mints the first token via
    `auth_service.create_token(admin)`, and returns `LoginResponse{token}`
    (auto-sign-in, decision 8). A `SetupError` from the service maps to
    **HTTP 400** with the error message.
  - **`POST /api/auth/setup/import`** — accepts a **multipart** upload (an
    `UploadFile` field named `file`); reads its bytes and calls
    `setup.import_database`, returning `AuthStatusResponse` (with `needs_setup`
    reflecting the new state; **no** token — decision 8). A `SetupError` maps to
    **HTTP 400** and the instance stays unconfigured.
- **router mount** (amend `app/main.py`) — mount the auth router with a bare
  `app.include_router(...)` (the router owns its `/api/auth` prefix). This is the
  only change to `main.py` in this step.

## Definition of done
1. `[test]` `GET /api/auth/status` returns `needs_setup: true` on a cold
   instance and `needs_setup: false` after a successful create. (Backs
   `US-001.AC-1` / `UC-001` step 1.)
2. `[test]` `US-001.AC-1` — `POST /api/auth/setup/create` with valid credentials
   returns HTTP 200 and a `LoginResponse` carrying a non-empty `token`
   (operator auto-signed-in).
3. `[test]` `US-001.AC-2` — `POST /api/auth/setup/create` on an
   already-configured instance is refused with an HTTP 4xx (not 200), so the
   operator is directed to normal login instead of creating a second admin.
4. `[test]` `US-001.AC-3` — `POST /api/auth/setup/create` with a password shorter
   than 8 characters returns HTTP 400 and mints no token.
5. `[test]` `US-001.AC-4` — `POST /api/auth/setup/create` with password ≠
   confirmation returns HTTP 400 and mints no token.
6. `[test]` `US-002.AC-1` — `POST /api/auth/setup/import` with a valid archive
   returns HTTP 200 with `needs_setup: false` (instance configured, no token).
7. `[test]` `US-002.AC-2` — `POST /api/auth/setup/import` with a corrupt/invalid
   archive returns HTTP 400, and a subsequent `GET /api/auth/status` still
   reports `needs_setup: true` (instance remains unconfigured).
