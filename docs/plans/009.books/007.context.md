# 007 context — Book settings frontend

MobX/API/forms conventions, the `key`-remount rule, and the frontend-test-runner
situation are in `context.md`. Narrow facts for this step:

- **First URL-param route in the repo.** `routes.tsx` has had no path params; this
  step introduces `/books/:bookId/settings`. Apply `frontend.md`'s "page = route =
  fresh state instance" via `key={bookId}` on the route element so a different book
  remounts a fresh `BookSettingsPageState`. There is no in-repo instance to copy — the
  rule is documented, not yet demonstrated.
- **Extends step 6's files.** `api/books.ts`, `types/books.d.ts`, `routes.tsx` and
  `src/user/components/books/` all already exist from step 6; this step adds to them
  (detail + mutation calls, detail + request types, the settings route, the two
  settings drafts).
- **Detail DTO drives the page.** The `members` list and current `visibility` /
  `state` come from `GET /api/books/{id}` (step 4 `BookDetailResponse`). After any
  mutation, re-load the detail rather than mutating local state, so the members list
  and state reflect the server (backend is the source of truth).
- **Transfer target restriction** (UC-024 resolved `_TBD_`: refuse non-co-authors)
  is enforced server-side (step 5); the UI offers only current co-authors as transfer
  targets, and surfaces a server refusal as a field error if one slips through.
- The `bookId` route param is a `string`; pass it straight into the `api/books.ts`
  calls (ids are strings across the DTO boundary). No numeric parsing on the client.
- Template drafts: `CreateUserDraft` (create shape) and `serverFormDraft.ts`
  (seed-from-existing edit shape) — the transfer/add forms are closest to the create
  shape (a single selection + submit).
