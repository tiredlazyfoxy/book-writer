# 002 context — Authorization spine

The full taxonomy, the resolve-in-dependency/decide-in-service rationale, and the
matrix source are in `context.md` → "Authorization taxonomy" and "Enforcement
spine", drawn from `docs/architecture/authorization.md`. Narrow facts for this step:

- The resolver is split into a testable `resolve_book_access(book_id, user)` plus a
  thin `book_access(book_id)` FastAPI dependency, precisely so the test-coder can
  exercise resolution against a seeded temp DB **without** an HTTP round-trip — mirror
  how the tests seed `Book` / `BookMember` rows directly (008 `test_data_domain_*`
  style) and pass a seeded `User`.
- `get_current_user` (from `services/auth.py`) already raises **401** on a
  missing/invalid token — the dependency wrapper gets 401 for free; the resolver
  itself never handles the no-token case.
- Existence hiding is produced in **exactly one place** here: `role == none`
  (private, no relationship) collapses to the same **404** as a missing book, so a
  private book is indistinguishable from a non-existent one to an outsider.
- `admin` is intentionally absent from the 009 `AccessRole` values used by the
  matrix — an admin hitting an authoring endpoint resolves as owner/co_author/reader
  if they happen to hold that relationship, else `none` → 404, i.e. treated as a
  stranger (`authorization.md` → "The admin boundary"). The moderation view that
  gives admins book content is FEAT-011, out of scope.
- Enum value strings must match the data-layer enums where they overlap
  (`book_state` ← `BookState`, `visibility` ← `Visibility`, `collaboration_mode` ←
  `CollaborationMode` from `models/book.py`); `BookAccess` carries them through
  as-resolved.
- `require` raising a typed `BookAuthorizationError` (not `HTTPException`) keeps the
  capability decision in `services/`; steps 3–5 routes map it to 403 via their
  error-mapping helper (same shape as the `LlmServerError` mapping).
