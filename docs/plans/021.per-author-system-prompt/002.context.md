# 002 — step context

Feature-wide facts (the wire contract, the status taxonomy, layer rules, the no-capability decision)
are in `context.md` and are not repeated here.

## The guard shape to copy, verbatim

`backend/app/services/chats.py:180-195` — `_resolve_owned_chat(access, chat_id)`. It returns the
typed reason `chat_not_found` (which the route maps to `404`) when the row is missing, belongs to a
different book, **or** when `chat.author_id != access.user_id`. Its docstring records the rule this
step inherits:

> the rule is **not** a `Capability` / `_CAPABILITY_MATRIX` entry — that table maps capability → roles
> and has no notion of row ownership.

**What this step copies is the *shape*, not the status.** Chats hide a row that exists but is not
yours, because a chat is private even from the book's owner (US-061.AC-1). This feature has nothing to
hide: the caller can only ever address *their own* prompt, because the user id comes from
`access.user_id` and never from an argument or a path segment. So there is no not-found case at all —
the only refusal is **"you are not a member of this book"**, which `context.md` maps to `403` per
`authorization.md` → "Failure modes".

## `services/authz.py` — what exists, and what must not be added

Harvested, current:

- `BookAccess` carries `book_id`, `user_id`, `role`, `book_state`, `visibility`,
  `collaboration_mode`.
- `AccessRole` is `owner` | `co_author` | `reader` | `none`.
- `Capability` currently holds nine members: `read_book`, `view_book_detail`, `archive_book`,
  `transfer_ownership`, `add_member`, `remove_member`, `set_visibility`, `browse_codex`,
  `edit_codex_entry`. Owner-only rows are `frozenset({AccessRole.owner})`; `view_book_detail` is
  `{owner, co_author}`.

**Add nothing to either.** `services/authz.py` is **not** in this step's source-file list. The
membership test is `access.role in {owner, co_author}`, written inside this step's own service — the
same layering `013.codex` used for the collaboration-mode nuance and `011.chat-panel` used for chat
row ownership.

## Collaboration mode does **not** apply here

`BookAccess` carries `collaboration_mode`, and several book-domain capabilities are marked *(mode)* in
`authorization.md`'s matrix — a co-author's write is held as a proposal in `proposal` mode. **That
rule does not reach this table.** A system prompt is not book content: it is the author's own
instruction to their own assistant, it is never seen by a co-author, and there is nothing for an owner
to review. Do not add a mode check, and do not copy `services/codex.py`'s proposal refusal.

## Timestamps belong to this layer

Step 001's `db/` module persists the row it is handed and sets no timestamps (its docstring says so).
So this service sets `created_at` **and** `modified_at` on create, and `modified_at` on update. DoD-4
asserts exactly this split — a db layer that quietly stamped rows would make the preserved-`created_at`
assertion pass for the wrong reason.

## Empty string is a value, not an absence

Two distinct states must both behave as "no prompt" at composition time but stay distinguishable in
storage:

- no row for the pair — the state before an author ever writes one;
- a row holding `""` — the state after an author clears one.

The response DTO renders both as `system_prompt: ""`; the difference shows only in `modified_at`
(`null` versus a real timestamp). Do not normalise one into the other in the mapper.

## Testing

Construct `BookAccess` instances directly — it is a frozen dataclass and needs no HTTP. Supporting
rows (users, books, memberships) are seeded through the sibling `db/` modules with the `db` fixture,
as `backend/tests/services/` specs already do. No route, no client, no JWT at this layer — those are
step 003's.
