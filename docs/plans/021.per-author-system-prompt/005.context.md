Feature-wide facts (the wire contract, the MobX rules, the frontend test harness, the gates) are in

## `bookSettingsPageState.ts` as it stands today

Harvested: `BookSettingsPageState` is a plain async trio — `detail` / `detailStatus` / `detailError` —
plus external effect functions shaped `(state, bookId, [body,] signal?)` that call the `booksApi.*`
module and then **re-run `loadBookSettings`**. There is **no optimistic mutation anywhere in the
file**.

The prompt additions follow that grain: a second trio, and effects that end by adopting what the server
returned. The one deliberate difference is that the save adopts the **response body directly** instead
of re-running the loader — the `PUT` already returns the stored prompt, so a second round trip would
add a window in which the editor shows neither the draft nor the stored value.

**Do not touch the existing trio or its effects.** This step is additive to the file.

## The single-text-field draft precedent

`frontend/src/user/components/books/addCoAuthorDraft.ts` (94 lines) is the pattern to copy:

- an observable field for the input,
- `serverErrors: Record<string, string>` held **separately** from client-side validation,
- a `submitStatus`,
- pure `get clientErrors` / `get errors` / `get canSubmit` computeds,
- an external `submit…(draft, bookId, onDone, signal?)` that maps an `ApiError` into `serverErrors`.

**Two deliberate departures.** First, this prompt has **no client-side validation at all** — every
string, including the empty one, is valid (`context.md` → decision 6), so there is no `clientErrors`
to compute and the server-error surface is the only error surface. Second, the draft lives in the
**page state**, not in a separate draft class: `addCoAuthorDraft` is a modal's draft with its own
lifetime, while this editor is part of the page and shares its mount.

## `SystemPromptCard` is not shared with step 006

Step 006 gives `BookStatePage` its own state additions and its own rendering. The two surfaces
deliberately do **not** share a component or a state class — `context.md` → "Planner-derived decisions"
carries the reasoning (each SPA owns its `pages/` and `components/`; only `src/` root is shared, and
crossing from `work/` into `user/` would break the folder layout).

What **is** shared, and is this step's to get right because step 006 consumes it unchanged: the two
DTOs in `types/books.d.ts` and the two functions in `api/books.ts`.

## The fourth omission comment

`frontend/src/types/books.d.ts` around lines **69-74** carries the fourth of the four docstrings
declaring `system_prompt` deliberately omitted. The other three are in
`backend/app/models/schemas/books.py` and belong to **step 004**. This step revises this one only, to

## The surface's reach

`BookSettingsPage` serves `/books/:bookId/settings` in the Shell entry, which
`frontend-workspace.md`'s route map describes as the archive / transfer / co-authors / visibility /
collaboration-mode surface — all owner-only capabilities. **Whether a co-author can reach this page is
a property of the existing page and is not changed by this step**, and no test here should assert
either way. The surface guaranteed to reach every member is the working page's Book state view, which
is step 006's.

## Testing

`BookSettingsPage` has **no spec file at all** today — both listed specs are created from scratch.

`frontend/tests/work/BookStatePage.test.tsx` is the working reference for the module-factory api-mocking
pattern: the factory must enumerate **every** export the subject imports from `api/books`, not just the
two new ones, or the module mock will strip the page's existing loads and the page will fail to render
for the wrong reason.

`ApiError` is imported real from `../../src/api/client` — DoD-6 needs a real one to assert the message
surfaces and the draft survives.
