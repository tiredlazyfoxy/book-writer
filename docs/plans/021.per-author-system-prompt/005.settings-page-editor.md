# 005 — Frontend DTOs, api functions, and the book-settings editor

## Goal

Add the shared prompt DTOs and the two api functions, revise the `types/books.d.ts` omission comment,
and give `BookSettingsPage` a writable editor for the caller's own system prompt.

## Interface intent

**`frontend/src/types/books.d.ts`** — two hand-written DTOs matching `context.md` → "The wire
contract" exactly: a **prompt response** (book id as `string`, prompt text, nullable modified
timestamp) and an **update request** (prompt text only). Wire-exact `snake_case`, no `any`.

The existing comment around lines 69-74 declaring `system_prompt` deliberately omitted from the book
DTOs is **revised, not deleted**: the new reason is that the prompt is per-author and served by its own
endpoint, so a book-shaped DTO cannot carry it. It mirrors the three backend docstrings step 004
revises.

**`frontend/src/api/books.ts`** — two functions on the existing resource module, named for the fact
that they address the **caller's own** prompt rather than the book's:

- a **read** taking a book id and returning the prompt response;
- an **update** taking a book id and the request body, returning the stored prompt response.

`signal?: AbortSignal` is the trailing argument on both; both go through the shared `request<T>`
wrapper.

**`frontend/src/user/pages/bookSettingsPageState.ts`** — additions only; the existing book-detail trio
and its effects are untouched.

- An **async trio** for the prompt (value / status / error), following the file's existing trio naming.
- A **draft field** for the textarea, a separate **server-error** holder, and a **submit status**,
  following `user/components/books/addCoAuthorDraft.ts`'s split between client-side and server-side
  error state.
- Pure `get` computeds: whether the draft differs from what the server last returned, and whether
  submitting is currently allowed.
- Two **external effect functions** `(state, bookId, signal?)` in the same file: one that loads the
  prompt and seeds the draft from it, one that saves the draft and **re-seeds state from the response**
  (the server is the source of truth — no optimistic mutation, matching how this file's existing
  effects behave).

**`frontend/src/user/components/books/SystemPromptCard.tsx`** (new) — an `observer` component taking
the page state. It renders the trio's loading and error branches, a multi-line editor bound to the
draft, a save control gated on the computed, a server-error surface distinct from any field-level
message, and one line of copy telling the author **this prompt is theirs alone — every author of the
book keeps their own**. Handlers are inner functions closing over the state; no extracted callbacks,
no hooks.

**`frontend/src/user/pages/BookSettingsPage.tsx`** — render the card, and trigger the prompt load from
the page's **existing** mount effect (no second `useEffect`).

## Definition of done

1. `[test]` On mount the page loads the caller's own prompt and shows its text in the editor.
2. `[test]` When the author has no stored prompt the editor renders empty and editable — the empty
   response is a normal state, not an error state.
3. `[test]` Editing the text and saving sends the draft to the update function, and the editor then
   shows the value the **server returned** rather than the local draft.
4. `[test]` The save control is unavailable while the draft matches the loaded value, and while a save
   is in flight.
5. `[test]` Saving an empty editor is allowed and clears the prompt — there is no delete control
   anywhere on the surface.
6. `[test]` A refused save surfaces the server's message to the author and **leaves the draft intact**
   so nothing typed is lost.
7. `[test]` A failed load renders the trio's error branch with a way to retry, and no editor bound to
   stale data.
8. `[test]` The surface states that the prompt is per-author, not book-wide.
   *(This is the copy that replaces UC-093's book-wide framing.)*
9. `[test]` The api functions call the `GET` and `PUT` paths from `context.md` → "The wire contract"
   and forward the abort signal.
10. `[manual/live]` `cd frontend && npm run build` and `cd frontend && npm run test:types` both pass —
    no `any` reaches the new DTOs or the new state.
