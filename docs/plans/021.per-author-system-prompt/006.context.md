# 006 — step context

Feature-wide facts (the wire contract, the MobX rules, the no-restore-buffer decision, the frontend
test harness and gates) are in `context.md` and are not repeated here.

## `bookStatePageState.ts` as it stands today

Harvested: an async trio plus `get` computeds plus **one** loader — and the page is **read-only
today**. This step makes it the first Book-state surface with a write path.

Additions only. Do not fold the prompt into the existing trio: `frontend.md` is explicit that a page
with several loadables has several trios and no aggregation type, and DoD-7 depends on the two failing
independently.

## Why this surface exists at all, given step 005

`BookSettingsPage` aggregates owner-only capabilities (`frontend-workspace.md`'s Shell route map:
archive, transfer, co-authors, visibility, collaboration mode). The working page's Book state view is
the **landing view every member reaches** (UC-091, US-106.AC-1). Since every author now owns a prompt,
the editor has to exist somewhere every author can get to — which is here. Both surfaces edit the same
row through the same endpoint; there is no precedence and no sync problem, because the server is the
only source of truth and each surface re-seeds from the response it gets.

## No restore buffer, no reconciliation view

The working page's draft-until-saved restore buffer (UC-092, `frontend-workspace.md`) is **not** used
for this field — `context.md` → "Planner-derived decisions" carries the reasoning. Concretely, that
means:

- do not import `restoreBuffer.ts`, do not build a buffer key, do not write on keystroke;
- there is **no `baseVersion`**, no stale-buffer detection and no divergence view;
- there is **no 409 path** — the endpoint carries no version token and the last write wins, which is
  acceptable because a row has exactly one writer: its owner.

Anything that looks like the codex entry page's reconciliation machinery is out of scope here.

## The editability table this step changes

`frontend-workspace.md` → "Content pane — subject and editability" currently says of the Book state
subject: **"state notes editable (UC-050); everything else read-only."** After this step the caller's
own prompt is editable there too. DoD-9 pins that the change is exactly one region wide, and
`outcome.md` carries the doc update. Do not make any other Book-state field editable in passing.

## Reuse, not re-declaration

The two DTOs and the two api functions come from step 005 (`frontend/src/types/books.d.ts`,
`frontend/src/api/books.ts`) and are consumed unchanged. **Neither file is in this step's source-file
list** — if this step appears to need a change there, that is a signal step 005's contract was wrong,
not licence to widen it here.

The two page-state files deliberately do not share code (`context.md` → "Planner-derived decisions").
Repeating the trio-plus-draft shape in this file is the intended outcome, not duplication to be
factored out.

## Testing

`frontend/tests/work/BookStatePage.test.tsx` **already exists** and is the repo's reference for the
module-factory api-mocking pattern. Extend it rather than adding a parallel spec.

The existing module factory for `api/books` must be widened to include the two new exports, and every
export the page imports must stay enumerated — a factory missing one strips it to `undefined` and the
page fails to render for the wrong reason.

`ApiError` is imported real from `../../src/api/client`; DoD-6 needs a real one.
