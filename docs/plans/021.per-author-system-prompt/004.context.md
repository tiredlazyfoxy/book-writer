## `services/prompt_composition.py` as it stands today

Harvested and verified:

- `compose_system_prompt(base=None, mode=None, book=None, chapter=None) -> str`.
- It builds the pair list `[("BASE", base), ("MODE", mode), ("BOOK", book), ("CHAPTER", chapter)]`,
  **skips any layer that is `None` or whitespace-only**, renders each survivor as
  `### {label}\n{text.strip()}`, and joins the survivors with blank lines.
- It is **pure** — no I/O, no database, no clock.

Everything above survives this step except the third pair's parameter name and label. Do not change
the rendering, the join, the skip rule, the ordering of the other three layers, or the purity.

## Why the column is kept — the constraint, once

`backend/app/db/engine.py` exposes only an **additive** migration seam (currently `pass`) and
`init_db()` runs `SQLModel.metadata.create_all`, which never alters an existing table. **There is no
Alembic in the repository.** So there is no supported DROP COLUMN path, and dropping
`Book.system_prompt` would mean either hand-written migration machinery this feature has no mandate to
build, or a schema that silently disagrees with every existing database file.

Current facts about the column: `backend/app/models/book.py:77` declares it as a bare required
`str` with no `Field(default=...)`; `backend/app/services/books.py:123` writes `""` at creation; it is
**never updated anywhere**; and `backend/app/services/db_import_export.py:369` / `:403` round-trip it.

After this step it is written once, exported, and read by nothing. DoD-6 and DoD-7 together are what
keep that pair of statements true: dead to the runtime, alive to the schema and the archive.
