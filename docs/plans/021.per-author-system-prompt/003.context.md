# 003 — step context

Feature-wide facts (the wire contract, the `401 / 404 / 403` taxonomy, route-layer rules, the test
harness) are in `context.md` and are not repeated here.

## What the planner did **not** have, and who resolves it

The harvest for this feature covered the data, service and composition layers in detail; it did **not**
enumerate the `routes/` package. So this step names *what must exist* and leaves two mechanical
details to the **skeleton** agent, which reads code and freezes signatures:

1. the exact router construction and prefix idiom (whether the prefix lives on the `APIRouter` or on
   the path decorators), and how `main.py` mounts it;
2. the exact shape of the reason → status map and its mapper function.

Both are to be copied from the **nearest existing book-scoped router** — the ones serving
`/api/books/{book_id}/…` — rather than invented. Do not introduce a second convention for either.

The two things that are **not** open and must not be re-derived: the path
(`/api/books/{book_id}/system-prompt`, `context.md` → decision 5) and the status taxonomy
(`context.md` → "The wire contract").

## Where each status comes from — three different layers

This is the part most easily got wrong, because only one of the four statuses is this step's to
produce.

| Status | Produced by | This step's part |
|---|---|---|
| `401` | the authentication dependency behind `book_access` | nothing — inherited |
| `404` | `resolve_book_access`, for a missing book or a caller with no relationship to a private one | nothing — inherited |
| `403` | **this router**, mapping step 002's single typed reason | the reason → status map |
| `200` | the handlers | the return annotations |

Do **not** add a `404` branch to the router. `authorization.md` → "Failure modes" places existence
hiding in the resolution step precisely so it is produced in exactly one place; a second
implementation here would drift from it.

Do **not** catch `authz.BookAuthorizationError` — step 002 raises no capability error, because this
feature adds no `Capability` (`context.md` → decision 4). If a caught-and-mapped
`BookAuthorizationError` appears in this router, something upstream went wrong.

## `PUT` returns `200`, and there is no `POST`

`PUT` is the upsert (`context.md` → decision 6). It answers `200` on both the create and the update
path: the addressed resource is "this caller's prompt for this book", identified entirely by the URL
plus the token, so there is no new location to report and `201` would be a lie on the second call.
There is no `POST` and no `DELETE` on this path.

## Testing

Copy `backend/tests/routes/test_chats.py` for the harness: the `http_client(tmp_path, monkeypatch)`
fixture (which drives the app lifespan manually) plus the seed helpers `_now`, `_auth_header`,
`_seed_user`, `_seed_author`, `_seed_private_book`, `_add_co_author`. **Auth is real** — seed a user
row and mint a real JWT; do not stub the current-user dependency.

`backend/tests/routes/test_chats.py:test_non_member_gets_404_from_every_route__DoD9` is the canonical
book-scoped-authz test shape; DoD-6 is that test with this feature's two routes.

DoD-7 needs a **public** book with a logged-in non-member, which is the only way to reach the `403`
branch at all — on a private book the dependency answers `404` first and the service is never entered.

Assertions validate response bodies through the response DTO from step 002 rather than by indexing raw
JSON.
