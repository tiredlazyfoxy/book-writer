# Step 004 — User-mutation modals (create / reset / role)

## Goal

Add the three account-mutation modals — create user, reset password, change role
— each a draft-in-state + computed-validation + server-error form, and wire them
into the users page so every mutation refreshes the list. (One cohesive UI slice:
three self-similar modal units sharing the page wiring; kept together because
splitting them adds no boundary value on a manual/live frontend.)

## Interface intent

- **`CreateUserModal.tsx`** — an `observer` modal. A `*Draft` MobX class holds
  the username / password / password_confirm / role fields; `get` computeds give
  the client-side validation (required username, min-length-8 password, confirm
  match) and a `canSubmit`; a separate `serverErrors` field holds field errors
  merged into the displayed errors. An external `submitCreate(draft, onCreated,
  signal)` effect calls `admin.createUser`, and on an `ApiError` (e.g. 409 taken
  username, 400 password) maps it into `serverErrors`; on success it invokes
  `onCreated` (the page's refresh) and closes. Role is chosen from the shared
  `ROLE_OPTIONS` (`admin | author`). **No Mantine `useForm`.**
- **`SetPasswordModal.tsx`** — same shape for a target user: a `*Draft` with
  password / password_confirm + `get` validation (min-length-8, confirm match) +
  `serverErrors`; an external `submitSetPassword(draft, userId, onSaved, signal)`
  calling `admin.setUserPassword`, mapping errors, and refreshing on success.
- **`SetRoleModal.tsx`** — same shape for a target user: a `*Draft` with the role
  field from `ROLE_OPTIONS`; an external `submitSetRole(draft, userId, onSaved,
  signal)` calling `admin.setUserRole`, surfacing the self-target refusal (400)
  and any other `ApiError` into `serverErrors`, and refreshing on success.
- **`UsersPage.tsx`** (amend) — add the per-row menu entries (Set Password, Set
  Role) and a Create button; hold the open/target flags in **component-local
  `useState`** (not page state); pass the page's `refresh` as `onCreated`/
  `onSaved` so each successful mutation re-loads the list.

## Definition of done

1. `[manual/live]` **US-006.AC-1 / US-006.AC-2** — creating a user with an
   untaken username makes it appear in the list after refresh; a taken username
   surfaces a server error in the modal (the create is refused, no new row).
2. `[manual/live]` **US-007.AC-1 / US-007.AC-2** — resetting a user's password
   succeeds and refreshes the list; resetting a disabled user's password makes it
   active again (it can log in).
3. `[manual/live]` **US-008.AC-1 / US-008.AC-2** — changing another user's role
   updates the row after refresh; attempting to change the admin's own role is
   refused and surfaces a server error (the change does not take effect).
4. `[manual/live]` decision 10 — each mutation refreshes the list via the page
   loader; each modal uses drafts-in-state + `get`-computed validation + separate
   `serverErrors`, with **no Mantine `useForm`**, and every component is
   `observer`.
5. `[manual/live]` `cd frontend && npm run build` completes clean (typecheck +
   bundle) with the three modals wired into the page.
