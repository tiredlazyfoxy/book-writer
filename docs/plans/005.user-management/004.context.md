## Form pattern (frontend.md forms + decision 10)

- Each modal owns its own `*Draft` MobX class (modal-dialog drafts may live in
  component-local state) with observable fields + `get` computeds for validation
  (`errors`, `isValid`/`canSubmit`) — no effectful methods on the draft.
- Server-side field errors live in a separate `serverErrors` field and are unioned
  with client errors in the displayed `errors` getter (do not overwrite client
  validation with server errors).
- Effectful submits are external `submit*(draft, …, signal)` functions using
  `runInAction`; on `ApiError` they populate `serverErrors` from the error
  (status + message/details), on success they call the passed refresh callback and
  close.
- Modal open/target flags are **component-local `useState`** in `UsersPage`, not
  page state (decision 10). Role selects read the shared `ROLE_OPTIONS`
  (`admin | author`) from `types/admin`.
- **No Mantine `useForm`** anywhere; every component is `observer`.

## Error mapping expectations (from the step-002 taxonomy)

The modals surface these backend refusals as `serverErrors`: 409 taken username
(create), 400 password-policy (create / reset), 400 self-target (change own role).
These are the `ApiError.status` values step 002 produces — map them to a
user-visible field/message; do not swallow them.
