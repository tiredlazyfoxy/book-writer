# Step 001 — Admin guard + admin user service + schemas + `db.get_all`

## Goal

Build the backend business layer for user management: the `require_role(admin)`
guard (first realization of the 004→005 deferral), the admin user service
(list / create / reset-password / change-role / disable with validation,
self-guards, credential minting/nulling, and the secret-excluding response
mapping), the four admin DTOs, and `db/users.get_all`.

## Interface intent

- **`require_role`** (in `app/services/auth.py`) — a dependency **factory**: given
  a minimum role, it returns a FastAPI dependency that resolves the caller via
  `get_current_user`, compares the caller's role against the ladder
  `{author: 0, admin: 1}`, and returns the caller `User` when the caller's level
  is at least the required level; otherwise it raises the HTTP-403 error directly
  (same pattern `get_current_user` already uses for 401). The admin routes will
  call `require_role(admin)`.
- **`AdminUserResponse`, `AdminCreateUserRequest`, `AdminSetPasswordRequest`,
  `AdminSetRoleRequest`** (in `app/models/schemas/admin.py`) — Pydantic
  `BaseModel`s. `AdminUserResponse` carries `id` (an `int` in Python but
  **serialized as a string on the wire** per the system-wide snowflake
  convention), `username`, `role`, `last_login`, and the derived `active` bool —
  **no secret fields**. `AdminCreateUserRequest` carries `username`, `password`,
  `password_confirm`, `role`. `AdminSetPasswordRequest` carries `password`,
  `password_confirm`. `AdminSetRoleRequest` carries `role`.
- **`app/services/admin.py`** — the admin user service. Functions:
  - a private response mapper that builds an `AdminUserResponse` from a `User`
    by hand (never dumps the ORM), computing `active = user.pwdhash is not None`
    and copying only non-secret fields.
  - **`list_users`** — returns every account (via `db.users.get_all`) mapped to
    `AdminUserResponse`, ordered by username, carrying role + last_login + active.
  - **`create_user`** — validates the password policy, refuses a taken username,
    hashes the password, generates a fresh signing key + `last_key_update`,
    persists a new `User` with the given role via `db.users.create`, and returns
    its `AdminUserResponse` (active true).
  - **`set_user_password`** — looks up the target (refusing if not found),
    validates the password policy, sets a new `pwdhash` + fresh `jwt_signing_key`
    + `last_key_update` via `db.users.update`, re-enabling a disabled account,
    and returns its `AdminUserResponse`.
  - **`set_user_role`** — takes the authenticated caller and the target id;
    refuses a self-target (caller is the target), refuses a missing target,
    updates the role via `db.users.update`, and returns the `AdminUserResponse`.
  - **`disable_user`** — takes the caller and the target id; refuses a
    self-target, refuses a missing target, refuses an already-disabled target
    (`pwdhash is None`), nulls `pwdhash` + `jwt_signing_key` via
    `db.users.update`, and returns the `AdminUserResponse` (active false).
  - A **typed admin error** the service raises for domain refusals, carrying a
    discriminator distinguishing the taxonomy cases (username-taken, not-found,
    self-target, already-disabled, password-invalid) so step 002's route can map
    each to its status (decision 2). Password-policy failures surface through this
    error's password-invalid case.
- **Shared password policy** — the min-length-8 + confirm-match check reused for
  create and reset. Reuse 003's setup password validation rather than adding a
  third copy (see step context for placement).
- **`db.users.get_all`** (in `app/db/users.py`) — session-free; opens its own
  session, selects all `User` rows ordered by username, returns them as a list;
  ORM/session never leaks. Mutations continue to go through the existing
  `update(user)` — no new per-field db funcs.

## Definition of done

1. `[test]` **US-006.AC-1** — `create_user` with an untaken username, a valid
   password, and a role of `author` (and separately `admin`) creates the account
   with that role; the returned `AdminUserResponse` shows that role and `active`
   true.
2. `[test]` **US-006.AC-2** — `create_user` with an already-taken username is
   refused (raises the admin error's username-taken case; no account created).
3. `[test]` **US-007.AC-1** — after `set_user_password`, the account's stored
   credential verifies against the new password (via `verify_password`) and not
   the old one.
4. `[test]` **US-007.AC-2** — `set_user_password` on a disabled account
   (`pwdhash is None`) re-enables it: the returned `AdminUserResponse` shows
   `active` true and the credential verifies against the new password.
5. `[test]` **US-008.AC-1** — `set_user_role` on a non-self target updates the
   role; the returned/refetched account shows the new role.
6. `[test]` **US-008.AC-2** — `set_user_role` where the caller is the target is
   refused (raises the admin error's self-target case).
7. `[test]` **US-009.AC-1** — `disable_user` on a non-self target nulls both
   `pwdhash` and `jwt_signing_key`; the returned `AdminUserResponse` shows
   `active` false.
8. `[test]` **US-009.AC-2** — after disable, the account row's `id`, `username`,
   `role`, and `last_login` are unchanged (data + attribution intact).
9. `[test]` **US-009.AC-3** — `disable_user` where the caller is the target is
   refused (raises the admin error's self-target case).
10. `[test]` decision 5 — `disable_user` on an already-disabled account
    (`pwdhash is None`) is refused (raises the admin error's already-disabled
    case).
11. `[test]` **US-005.AC-1** — `list_users` returns one entry per account, each
    carrying its role and last_login, ordered by username.
12. `[test]` **US-005.AC-2** — an `AdminUserResponse` exposes no secret fields
    (no `pwdhash`, no `jwt_signing_key`, no `salt`) and does expose `active`.
13. `[test]` **US-005.AC-3** — the dependency returned by `require_role(admin)`
    rejects a caller with role `author` (raises the 403 error) and returns the
    caller for role `admin` (ladder `author < admin`).
14. `[test]` decision 4 — `create_user` and `set_user_password` refuse a password
    shorter than 8 characters or one whose confirm does not match (raise the
    admin error's password-invalid case).
