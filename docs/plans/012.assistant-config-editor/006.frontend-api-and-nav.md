# 006 — frontend wire contract, nav entries, routes and page shells

## Goal

Create the first frontend surface for the assistant configuration: hand-written wire types, the
`api/assistantConfig.ts` module, two sibling admin nav entries with their flat routes, and two
minimal page shells for steps 007 and 008 to fill.

## Interface intent

Prose only — the `skeleton` agent freezes the exact signatures.

### `frontend/src/types/assistantConfig.d.ts` (new)

Hand-written, wire-exact `snake_case` interfaces mirroring step 002–004's DTOs one-for-one. **All
ids are `string`.** No `any`, no runtime validation, **no runtime values** (option constants live in
the `.ts` api module, `api/llmServers.ts:27-31`).

- **A tool** — `name`, `description`.
- **An assistant mode** — `key`, nullable `system_prompt`, `tool_names`, `sub_agent_ids`, and the
  two timestamps typed with `ISODateString` from `common.d.ts`.
- **A sub-agent** — `id`, `name`, `system_prompt`, `disabled`, nullable `llm_server_id`, nullable
  `model_name`, `tool_names`, `mode_keys`, timestamps.
- **A mode update payload** and **a sub-agent create/update payload** matching the request bodies.

**No list-envelope interfaces** — envelopes are unwrapped in the api layer and never modelled
(`context.md` → frontend constraints).

### `frontend/src/api/assistantConfig.ts` (new)

A `const BASE = "/api/admin/assistant-config"` plus one thin function per endpoint, each delegating
to `request<T>` from `api/client.ts`, each taking `signal?: AbortSignal` as its **trailing**
argument:

- **list tools** → unwraps `.items`, returns the tool array.
- **list modes** → unwraps `.items`, returns the mode array.
- **save a mode** — takes the mode key and the update payload, returns the updated mode.
- **list sub-agents** → unwraps `.items`, returns the sub-agent array.
- **create a sub-agent** — takes the payload, returns the created sub-agent.
- **update a sub-agent** — takes the id and the payload, returns the updated sub-agent.
- **disable a sub-agent** / **enable a sub-agent** — take the id, return the updated sub-agent.

Also export a **runtime label map for the five mode keys** — a `Record` from mode key to a
human-readable label (e.g. `edit-character` → "Edit character"). This lives here, not in the
`.d.ts`, per the runtime-constants rule, and it is what stops steps 007 and 008 each inventing
their own labels. It must be **total over the five keys** and its lookup must degrade to the raw key
for anything else, so an unexpected key renders rather than crashing.

### `frontend/src/admin/components/shell/navItems.ts`

Append **two** `AdminNavItem` objects to `ADMIN_NAV_ITEMS` — `/assistant-modes` → "Assistant modes"
and `/sub-agents` → "Sub-agents" — plus their two `@tabler/icons-react` icon imports (the coder
picks two sensible icons from that package). Nothing else in the module changes: the
`AdminNavItem` interface, `ADMIN_NAV_ITEMS`' readonly-ness and `isNavItemActive` are untouched, and
`AdminNav.tsx` renders the new entries generically with no edit.

### `frontend/src/admin/routes.tsx`

Add two `<Route>` elements to the existing flat `<Routes>`, **above** the `path="*"` catch-all, with
their two imports. Flat single-segment paths, matching the Users / LLM Servers / Database shape. No
`<Outlet/>`, no layout route, no nested route.

### `frontend/src/admin/pages/AssistantModesPage.tsx` and `SubAgentsPage.tsx` (new)

Minimal `observer` page shells: each is a default-exported component rendering
`Container size="lg" py="md"` with a `Title` and nothing more. **Deliberately no data loading, no
page-state class, no `useEffect`, no api call** — step 007 and step 008 own those. The reason is
recorded in `006.context.md`: `frontend/tests/admin/routes.test.tsx:9-13` deliberately never
navigates to a real page *because the pages fetch on mount*, and a fetch-free shell keeps this step
from making that spec's premise false before 007/008 are ready.

## Definition of done

1. `[test]` `ADMIN_NAV_ITEMS` contains an "Assistant modes" entry at `/assistant-modes` and a
   "Sub-agents" entry at `/sub-agents`, each with an icon, and the pre-existing Users / LLM Servers
   / Database entries are still asserted **by name and path**. Where
   `frontend/tests/admin/navItems.test.ts` already pins the array — an exact length, a full-array
   equality, an ordered label list — those assertions are **extended to the new, longer list**, not
   weakened to a `.some()` or subset check (UC-095 step 1, UC-097 step 1 — the admin can reach both
   surfaces).
2. `[test]` `isNavItemActive` marks each new entry active for its own path and not for the other's,
   nor for `/`; and `frontend/tests/admin/AdminNav.test.tsx`'s rendered-nav assertions cover the two
   new entries alongside the existing ones, still pinned rather than sampled (UC-095 step 1,
   UC-097 step 1).
3. `[test]` The api module's mode functions call the expected `/api/admin/assistant-config/...`
   URL and method, **unwrap the `items` envelope** to a plain array for the list calls, and pass a
   supplied `AbortSignal` through (US-110.AC-1, US-111.AC-1).
4. `[test]` The api module's sub-agent functions do the same for list, create, update, disable and
   enable, each hitting its own URL and method (US-113.AC-1, US-114.AC-1, US-114.AC-2).
5. `[test]` The tool-catalogue call unwraps to a plain array of `{ name, description }`
   (UC-095 step 3).
6. `[test]` An error response surfaces as an `ApiError` carrying the HTTP status, so callers can
   branch on 409 vs 400 — the api layer neither swallows nor re-wraps it (US-113.AC-3).
7. `[test]` The mode-label map covers all five mode keys and returns the raw key for an unknown one
   (UC-095 precondition — the fixed system set of five).
8. `[manual/live]` `cd frontend && npm run build` (= `tsc && vite build`) succeeds,
   `cd frontend && npm run test:types` succeeds, and `cd frontend && npm test` is green.
9. `[manual/live]` Both new nav entries appear in the running admin SPA and navigate to their pages
   without a console error (`cd frontend && npm run dev`).
