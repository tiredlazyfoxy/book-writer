# 001 — db-layer completion and the seed-on-import fix

## Goal

Fill the nine missing session-free `db/` functions the assistant-config service will need — an
update on each config table, the two reverse lookups, and the three replace-set bulk deletes — and
close the first-run gap where an instance bootstrapped by DB import never seeds the five modes.

## Interface intent

Prose only — the `skeleton` agent freezes the exact signatures. Every function below is
**session-free**: it opens its own session internally via `get_standalone_session()` and returns
detached rows or plain values, exactly like the existing functions in the same modules. Nothing new
is imported into `db/` beyond what those modules already use.

- **`db/assistant_modes.py`** — add an **update**: given a mode row carrying its already-mutated
  fields, persist it and return nothing. Mirror `db/llm_servers.py:62 update(server) -> None`
  (take the row, not a field bag). The existing `DEFAULT_MODE_KEYS`, `create`, `get_by_id`,
  `list_all`, `seed_default_modes` are untouched.

- **`db/sub_agents.py`** — add three:
  - **`list_all`** — every `SubAgent` row, ordered by `name` ascending so the admin list is stable
    (the existing `assistant_modes.list_all` is unordered; do not copy that).
  - **`get_by_name`** — one row matched on the exact `name`, or `None`. This is the lookup the
    409 name-uniqueness check in step 003 runs *before* attempting a write, so the service refuses
    with a typed reason rather than surfacing a raw integrity error.
  - **`update`** — same row-in / `None`-out shape as `assistant_modes.update`.

- **`db/mode_tools.py`** — add **`delete_by_mode`**: delete every `ModeTool` row for a mode key and
  return the number deleted. This is the first half of the replace-set save (`context.md` →
  "Replace-set semantics"). Return the count rather than `None` so a caller can assert the set was
  cleared; unlike `db/llm_servers.py:71 delete`, a zero result is **not** an error — an unconfigured
  mode legitimately has no rows.

- **`db/subagent_tools.py`** — add **`delete_by_sub_agent`**, same contract keyed on the sub-agent
  id.

- **`db/mode_subagents.py`** — add three:
  - **`list_by_sub_agent`** — every `ModeSubagent` row for a sub-agent id. This is the
    **accessible-modes reverse lookup**: the mode side already has `list_by_mode:38`; the sub-agent
    editor needs the same set read the other way round (US-112.AC-2 — one row set, two editors).
  - **`delete_by_mode`** — count-returning bulk delete keyed on `mode_key`.
  - **`delete_by_sub_agent`** — count-returning bulk delete keyed on `sub_agent_id`. This is also
    the primitive the disable cascade uses in step 004.

- **`services/setup.py`** — in `import_database` (`:69-87`), call the existing
  `assistant_modes.seed_default_modes()` on the import bootstrap path, in the same relative
  position `create_database` (`:57`) uses it: after the schema exists and before readiness is
  flipped. **Do not write a second seed implementation** and do not change `create_database`. The
  seed is already an idempotent check-then-create keyed on `key`, so running it after an archive
  that already contained the five modes must converge, not collide — that is exactly the property
  the natural-key PK buys (`assistant-config.md` → "Seeding"). This is the whole of the ~5-line
  change; `services/setup.py` is otherwise untouched.

## Definition of done

1. `[test]` `assistant_modes.update` persists a changed `system_prompt` (including setting it back
   to `None`) and a changed `modified_at`, and a subsequent `get_by_id` reads the new values back
   (US-110.AC-1).
2. `[test]` `sub_agents.list_all` returns every row ordered by `name` ascending, including rows with
   `disabled = True` — the db layer filters nothing; `sub_agents.update` persists changed scalar
   fields and reads back (US-114.AC-1).
3. `[test]` `sub_agents.get_by_name` returns the matching row for an exact name and `None` for a
   name no row carries (US-113.AC-3).
4. `[test]` `mode_tools.delete_by_mode` removes exactly the rows for the named mode, leaves other
   modes' rows intact, returns the number removed, and returns `0` without raising when the mode has
   no rows (US-111.AC-1).
5. `[test]` `subagent_tools.delete_by_sub_agent` behaves the same way, scoped to one sub-agent id
   (US-113.AC-1).
6. `[test]` `mode_subagents.list_by_sub_agent` returns exactly the link rows for that sub-agent, and
   the same link row created from the mode side is visible through it — one row set, read from both
   directions (US-112.AC-2).
7. `[test]` `mode_subagents.delete_by_mode` and `mode_subagents.delete_by_sub_agent` each remove
   only their own slice of the same table: deleting by mode leaves that sub-agent's links to other
   modes intact, and deleting by sub-agent leaves that mode's links to other sub-agents intact
   (US-114.AC-2).
8. `[test]` After `services/setup.py:import_database` completes on a fresh instance, all five
   `DEFAULT_MODE_KEYS` rows exist — an instance bootstrapped by DB import is no longer missing its
   modes (UC-095 precondition "the mode is one of the fixed system set of five"; US-110.AC-1 has
   nothing to store a prompt on otherwise).
9. `[test]` The seed on the import path is idempotent and non-destructive: importing an archive
   whose `assistant_modes` rows already carry `system_prompt` values leaves those values intact and
   creates no duplicate row, and there are still exactly five modes (UC-095 precondition;
   `assistant-config.md` → "Seeding").
10. `[manual/live]` `cd backend && .venv/Scripts/python -m pytest` is green, including the
    pre-existing `tests/test_data_domain_mode_seed.py`, `test_data_domain_assistant_core.py` and
    `test_data_domain_assistant_links.py` suites.
