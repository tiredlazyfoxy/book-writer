### `frontend/src/admin/routes.tsx:16-25`

anywhere in the admin SPA — that shape was explicitly rejected at `AdminShell.tsx:68-72`. Do not
introduce one for a modes/sub-agents grouping (`context.md` → scope decision 2).

## The api layer

`frontend/src/api/client.ts`:

```ts
class ApiError extends Error { constructor(public status: number, message: string, public details?: unknown) }  // :6
function request<T>(url: string, opts: RequestOptions = {}): Promise<T>                                         // :39
// injects the bearer token, returns `undefined as T` for 204, one silent refresh attempt on 401
```

Module conventions taken from `api/llmServers.ts`:

- `const BASE = "/api/admin/..."` at the top.
- **List envelopes are unwrapped in the api layer** — `listServers` returns `LlmServer[]` from
  `.items`. Do the same, and do not model the envelope in the `.d.ts`.
- `signal?` is always the trailing parameter.
- Call sites use namespace imports.
- Runtime `*_OPTIONS`-style constants live in the `.ts` api module, **never** in a `.d.ts`
  (`llmServers.ts:27-31`). The mode-label map follows that rule.

## Why the page shells do not fetch

`frontend/tests/admin/routes.test.tsx:9-13` deliberately never navigates to a real admin page,
because those pages fetch on mount. Shipping fetch-free shells in this step keeps that premise
intact for one more step; steps 007 and 008 replace the shells with loading pages, and their own
specs mock `api/assistantConfig` (and `api/llmServers`) at the module level, which is how the
existing page-level specs handle it.

## The two pre-existing nav specs are in scope — extend their pins, do not weaken them

`frontend/tests/admin/` contains exactly six specs: `AdminNav.test.tsx`, `AdminShell.test.tsx`,
`adminGate.test.ts`, `AdminUserMenu.test.tsx`, `navItems.test.ts`, `routes.test.tsx`.

Two of them are in this step's **Test files** because this step's change is what invalidates them:

- **`frontend/tests/admin/navItems.test.ts`** — very likely enumerates `ADMIN_NAV_ITEMS`; the
  work-SPA sibling `frontend/tests/work/navItems.test.ts` is explicitly recorded as *pinning its
  table*, and the admin spec is built from the same mould.
- **`frontend/tests/admin/AdminNav.test.tsx`** — renders the nav, so a rendered-label or
  rendered-link assertion covering the full item set is the expected shape.

**Instruction to the test-coder:** where either spec asserts an exact `ADMIN_NAV_ITEMS` length, a
full-array equality, or an ordered label/path list, **extend those assertions to the new longer
list** — keep the five existing entries asserted **by name and path**, and add the two new ones in
their appended position. Do **not** relax a pin to a `.some()`, a `toContain`, a subset match, or a
length-agnostic check: the pin is the thing that makes an accidental nav change visible, and
loosening it to make this step pass would silently spend that guarantee.

The other four specs are **not** in scope and must not be touched.

## Testing notes for this step

- `vitest.config.ts` has `globals: false` — import `describe` / `it` / `expect` / `vi` from
  `"vitest"` explicitly. `restoreMocks: true`, so set mock implementations in `beforeEach` via
  `vi.mocked(...)`.
- The **api-module** spec is the one place in this feature that legitimately tests against the HTTP
  boundary rather than mocking `api/`: mock `../../src/api/client` (the `request` function) with a
  module factory and assert the URL, method, body and `signal` it receives. Every other spec in this
  feature mocks the `api/assistantConfig` module itself.
- The **new nav** spec (`assistantConfigNav.test.tsx`) covers what the two pre-existing specs do not
  — the new entries' own behaviour under `isNavItemActive`. Do not duplicate into it assertions that
  belong in `navItems.test.ts`; extend that file instead.
- Any spec that renders must go through `renderWithProviders` (`tests/support/render.tsx:29`) —
  `MantineProvider env="test"` is load-bearing.
