# Step 003 — step-specific context

## The fixed five modes

`assistant-config.md` → "AssistantMode — the fixed five, seeded" and
"Persistence and registry obligations" → "Seeding":

- Keys: `edit-character`, `edit-location`, `edit-fact`, `write-chapter`,
  `close-chapter`. Fixed system set — not admin-creatable; the admin later edits
  `system_prompt` and selections but never adds/removes a row.
- Seeded with `system_prompt = None` (null-or-empty is valid, US-110.AC-4).
- The PK being the natural `key` string is exactly what makes seed + import
  converge: import is an idempotent UPSERT on `key`, so a self-seeded instance
  and an incoming archive of the same keys reconcile instead of colliding on
  disagreeing surrogate ids. This is the recorded reason for the natural-key
  exception (`assistant-config.md`, `domain-model.md`).

## Seed placement

Per the briefing decision: the seed logic is a **session-free `db/` helper**
(`seed_default_modes()` in `db/assistant_modes.py`) so no ORM/session leaks into
`services/setup.py`; the service only calls it. Reuse the module's own `create`
/ `get_by_id` (from step 001) — check-then-create so an existing row is never
overwritten.

## `services/setup.py` touch-point

`create_database` is one of the two sanctioned service touch-points for this
feature (the other is `services/db_import_export.py`). Insert the
`seed_default_modes()` call **after** the existing `await init_db()` (tables must
exist first) and **before** `set_db_ready(True)` (the instance must not report
ready until modes are seeded). Do not alter any other step of the setup flow.
The exact `create_database` signature is frozen by the skeleton agent.
